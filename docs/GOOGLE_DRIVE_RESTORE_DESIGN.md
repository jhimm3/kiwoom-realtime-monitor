# Google Drive 복원 원자성 설계 검토

검토·로컬 구현일: 2026-09-25 · 제품: 2.1.0 · 상태: **원격 v2 실계정 게시와 격리된 시작 전 복원·강제 종료 복구 검증 완료**

## 현재 구현 범위

사용자가 설정창의 **다음 실행 때 선택 항목 복원**을 누르면 다운로드한 설정·테마·뉴스 AI 파일을 SHA-256과 함께 `data/strict_restore/operations/<id>/`에 보관하고 `current.json`에 `STAGED`를 기록한다. 이때 운영 DB는 바꾸지 않는다. 앱을 정상 종료하고 다시 열면 DB 초기화보다 먼저 공통 데이터 폴더 잠금을 독점 획득한다. 다른 지원 앱 프로세스가 남아 있으면 최대 30초 기다린 뒤 적용하지 않고 시작을 중단한다.

독점 구간에서 `monitor.sqlite3`와 선택 뉴스 AI가 쓰는 `news.sqlite3`의 SQLite 온라인 사본, 뉴스 설정 파일 및 변경 대상 아이콘·소리의 이전 bytes/부재 여부를 보존한다. 이 구현은 테마 FK/cascade의 수정 범위를 놓치지 않도록 **대상 DB 전체의 변경 전 사본**을 사용한다. 이는 아래 원래 권고안의 선택 행 before-image와 다른 구현 선택이며, 복구할 때 관련 없는 DB 행도 복원 직전 상태로 되돌린다. 지원 프로세스는 적용 중 쓰지 못하도록 막지만 외부 독립 스크립트는 이 잠금을 따르지 않을 수 있다. 저장 공간은 두 DB 크기의 약 두 배와 작업 여유 64MiB 이상을 시작 전에 검사한다. 완료/복구 자료는 자동 삭제하지 않으며 디스크 비용과 보존 정책이 후속 검토 대상이다.

`PREPARED` 다음, 첫 운영 쓰기 전에 `APPLYING`을 기록한다. 정상 종료면 `COMMITTED`, 적용 오류면 사본 해시를 확인한 후 DB·파일을 복구해 `ROLLED_BACK`으로 기록한다. 강제 종료가 `APPLYING`/`ROLLING_BACK`에서 일어나면 다음 시작에 다시 복구한다. 사본·원장이 손상되거나 잠금을 얻지 못하면 정상 앱 시작을 막는다. 설정·테마 SQL은 기존 단일 트랜잭션을 재사용하며 뉴스 AI는 별도 DB 트랜잭션이다. 예약 뒤 같은 실행의 Drive 업로드·다운로드는 재시작까지 막는다. 일반 즉시 다운로드는 종전 동작을 유지한다.

임시 DB 검사 10건에서 설정·테마·뉴스 AI 묶음의 정상 적용, 두 번째 저장소 실패, 뉴스 DB의 기존 부재, 적용 도중 자식 프로세스 강제 종료·재시작 복구, 이전 사본 손상 차단, 다른 프로세스와의 잠금 경합을 확인했다. 이 첫 격리 검사 당시에는 실제 Drive 실계정·전체 GUI·장시간 고아 자식 경합·디스크 부족/권한 장애·Windows 전원 중단 내구성을 확인하지 않았다. 이후 Drive 실계정 게시와 격리 복원 결과는 아래 날짜별 기록을 따른다.

2026-09-25 후속 구현: 업로드는 불변 세대 파일(`kiwoom-monitor-v2-<세대>-<구성요소>.json`)을 먼저 만들고, 마지막에 `kiwoom-monitor-manifest-v2.json`을 게시한다. 새 클라이언트는 manifest가 가리키는 파일 ID·크기·SHA-256을 모두 확인한 뒤 그 세대만 적용한다. manifest가 없는 기존 Drive는 v1 고정 파일을 읽고, 첫 v2 업로드 시 선택하지 않은 설정/테마 파일도 검증 후 불변 파일로 고정한다. v2가 있으면 손상된 manifest나 구성요소를 v1로 조용히 대체하지 않는다. 구형 클라이언트를 위해 선택한 v1 별칭도 갱신하지만, 그 별칭은 다중 파일의 원자성을 제공하지 않으며 새 클라이언트는 v2 manifest를 우선한다. 선택한 설정과 테마는 동일 `monitor.sqlite3` 읽기 트랜잭션에서 만든다. 뉴스 AI는 별도 `news.sqlite3` 스냅샷이며 두 DB 사이의 같은 순간성까지 보장하지 않는다. 업로드 실패가 manifest 게시 전에 발생하면 새 구성요소 파일은 미참조 잔여 파일로 남을 수 있다. 격리 테스트 14건은 구성요소 업로드, v1 별칭 갱신, 최종 manifest 게시 실패 주입에서 기존 manifest가 선택 상태로 남는 것과 다운로드 구성요소 hash/size 불일치가 로컬 적용 전에 차단되는 것을 확인했다. 이는 실제 Google API 장애 동작 검증은 아니다. 첫 게시 전 읽기 전용 조회에서는 앱 폴더와 v1 별칭 세 개만 있었고 v2 manifest는 없었다. 이후 실제 v2 게시·격리 복원은 아래에 기록했으며 잔여 파일의 자동 정리 정책은 미결정이다.

2026-09-25 실계정 게시 후속: 기존 뉴스 AI JSON은 약 11.2 MB라 일반 업로드 요청이 시간 초과됐다. 재개 업로드로 세 불변 구성요소와 구형 v1 별칭은 완료됐으나 최종 manifest 생성은 Google API HTTP 500으로 실패했다. 설정·테마·뉴스 AI 각 원격 파일을 내려받아 크기·SHA-256·형식을 검증하고 v1 별칭의 바이트와 일치함을 확인한 뒤, 같은 세대 `13c8af69f64549db8a8c59ea60fd61b7`의 manifest만 게시했다. 게시한 manifest를 다시 읽어 generation·세 참조 정보를 검증했다. 설정은 6,537 B, 테마 592,681 B, 뉴스 AI 11,230,132 B다. 업로드 코드는 5 MiB 이상에 1 MiB resumable chunk를 사용하고 모든 업로드 변경 요청에 `num_retries=3`을 적용한다. 첫 실패 이전의 미참조 세대 파일은 삭제하지 않고 보존한다. 운영 자료 변경이 따르는 실제 복원과 미참조 파일 정리는 수행하지 않았다. Drive·엄격 복원·설정·테마 인접 회귀 40건이 통과했다. 이 게시 단계의 결과만으로는 복원 경로가 검증된 것은 아니었고, 실제 격리 복원은 아래 후속 기록에서 확인했다.

2026-09-25 격리 복원 후속: 실계정의 활성 v2 manifest와 세 구성요소를 실제로 다운로드해 빈 임시 monitor/news DB에 적용했다. 현행 설정 87개와 테마 프로필 2개, 종목 뉴스 AI 8,694건, 공통 뉴스 AI 2,421건이 원격 파일 내용과 일치했다. 두 DB의 무결성 검사도 `ok`였다. 백업 JSON에 있는 옛 설정 키 7개는 `DEFAULT_SETTINGS`에 없어 의도된 import 허용 목록 밖이다. 최초 시험의 불일치는 이 옛 키까지 비교한 시험 코드 오류였고, 최초 임시 폴더 정리 오류는 시험 코드가 SQLite 연결을 닫지 않은 탓이었다. 운영 DB를 대상으로 한 복원이나 앱 재시작 단계의 엄격 복원은 이번 검사에 포함하지 않았다.

2026-09-25 시작 전 엄격 복원 격리 후속: 같은 실제 v2 세대를 임시 데이터 폴더에 예약해 원장에 `STAGED`와 원격 manifest에 일치하는 세 입력의 SHA-256·크기를 확인했다. 예약 상태의 활성 설정·뉴스 DB는 변경되지 않았다. 별도 Python 프로세스에서 앱이 사용하는 `enter_main()`을 호출했고 `COMMITTED` 원장, 복원 전 DB 사본, 복원 뒤 테마 2개·뉴스 AI 8,694건·공통 AI 2,421건, 두 DB 무결성 `ok`를 확인했다. 이 시험은 실제 사용자 데이터 폴더나 GUI를 시작하지 않았으며, Windows 전원 중단·두 PC 동시 복원·운영 자료와 동시 작업의 위험까지 해소하지는 않는다.

2026-09-25 실제 세대 실패 복구 격리 후속: 같은 원격 v2를 별도 임시 폴더에 예약하고 시작 프로세스에서 `NewsAIBackupService.import_from()`에 예외를 주입했다. 설정·테마 적용 후 실패한 복원은 `ROLLED_BACK` 원장을 기록했고, 설정 시험값·테마 프로필 수·뉴스 AI 빈 상태와 두 DB 무결성이 복원 전과 같았다. 다음 프로세스 시작은 해당 작업을 다시 적용하지 않았다. 이는 제어된 예외·정상 프로세스 종료의 검증이며 운영 사용자 폴더, 비정상 종료나 전원 중단 검증으로 확대 해석하지 않는다.

2026-09-25 실제 세대 강제 종료 격리 후속: 같은 v2를 임시 폴더에 예약한 뒤, 설정·테마 DB 적용이 끝나고 뉴스 AI 적용에 진입할 때 자식 프로세스를 `os._exit(23)`으로 종료했다. 원장에 복원 전 사본과 `APPLYING`이 남았고 설정값은 부분 변경된 상태였다. 다음 별도 프로세스의 `enter_main()`이 이전 설정·테마·뉴스 상태를 복원하고 `ROLLED_BACK`을 기록했으며 두 SQLite 무결성 검사가 `ok`였다. OS 종료·전원 장애에서 파일 flush 내구성까지 보장한다는 뜻은 아니다.

2026-09-25 원격 세대 목록 점검: Drive 폴더에 v2 manifest 1개, 세대 2개가 있다. 활성 세대 `13c8af69f64549db8a8c59ea60fd61b7`의 구성요소 3개는 모두 manifest가 참조한다. 첫 시간 초과 업로드에서 남은 `48e064cc19de4e078988c18326a76768`의 설정·테마 파일 2개(599,218 B)는 참조되지 않는다. 이는 이름·ID·수정시각을 읽은 결과이며 파일 삭제의 안전 조건을 뜻하지 않는다. 현재 정책은 자동 삭제를 하지 않고, 다른 PC의 진행 중 게시·이전 세대 보존 목적을 구분할 보존 기간과 정리 절차를 정할 때까지 그대로 둔다.

## 결론

Google Drive에서 선택한 설정·테마·뉴스 AI 결과와 포함된 뉴스 설정·이미지·소리를 적용하는 범위를 검토했다. 전체 앱 데이터, 시세·분봉·매매일지·계좌·NAS 운영 DB 복원을 뜻하지 않는다.

권고는 두 단계다. 먼저 **선택한 설정·테마 JSON 전체의 DB 변경**을 같은 `monitor.sqlite3` 트랜잭션으로 묶는다. 엄격한 전체 복원이 필요할 때에는 **다운로드·검증 후 다음 앱 시작 전 전용 복원 단계에서 적용하고, 미완료 복원은 정상 실행 전에 되돌리는 방식**을 사용한다. 평소 자동 동기화를 재시작 복원으로 자동 변경하지 않는다.

여러 파일을 디스크에서 동시에 교체한다는 보장은 하지 않는다. 복원 중간 상태를 앱·자식 프로세스·NAS 동기화가 사용하지 못하게 하고, 정상 실행을 허용할 때는 모두 복원 전이거나 모두 복원 후인 **앱 관측 기준의 원자성**을 목표로 한다. 이 접근은 저장소 소유권·시작 경계의 변경이 필요하지만 운영 DB를 통합하거나 모든 읽기 경로를 세대별 DB로 바꿀 필요는 없다.

### 앱 시작 순서 실사와 변경 이유

최초 기본 실행은 `bootstrap.main()`에서 자식 실행 인자(`--central-server`, `--journal-process`, `--news-process`, `--research-process`)를 먼저 분기했다. 일반 앱 경로도 `AppPaths` 생성 뒤 `Database.initialize()`를 호출하고 로컬 중앙 서버와 뉴스 DB 이관을 시작한 다음 중앙 콘텐츠 동기화 thread·테마 조회·메인 창을 열었다. 이번 구현은 복구 gate를 `Database.initialize()`보다 앞으로 옮기고 각 지원 자식 진입점에도 공유 수명 잠금을 붙였다.

뉴스 프로세스는 별도 진입 후 `initialize_news_database()`를 직접 실행한다. 매매일지 프로세스는 자체 SQLite repository를 열고 백그라운드 worker에서 추가 자료를 저장한다. 부모 PID 감지에만 의존하지 않도록 지원 자식이 저장소를 열기 전에 공통 공유 잠금을 획득하고 종료할 때 해제하게 했다. 복원자는 독점 잠금을 얻기 전에는 운영 데이터를 적용하지 않는다.

구현 전제는 **모든 지원 프로세스의 저장소 진입 전에 같은 복구/소유권 계약을 확인하는 것**이다. 잠금을 획득하지 못하면 DB migration·초기화·복원·중앙 동기화를 시작하지 않아야 한다. 프로세스 목록 확인만으로 잠금을 대체하지 않는다. 이 계약을 적용할 진입점은 bootstrap의 네 자식 경로와 일반 경로, 뉴스·일지 repository 초기화이며, 동작 중 명시 복원을 예약할 때는 기존 보조 프로세스와 worker가 종료된 사실도 확인해야 한다.

현재 구현에서 `target=settings/themes/both`와 무관하게 원격 뉴스 AI 파일이 있으면 함께 가져온다. 새 엄격 복원의 사전 화면은 실제 적용할 구성요소를 명시해야 한다. 기존 선택 의미를 이번 문서만으로 변경하지 않는다.

### 격리된 재현 결과

운영 DB·Google Drive·NAS를 사용하지 않고 임시 SQLite와 파일만 사용했다. 모든 재현은 마지막 실행 종료 코드 0으로 끝났다.

재현 1~4는 이전 구현에서 발견한 결함을 설명한다. 1·2는 한 JSON 내부와 순차 복원의 DB 경계를 비교한 결과다. 3의 오류 무시와 4의 문자열 판정은 이번 로컬 수정으로 고쳤지만, 강제 종료 복구나 실제 UI 동작을 확인한 결과는 아니다.

1. **한 JSON 내부 실패:** 설정 `decimal_strength=4`를 3으로 변경하고 중복 테마 프로필로 제약 오류를 발생시켰다. 설정은 4로 롤백됐다.
2. **두 파일 순차 적용 실패:** 설정만 먼저 적용하고 다음 테마 적용에서 같은 오류를 발생시켰다. 설정은 3으로 남았다. 이 결과를 근거로 Drive 설정·테마를 한 monitor DB 트랜잭션으로 묶었다.
3. **자산 저장 실패:** 임시 PNG 대상 쓰기에 `OSError`를 주입했다. 이전 구현은 오류를 무시했다. 현재 구현은 입력을 DB commit 전에 검증하고 파일 쓰기 오류를 실패 결과로 반환한다. 강제 종료 때 다수 파일을 원상복구하는 동작은 아직 없다.
4. **성공 후 화면 갱신 조건:** 이전에는 반환 문구와 메인창 문자열 조건이 일치하지 않았다. 현재는 명시 결과 상태와 적용 여부로 판정하도록 바꿨다. 실제 화면 실행은 아직 확인하지 않았다.

첫 진단 실행은 진단 코드가 SQLite 연결을 닫지 않아 임시 폴더 정리 중 `WinError 32`로 실패했다. 연결을 명시적으로 닫은 재실행 결과만 위 근거로 사용한다.

## 대안 비교

| 대안 | 얻는 보장 | 판단 |
|---|---|---|
| 파일별 트랜잭션 + 완료/실패 표시 | 실패 위치를 알 수 있고 재시도 가능 | 온라인 동기화의 제한적 보완. 전체 rollback은 아님 |
| SQLite `ATTACH`로 두 DB를 한 commit에 포함 | 조건을 만족하는 SQLite 파일 사이의 원자성 | 파일 설정·아이콘은 포함하지 못함. 실행 중 앱의 정책을 바꾸는 단독 해결책으로 채택하지 않음 |
| 운영 DB 전체를 복사·교체 | 전용 정지 상태에서는 복원 가능 | 백업 대상과 무관한 실시간 기록까지 되돌릴 수 있고 뉴스 DB 크기·열린 연결 문제가 있어 비권고 |
| 세대별 모든 저장소 + 단일 활성 세대 포인터 | 모든 소비자가 포인터 계약을 따를 때 세대 전환 가능 | 모든 저장소·읽기 경로·기존 작업자의 수명을 바꿔야 하므로 이 기능에는 과도함 |
| 시작 전 복원 단계 + 변경 전 자료 원장 + 실패 복구 | 정상 앱 실행 전에 전부 성공/전부 복구를 확정 | **엄격한 전체 복원의 권고안** |

이전 설명의 “DB가 다르므로 한 트랜잭션으로 묶을 수 없다”는 단정은 정정한다. SQLite `ATTACH`는 main이 메모리 DB가 아니고 WAL이 아닌 등의 조건에서 DB 간 원자성을 지원한다. WAL에서는 각 DB 내부만 원자적이며 DB 묶음의 crash 원자성을 보장하지 않는다. 현재 PC 운영 DB의 journal mode를 이 검토에서 측정하지 않았으므로 WAL이라고 가정하지 않는다. 어느 모드든 일반 파일 쓰기는 SQLite 트랜잭션에 포함되지 않는다. [SQLite ATTACH 공식 문서](https://www.sqlite.org/lang_attach.html), [WAL 공식 문서](https://www.sqlite.org/wal.html).

## 권고 설계

### 1. 실제 적용 전 입력 확정

- 네트워크 다운로드는 기존 background worker에서 완료한다. 이때 실시간 표를 멈추지 않는다.
- 무작위 `operation_id`, 선택 항목, 각 파일 hash·길이·형식 버전, 예상 대상 DB/파일 경로를 담은 로컬 복원 요청을 만든다. 운영 자료는 아직 변경하지 않는다.
- `TemporaryDirectory` 종료와 함께 지워지는 다운로드를 재개 자료로 쓰지 않는다. 검증한 입력을 앱 데이터 아래 전용 작업 폴더에 보존한다.
- 모든 필드와 관계를 검증하고, 허용된 자산의 디코딩·크기·경로·중복을 검사한다. SQLite 복제본이나 전용 검증 DB에서 동일 적용 코드를 실행해 실제 제약 오류도 미리 확인한다. 이것만으로 디스크·권한·commit 실패가 없어지는 것은 아니다.
- 보안상 허용되지 않는 경로는 적용하지 않는다. 선택된 필수 자산이 손상됐으면 적용 전에 실패로 끝내거나 사용자가 확인한 제외 목록을 새 요청에 고정한다. 오류를 조용히 성공으로 처리하지 않는다.

### 2. 적용 시점과 소유권

- 사용자가 명시적으로 시작한 엄격 복원만 정상 종료 후 다음 시작의 복원 단계로 넘긴다. 장중 자동 다운로드나 모의·실전 작업을 이유 없이 중지하지 않는다. 자동 종료나 강제 종료는 하지 않는다.
- 공통 데이터 폴더 기준 프로세스 간 잠금을 사용한다. 메인·뉴스·매매일지·연구 등 해당 자료를 읽거나 쓰는 진입점은 정상 저장소 초기화·migration·동기화 전에 이 경계를 확인해야 한다.
- 기존 작업자가 모두 종료·연결 반환된 것이 확인되지 않으면 원본 적용을 시작하지 않는다. 단지 잠금 파일이 있다는 사실이나 PID 한 개가 없다는 것만으로 독점 소유를 판정하지 않는다.
- 복원 중 부분 상태를 읽는 UI, 주문 판단, NAS push/pull, Google Drive 자동 업로드를 시작하지 않는다. 다른 PC/NAS까지 rollback하는 분산 트랜잭션을 만들지 않는다.
- 잠금 계약을 따르지 않는 외부 도구의 동시 DB 접근까지 보장한다고 주장하지 않는다. 지원하는 앱 진입점 전체의 협조가 구현 완료 조건이다.

### 3. 변경 전 자료와 완료 결정

- 별도 로컬 SQLite 복원 원장에 입력 hash, 대상 schema/version, 변경 전 자료, 적용 순서와 상태를 영속 저장한다. 원장이 완성·동기화되기 전 운영 자료에 쓰지 않는다.
- 대상은 선택한 settings key·column row·테마 그래프 및 별칭·카탈로그의 실제 수정 필드·선택 뉴스 AI identity와 자산 파일이다. 수정하지 않는 시세/분봉/뉴스 본문/일지 전체를 되돌리지 않는다.
- 테마 삭제가 cascade하는 이름 결정·추천·프로필 관계와 ID까지 before-image에 포함한다. `stocks`의 이름/시장 등을 바꾸더라도 현재가 등의 무관 필드는 건드리지 않는다. 정확한 FK·trigger·기본값 영향 범위를 구현 때 다시 확인해야 한다.
- 파일의 변경 전 bytes와 원래 부재 여부를 남긴다. `naver_news.dat`는 현재 PC 비밀을 보존한 암호문으로 취급하고 복구 자료를 Drive로 올리거나 로그로 출력하지 않는다.
- 두 DB는 각자 명시적 트랜잭션으로 적용한다. 자산은 완성한 임시 파일을 같은 디렉터리에서 교체한다. 파일 하나의 교체 성공을 전체 작업 완료로 해석하지 않는다.
- 모든 구성요소의 내구성 있는 저장·검증 뒤 원장에 `COMMITTED`를 기록한다. SQLite 동기화 설정과 Windows 파일 교체·flush의 전원 중단 내구성은 지원 환경에서 별도 검증한다. 임의의 하드웨어 고장까지 무조건 복구한다고 보장하지 않는다. [SQLite 원자적 commit의 전제](https://www.sqlite.org/atomiccommit.html).

### 4. 중단과 재시작

| 원장 상태 | 다음 시작 시 처리 |
|---|---|
| 준비 중 / `PREPARED` | 원본 미변경을 보장하는 단계. 검증된 입력으로 명시 재시도하거나 취소 |
| `APPLYING` / `ROLLING_BACK` | 일반 앱을 열지 않고 변경 전 자료를 반복 가능하게 복구. 일부 단계 완료 표시만 믿고 건너뛰지 않음 |
| `COMMITTED` | 복원 완료 상태로 캐시를 새로 읽고 정상 실행. cleanup 실패는 이미 완료된 복원을 rollback하지 않음 |
| `ROLLED_BACK` | 이전 상태로 정상 실행하고 복원 실패를 알림 |
| 원장 손상·복구 자료 부족·복구 오류 | 정상 실행 및 외부 동기화를 보류하고 작업 ID와 복구 상태를 표시. 성공 또는 원상복구로 단정하지 않음 |

`APPLYING`은 첫 운영 쓰기 **전에** 영속 기록한다. 변경 후 완료 표시를 쓰기 전 꺼진 경우도 복구 대상이다. 복구 자체가 중단돼도 다시 원상복구할 수 있어야 한다. 원장과 before-image는 최종 완료/복구 및 보존 정책 확인 전 삭제하지 않는다.

이는 중단된 작업을 무조건 계속 진행하는 설계가 아니다. 완료 결정 전 중단되면 우선 이전 상태를 복구하며, 재시도는 같은 고정 입력을 검증해 새 작업으로 시작한다. 성공 후 NAS 공유 정책은 기존 설정을 따르되 전체 commit 전에 외부 변경을 발행하지 않는다.

## 원격 백업 묶음과 로컬 원자성은 별개

로컬 rollback과 원격 세대 manifest는 각자 별도 경계다. v2 manifest는 선택 구성요소의 정확한 파일 ID·크기·SHA-256을 고정하고 manifest 게시 전에 생성된 고아 구성요소를 무시하게 한다. 다만 같은 DB 안에서 선택하지 않은 이전 테마를 함께 묶을 수 있으며, 설정/테마와 별도 뉴스 AI DB의 촬영 시각까지 일치시키지는 않는다.

v1 파일은 manifest가 없는 폴더의 호환 입력으로 읽는다. v2가 게시된 뒤에는 v1 별칭을 계속 갱신해 구형 클라이언트도 최신 내용을 받을 수 있게 하지만, 구형 클라이언트의 다운로드에는 v2의 세대 검증이 없다. 같은 manifest를 동시에 갱신하는 여러 PC의 최종 승자 정책은 Drive가 마지막으로 완료한 manifest이며, 동시 편집 병합은 제공하지 않는다.

## 구현 순서와 완료 조건

1. **한 DB 범위 보완 — 로컬 구현 완료:** 선택 설정·테마 문서를 모두 파싱·검증한 뒤 한 `monitor.sqlite3` 트랜잭션에 적용한다. 뉴스 AI JSON 검증도 monitor DB 적용보다 먼저 한다. 개별 백업 파일 복원 API는 유지한다.
2. **오류와 결과 계약 — 로컬 구현 완료:** 설정 백업 안의 아이콘·소리 파일을 모두 사전 검증하고, 대상별 임시 파일 기록·flush·교체 오류를 반환한다. Drive 작업은 `operation/status/message/local_changes_applied` 결과를 명시하며, 파일 처리 실패 전에 DB commit이 끝난 경우 실패를 표시하면서 앱 메모리·화면을 commit된 DB 상태로 새로 읽는다. 빈 원격 백업 판정과 다운로드 성공 판정은 문구 비교에서 상태 비교로 바꿨다. 구문 검사와 `git diff --check`만 실행했고 회귀 테스트·실제 UI는 확인하지 않았다.
3. **엄격 복원 단계 — 로컬 구현 및 격리 검사 완료:** 메인·중앙 서버·뉴스·일지·연구 자식의 공통 수명 잠금, 영속 입력/상태 원장, DB 전체 사본과 파일 이전 상태, 시작 전 recovery gate, 반복 가능한 rollback을 구현했다. 강제 종료 재시작 시험을 통과했으나 운영 계정·실제 앱 전체·전원 중단 검증은 별도다. 일반 자동 다운로드를 엄격 복원으로 바꾸지 않았다.
4. **원격 v2 — 실계정 게시·격리 시작 복원 완료:** 불변 구성요소와 마지막 manifest 게시, hash/size 검증, legacy 고정 파일 호환, 같은 monitor DB 읽기 시점을 구현했다. 실계정 구성요소·v1 별칭·manifest를 검증하고 원격 v2를 임시 DB 두 개에 적용했으며 별도 프로세스의 시작 전 정상 복원·제어된 실패·프로세스 강제 종료 복구 경로도 통과했다. 운영 사용자 데이터 폴더·GUI 복원, 동시 PC 충돌, 전원 중단과 모든 API 실패 지점의 운영 검증, 고아 세대 정리 정책은 남아 있다.

검증은 정상 복원, 두 번째 JSON 제약 실패, 두 번째 DB commit 실패, 각 파일 교체 실패, 적용/복구 도중 강제 종료, 완료 표시 직전·직후 종료, 디스크 부족·권한 오류, before-image 손상, 다른 앱/자식 프로세스 동시 접근, 키·로컬 전용 설정 보존, NAS에 부분 변경이 나가지 않음, 무관 시세/일지 보존을 포함한다. 단위 테스트뿐 아니라 별도 자식 프로세스 강제 종료 후 재시작 검증이 필요하다.

저장소별 SQL은 기존 backup 서비스가 소유한다. 별도 복원 실행기가 필요하다면 독점 소유·원장·복구 수명을 맡는 한 모듈로 제한하고 범용 분산 트랜잭션 framework를 만들지 않는다. 현재 단계에서 앱의 전체 DB 구조를 바꿀 이유는 없다.

설계 선택은 위 권고안으로 구체화했다. 구현은 동시성·영속 복구 경계를 포함하므로 Sol High 수준이 적절하다. 추가 전체 아키텍처 재설계는 필요하지 않지만, 정상 시작 전 모든 소비자를 차단할 수 없다는 새 증거가 나오면 해당 소유권 경계만 다시 검토한다.
