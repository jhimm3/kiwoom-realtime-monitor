# 증분 테스트 관리

2026-10-18 사용자 요청. 정본 감사는 [5,504개/460모듈 개별 원장](workstreams/test-case-review-20261018/README.md)이다. 원래 판정(유지5,208·보강216·기대값수정19·정리12·미결49)과 [후속 수정/실행](workstreams/test-case-review-20261018/FOLLOWUP.md)을 덮어쓰지 않는다. 본 체계는 원래 전수 의미 검토를 반복하지 않고 **그 뒤 변경분의 근거와 실행**을 관리한다.

## 기존 구조와 새 연결

| 구분 | 담당 |
|---|---|
| 기존 `regression_profiles.json`/`ci_groups.json` | 전체 모듈 등록·단일 배정·Windows/Linux/PG/봉인 replay/operator 경로. 새 목록을 중복 만들지 않는다. |
| 기존 `run_regression`/`select_ci_groups` | 관련 import 소비자 제안, 명시적 실행, 모듈별 발견/실행 수, skip/expectedFailure, 소스·환경·자식 종료·실패 보존. 관련 import 제안은 실제 기능 연결의 증명이 아니다. |
| 새 `check_test_changes` | import/실행 없는 AST 차이, 본문·공용 fixture·decorator 변경, 누락된 검토·개수 변화·ID 연결·원장 재작성 검사. 기존 catalog 검사 재사용. |
| 보완한 기존 실행기 | 계획 ID·실제 실행 ID를 보존한다. 같은 worker/전체 CI 보고서의 ID 중복과 변경 모듈의 예상 발견 수를 확인한다. |
| GitHub 기존 필수 workflow | Windows 전체회귀 전에 정적 검토를 확인하고, 기존 필수 결과 대조 뒤 관련 테스트 ID/실제 실행을 대조한다. 기존 job·플랫폼·일정·성공 요건을 줄이지 않는다. |

`tests/test_review_baseline.json.gz`는 **현재 파일의 기계 목록 채택점**이다. 감사 원문에 대한 참조·해시와 현재 AST 정의/fixture/코드 상태를 자동 기록한다. 실제 runtime ID 5,504개와 정적 정의 수(상속·동적 suite 전개 전)는 다른 단위다. 수를 맞추려고 검사를 제외하지 않는다.

채택 전부터 있던 다른 작업의 미커밋 변경도 기계 목록에는 포함될 수 있다. 그 포함이 해당 변경의 의미 검토·제품 정상·현재 실행 또는 기존 결함 해결을 증명하지 않는다. 원래 감사 판정과 후속 근거는 별도로 남으며 새 ID·기존 감사와의 대응 차이도 채택 정보에 기록한다. 채택 뒤 변경부터는 증분 원장이 필수다. 새 snapshot으로 과거 검토를 초기화하지 않는다.

## 개발할 때의 순서

감사 원장 전체를 매번 읽거나 재분석하지 않는다. 먼저 Git diff와 테스트 변경 감지 결과로 범위를 정한 뒤, 변경된 검사·영향받는 기존 검사·관련 미결 항목만 ID/파일 기준으로 조회한다. 공용 fixture·호출자·소비자 변경의 영향이 확인되면 필요한 범위만 확장한다. 아래의 기존 문제 조회도 전체 결과의 반복 열람이 아니라 관련 항목을 찾는 데 사용한다.

1. 제품 caller→입력/판단→저장/조회→API/UI/후속 소비자에서 관련 기존 테스트를 찾는다. 이미 충분한 결과·실패 검사가 있으면 재사용한다. 새로운 동작/실패만 필요한 만큼 검사한다.
2. `python -m scripts.check_test_changes --plan tmp/test-review-change.json`으로 미기록 차이를 만든다. 제품 import나 테스트 실행은 없다. 기존 import 분석의 `related_module_suggestions`는 제안일 뿐이며 전부 실행하라는 지시가 아니다.
3. 초안의 `id`를 고유하게 정하고 변경 항목의 `reason`, `requirement`, `connection`, `oracle`, `overlap`을 Codex가 검토해 채운다. `oracle`에는 독립 기대 결과·결함 때 실패하는 assertion·fixture/mock가 우회하지 않는 근거를 쓴다. 구현 결과와 같은 값을 다시 적었다는 설명은 근거가 아니다. 제품 항목은 연결과 관련 **실제 테스트 ID**를 기록한다.
4. `module_counts`에는 변경된 모듈의 실제 unittest 발견 수를 쓴다. 정적 정의 수를 그대로 복사하지 않는다. 기존 좁은 profile 또는 지정된 관련 suite를 사용해 발견·실행을 확인한다. 이름 변경/파일 이동은 `renames`의 이전ID→현재ID로 연결한다. 상속/동적 실행 이름은 테스트 항목의 선택 `executed_as`에 실제 ID를 대응한다. 삭제는 목적 종료·대체 검증/호환 범위를 근거로 기록한다.
5. 검토한 JSON 객체 한 개를 **한 줄 JSON**으로 `tests/test_review_changes.jsonl` 끝에 추가한다. 기존 줄을 수정/삭제하지 않는다. `counts`의 추가·수정·삭제/전후 정의 수는 실제 차이와 맞아야 한다. 공용 fixture 변경은 `support`에 별도로 기록하고 그 fixture를 실제 쓰는 `tests` ID를 정한다. module entry가 없는 테스트 본문 수정도 빠짐없이 기록해야 한다.
6. `python -m scripts.check_test_changes --base-ref HEAD --report tmp/test-review-static.json`으로 원장·현재 소스·기존 등록을 대조한다. 관련 테스트 실행 후 `python -m scripts.check_test_changes --base-ref HEAD --execution <관련 실행기의 run.json> --report tmp/test-review-execution.json`으로 현재 소스의 실행 ID와 모듈 수를 확인한다. 여러 플랫폼 보고서는 `--execution`을 반복한다. 이전 소스의 보고서는 재사용하지 않는다.

이 명령은 테스트를 실행하지 않는다. **로컬 전체회귀는 사용자 명시 요청 시에만** 실행한다. 이 작업에서는 기존 `runner` profile에 관리 도구와 PG 실행기 단위 검사를 연결해 세 모듈을 실행한다. 실제 PostgreSQL 연결을 뜻하지 않는다. CI에는 Windows 전체와 기존 Linux/PG 필수 결과를 유지한다. 플랫폼이 다른 관련 검사는 필요한 환경에서 확인하고 미실행 범위를 구분한다.

검증 로그는 성공 건수·실패/오류·미실행 수와 실행/정리 상태를 먼저 요약하고, 실패한 검사에 대해서만 상세 로그를 확인한다. 성공 상세 로그는 보존하되 일괄 열람하지 않는다. 이 조회 원칙은 필요한 검사 범위를 줄이는 지시가 아니며, 영향 범위를 확인하는 데 필요한 검사는 생략하지 않는다.

## 선택적 조회·실행 명령

전체 원장을 대화에 읽어들이기 전에 다음 명령으로 Git 기준 변경과 영향만 조회한다. 기본 범위는 지정 Git 기준→현재 작업 파일이며 staged/unstaged/untracked/삭제를 포함한다. 의미 검토용 `--plan`과 달리 `--query`는 감사 상태 전체를 로드/승인하지 않고 변경 파일의 전후 정의, import 소비자와 관련 감사 항목을 조회한다.

감사 원문은 최초 조회 때만 기계적으로 읽어 `tmp/test-review-query.sqlite3`에 ID/모듈/파일/제품 근거별 파생 조회 인덱스를 만든다. 이후에는 원본 경로·크기·수정시각을 확인하고 관련 행만 조회하므로 압축 원장 전체를 다시 읽지 않는다. 원문 파일이 바뀌면 인덱스만 다시 만들며 의미 재감사나 판정 변경은 없다. 이 캐시는 삭제해도 재생성되며 기준선·원장·후속 상태의 대체 저장소나 승인 근거가 아니다. 원본 무결성 검사는 기존 증분 관리/CI가 담당한다.

```powershell
python -m scripts.check_test_changes --query --base-ref HEAD --limit 10 --report tmp/test-selection.json
python -m scripts.run_regression --selection tmp/test-selection.json --output tmp/selected-run
python -m scripts.run_regression --summarize tmp/selected-run/run.json
```

진행 중인 다른 작업을 제외해 별도 범위를 확인할 때는 조회에 `--path scripts/대상.py` 또는 디렉터리를 반복 지정한다. 이 제한은 보고서와 실행 결과에 남으며 전체 변경의 검증 완료를 뜻하지 않는다. `--offset 10 --limit 10`으로 다음 항목을 조회한다. 화면 출력은 제한된 변경/선정 근거·감사 요약만, 보고서 파일은 전체 **선택 범위**와 근거·원래 감사/후속 상태를 보존한다. 과거 미결/보강과 후속 구현·현재 실행 상태는 합쳐서 자동 완료 처리하지 않는다.

영향 분석은 기존 `select_ci_groups`의 import 그래프를 재사용한다. 직접·간접 소비자, 변경 전 import, 공용 fixture/패키지 초기화, 리터럴 파일/계약 참조와 리터럴 동적 import를 포함한다. 확인하지 못한 동적 import는 기존 소유 profile 범위로 확대해 `uncertainties`에 기록한다. 제품/공용 helper 변경에서는 정적 연결을 찾지 못한 동적 테스트·런타임 importer도 제외하지 않고 소유 범위를 포함한다. 소유 범위가 없거나 공용 설정/계약의 경계가 불명확하면 등록된 환경 전체로 확대한다. 이때 `full_required`(조회 종료2)로 표시하며 로컬 선택 실행은 거절한다. 등록 누락·분석 실패도 성공이 아니다. GitHub는 넓은 영향 보고서를 보존한 뒤 기존 전체/환경별 CI를 그대로 수행하며, 선택 명령으로 기존 CI를 축소하지 않는다. 콘솔의 각 모듈 근거는2개, 불확실성 목록 필드는3개까지만 미리 보여주고 남은 수를 표시한다. 전체 근거는 선택 보고서에 보존한다.

선택 실행은 기존 profile의 batch/모듈 격리·timeout·자식 종료·로그 보존을 재사용한다. 소스와 Git 변경/영향을 재대조해 낡거나 축소 편집된 선택 파일은 거절하고, 실제 발견 모듈·계획/실행 ID·소스 불변을 확인한다. 현재 실행기는 Windows worker 경로이므로 Linux/PG/replay/operator가 포함되면 부분 성공으로 실행하지 않고 해당 환경을 보고한다. 필요한 환경 검증은 기존 경로에서 별도로 수행한다. 전체회귀를 자동 실행하는 우회 옵션은 없다.

성공 출력은 실행 수·실제 통과 수·소요 시간·기존 소스 식별자뿐이다. 실패/오류는 해당 ID·구조화된 원인·로그 경로를, 로딩 실패/timeout 등은 해당 worker의 마지막30줄을 보여준다. 상세 성공 로그는 열람하지 않고 파일에 보존한다. skip/expectedFailure/미실행/timeout/소스 변경은 정상 통과로 표시하지 않는다. `--profile runner --compact`처럼 기존 좁은 profile에도 같은 출력을 적용할 수 있다.

정적 의존성으로 반사 호출·플러그인·자료 기반 연결 전체의 완전성을 증명할 수는 없다. 명령의 선정 근거/불확실성을 Codex가 실제 caller→소비자와 함께 검토하고 필요하면 조회 범위를 확장한다. 필요한 검사를 빼거나 `--path`로 잘라 전체 완료라고 하지 않는다.

이번 보완의 관련92건이 통과했고 실제 선택 파일→실행 명령의17건도 통과했다(별도 고유17건 추가가 아니라92건에 포함). source/선정/발견·실행 ID·종료를 대조했으며, fixture 경로 오류가 났던 최초 결과와 수정 후 결과를 분리했다. 넓은 설정 변경의 `full_required` 및 축소 편집된 선택 파일은 실행 전에 거절한다. 성공/실패/skip/expectedFailure/timeout, 등록 누락·잘못된 Git 기준·동적 범위 확대·누락 발견·캐시 재사용/원본 변경 시 재생성 시나리오를 확인했다. 증거는 `data/diagnostics/selective-tests-20261018/verification-summary.json`이며 실제 hosted CI·Linux/PG 실행을 뜻하지 않는다.

## 기존 결함과 미결의 승계

`python -m scripts.check_test_changes --findings`는 기존 발견 키와 명시 후속 상태를 보여준다. `audit:<원래 검토자>:<원래 발견ID 또는 caseID>` 및 `unresolved:<원래 baselineID>`를 재사용한다. 동일 증상으로 새 항목을 만들기 전에 원래 근거를 확인한다. 자동으로 문장의 의미가 같은지 판단하지는 못한다.

원장의 `findings`는 해당 키, `status`(`open/investigating/deferred/resolved`), 이유와 증거를 기록한다. 새 항목일 때만 `new: true`를 사용한다. 해결에는 `requirement`, `fix`, `tests`가 추가로 필요하며 CI가 새 해결 항목의 검사 ID 실행도 확인한다. 원래 원문과 미결49 판정은 그대로 남는다. 새 테스트·성공 실행·해결 필드의 존재만으로 사실상 해결됐다고 판단하는 것은 Codex의 검토 오류다. 후속 수정의 확인된 로컬 해결과 실제 PG/NAS/장중·예약/계좌 수락의 공백도 분리한다.

## 자동 검사와 사람의 판단

자동으로 확인하는 것은 등록 누락, 중복 정의/실행 ID, 기록되지 않은 추가·본문/fixture/decorator 수정·삭제, 동일 본문 이름 변경의 연결 누락, 예상 정의/발견 수 불일치, 원장/채택점 재작성, 필요한 검토 필드, 명시 관련 테스트의 현재 소스 실행 여부다. skip·expectedFailure는 검토 문장을 적어도 기존 실행기에서 성공이 되지 않는다. 실패를 보고서의 제외로 숨기지 않는다.

현재 요구사항과의 일치, 의미상 중복, 유효한 독립 oracle, mock/빈 fixture/상수 왕복이 결과를 우회하는지, 삭제할 만큼 목적이 끝났는지, 연결된 모든 기능을 골랐는지는 Codex가 판단한다. CI는 검토 문장의 진실이나 수익성·실제 장중 동작을 증명하지 않는다. 과거 버그·자료 복구·호환성·연구 비교를 보호하는 검사는 근거 없이 제거하지 않는다.

## 한계

- 정적 정의 목록은 top-level 클래스의 메서드를 다룬다. 조건부 생성·상속·`load_tests`·동적 monkeypatch는 fixture 변경으로 감지하고 실제 발견 수·실행 ID로 보완한다. 사람이 잘못된 예상 수나 소비자를 골랐는데 우연히 통과하는 의미 결함까지 자동 발견하지 못한다.
- 최초 채택 전 변경의 의미 승인은 소급 생성하지 않는다. 감사에 없는 현재 정의는 채택 정보에서 구분한다. 기존 미결49·분류 oracle·일부 플랫폼/실제 운영 검증 공백을 다시 전체 완료로 바꾸지 않는다.
- 줄바꿈/주석/공백만 다른 Python은 같은 AST로 취급한다. 실제 기대값이나 fixture·skip 조건·활성 테스트 이름은 기록 대상이다. 복잡한 이름/본문 동시 변경은 자동 rename 추정이 불완전하므로 Codex가 이전 ID를 연결한다.
- GitHub에서 이 코드가 실제 실행된 결과는 push 후에만 확인할 수 있다. 로컬 모의 시나리오·관련 실행 결과를 CI 성공으로 보고하지 않는다. NAS·운영 DB·주문·배포·권한에는 연결하지 않는다.

## 도입 중 확인한 결과

관리 도구의 집중 검사20개를 추가하고 기존 실행기 검사3개의 관련 목적을 보강했다. 새 테스트 모듈은 기존 `runner` 프로필에 등록했고 PG 실행기 단위 모듈도 같은 좁은 실행 경로에서 재사용한다. 전체 profile 계획은 기존 중복 제거를 유지한다. 실제 GitHub 필수7개 job과 Windows artifact의 원래 단일 루트/다운로드 위치를 유지했다. 관리 보고서는 별도 artifact로 보존해 기존 `windows/run.json`을 중첩 경로로 바꾸지 않는다.

| 가정 | 실제 확인 |
|---|---|
| 테스트 추가 | 미기록 추가 거절 → 근거와2→3 개수 기록 뒤 통과. 기존 미결 자동 종료0 |
| 기대값/fixture 수정 | 미기록 본문·공유 상수 변경, oracle 누락 거절. skip/skipIf/expectedFailure 변화 노출 |
| 테스트 삭제 | 미검토 삭제와2→1 변화 숨김 거절. 목적 종료 검토 후 기록하되 원래 문제 상태 유지 |
| ID 변경/중복 | 이름 변경·파일 이동의 연결 누락과 같은 이름 정의 덮어쓰기 거절. 실제 worker의 중복 실행도 실패 |
| 실행 누락/낡은 결과 | 현재 소스가 아닌 보고서·누락 ID·skip·관련 검사 미실행과 예상 발견 수 불일치 거절. Git 차이가 없는 예약 실행도 이미 기록된 모듈 수를 대조 |
| 기존 문제 관리 | 원문 변경·기준선 초기화·원장 재작성 거절. 동일 문제 키 재사용, 명시적인 요구/수정/실행 근거 필요 |

위 단위 시나리오와 기존 worker/PG 실행기 단위 검사는 실제 NAS나 PG 수락이 아니다. 실제 명령으로 만든 현재 소스 `runner` 실행 보고서와 증분 검사 결과는 아래 근거 위치에 보존한다. 전수 회귀·commit·push·배포는 실행하지 않았다.

현재 소스의 관련75건/worker3개가 통과했고, 실제 `verified-run/run.json`을 입력한 `verified-execution.json`도 통과했다. 계획/실행 ID와 발견 수가 일치하며 worker/자식 종료·임시 자료 정리와 실행 중 소스 불변을 확인했다. 기존 감사 JSON의 LF/CRLF 차이는 내용 변경과 구분하고 압축 원장은 바이트 그대로 보존한다. 원문을 쓰지 않은 줄바꿈 모의 대조도 통과했다.

현재 도입 검증과 관련 실행 근거는 `data/diagnostics/test-management-20261018/`에 보존한다. 실패를 수집한 최초 실행과 수정 후 결과를 구분한다. 실제 GitHub CI·Linux/PG 실행 수락은 별도로 남는다.
