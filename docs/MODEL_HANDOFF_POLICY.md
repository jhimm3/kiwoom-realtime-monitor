# 모델 단계 전환 정책

`Codex Mandatory Bidirectional Model Handoff Policy`의 **2026-10-13 제한적 Luna 허용 개정 요약**이다. **정본은 저장소 루트 [AGENTS.md](../AGENTS.md)** 이며 충돌 시 AGENTS.md의 현행 규칙을 따른다. 기존 Luna 사용 금지 지시는 철회하고 아래의 제한된 저위험 조건으로 대체한다. GPT-6.1 Sol을 기본으로 정확도·총비용·전환 비용·문맥 손실 위험을 함께 판단하며, 실질적인 상위 판단이 필요한 경우에 GPT-6 Astra를 사용한다. 정책 문서 수정만으로 현재 채팅의 실행 설정이 바뀌지는 않는다.

## 사용 가능한 모델과 추론 수준

- 기본: **GPT-6.1 Sol** (`gpt-6.1-sol`). 아래의 Sol은 기본적으로 이 모델을 뜻한다.
- 제한적 저위험: **GPT-6 Luna** (`gpt-6-luna`). 아래 네 조건과 허용 범위를 모두 만족할 때만 사용한다.
- 상위 판단: **GPT-6 Astra** (`gpt-6-astra`).
- 대체: **GPT-6 Sol** (`gpt-6-sol`). 해당 환경에서 GPT-6.1 Sol 미지원이 확인된 경우에만 허용한다. 현재 설정 확인 실패는 미지원의 증거가 아니다.
- 런타임에서 지원되는 실제 모델·추론 표기를 사용한다. `Low`, `Medium`, `High`, `XHigh`, `Max` 등을 전 모델 공통 지원 목록으로 가정하지 않는다. `Ultra` 같은 다른 표기도 해당 모델·환경 지원이 확인된 경우에만 검토한다.
- 과거 첨부의 Light는 Low, Extra High는 XHigh로 대응한다. API의 지원 목록과 Codex 환경의 지원 목록은 별도로 확인한다. 공식 [GPT-6.1 Sol 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol)의 API ID·추론 수준이 현재 채팅의 실제 설정을 뜻하지는 않는다.

## 작업 선택 기준과 사용자 선호

GPT-6.1 Sol을 우선 평가한다.

| 작업 | Sol의 판단 기준 |
| --- | --- |
| 일반 구현·문서화·테스트 | Medium; 범위가 명확한 단순 작업은 지원되는 Low도 검토 |
| 다중 모듈·비동기·DB 정합성·transaction·회귀 위험 구현 | High |
| 복잡한 원인 추적·경합·일관성 분석·고난도 구현 검증 | XHigh/Max를 실질적인 필요에 따라 검토 |

**현재 GPT-6.1 Sol High이고 다음 작업이 High 이하로 충분하면 High를 유지할 수 있다.** 불필요한 추론 수준 하향 요청이나 반복적인 변경을 강제하지 않는다. 적합성 재평가는 계속한다. High보다 높은 분석이 실질적으로 필요하면 지원되는 XHigh/Max를 검토한다.

### Luna의 제한적 허용 조건

다음 조건을 **모두** 만족할 때만 허용한다.

1. 작업 내용과 완료 기준이 명확하다.
2. 새로운 설계·알고리즘·데이터 흐름 판단이 필요 없다.
3. 잘못 수행해도 실행 동작이나 데이터 정합성에 영향을 주지 않는다.
4. 결과를 간단하고 확실하게 검증할 수 있다.

사용 범위는 **문서 서식 수정, 단순 정보 조회, 정해진 결과 정리** 등으로 제한한다. 정책·계약·설계의 의미 변경은 문서 작업이라는 이유만으로 저위험으로 간주하지 않는다. 코드 로직 변경·구조 변경·DB 수정·원인 분석·복잡한 테스트 수정에는 기본적으로 사용하지 않는다. 위험이나 조건 충족 여부가 불확실하면 Sol을 유지한다.

Luna부터 평가하도록 강제하지 않는다. 적격 작업이라도 모델 전환 비용이나 문맥 손실 위험이 더 크면 Sol을 유지한다. Luna 사용 중 예상하지 못한 복잡성·판단 문제가 발견되면 **중단하고 상향 handoff**한다. 기본 복귀 대상은 Sol이며 상위 구조 판단이 실질적으로 필요하면 Astra를 검토한다. 전환 확인 전 다음 작업을 진행하지 않고, 불안전한 원자적 수정만 가장 가까운 안전 경계까지 마무리한다. Luna의 추론 수준도 실제 지원 조합을 확인한다.

### Astra의 상위 판단 기준

Astra는 다음 문제에 상위 판단 능력이 실질적으로 필요한 경우에 사용한다.

- 시스템 아키텍처나 책임 경계가 미확정이며 Sol로 신뢰성 있게 결정하기 어려움.
- 여러 설계안의 trade-off가 중대하고 기존 정보만으로 결정하기 어려움.
- 데이터 보존·일관성·동시성 요구가 충돌해 새로운 구조적 판단이 필요함.
- Sol 분석으로 핵심 원인·설계 문제가 해소되지 않았고 추가 판단 능력이 필요함.

설계 작업이라는 이유만으로 Astra를 자동 선택하지 않는다. Astra가 필요한 문제에서 Sol의 모든 추론 수준을 순서대로 소진하도록 요구하지 않고, 추론 수준 상향만으로 상위 판단을 대체하지 않는다. Astra의 수준도 실제 지원 조합과 남은 판단 난도로 정한다.

## 현재 채팅의 실제 설정 확인

handoff를 작성하기 전, 직전 메시지나 사용 가능한 모델 목록으로 현재 설정을 추측하지 말고 **현재 채팅의 최신 실행 기록**을 확인한다. Windows Codex에서는 현재 채팅의 `CODEX_THREAD_ID`와 같은 이름으로 끝나는 JSONL 파일이 `%USERPROFILE%\.codex\sessions\<연도>\<월>\<일>\rollout-*-<thread-id>.jsonl` 아래에 있다. 최신 `turn_context` 레코드의 `payload.model`과 `payload.effort`가 그 턴에 실제 적용된 모델과 추론 수준이다. `session_meta`의 모델 제공자나 이전 `turn_context`를 현재 설정으로 쓰지 않는다.

현재 Codex 터미널의 PowerShell에서 다음을 실행한다. 마지막에 출력된 `model`, `effort`, `turn_id`를 확인하고, 긴 턴이라 레코드가 안 나오면 `-Tail 120` 값을 늘린다.

```powershell
$threadId = $env:CODEX_THREAD_ID
$sessionRoot = Join-Path $env:USERPROFILE '.codex\sessions'
$log = Get-ChildItem -LiteralPath $sessionRoot -Filter "*-$threadId.jsonl" -File -Recurse |
    Sort-Object LastWriteTime -Descending |
    Select-Object -First 1
if (-not $threadId -or -not $log) { throw '현재 채팅의 Codex 실행 기록을 찾지 못했습니다.' }
Get-Content -LiteralPath $log.FullName -Tail 120 | ForEach-Object {
    try { $_ | ConvertFrom-Json -ErrorAction Stop } catch { }
} | Where-Object { $_.type -eq 'turn_context' } |
    Select-Object -Last 1 |
    ForEach-Object { [pscustomobject]@{
        turn_id = $_.payload.turn_id
        model = $_.payload.model
        effort = $_.payload.effort
    } } | Format-List
```

이 셸 변수나 실행 기록에 접근할 수 없는 다른 환경에서는 Codex 화면의 현재 채팅 모델 선택기를 확인한다. 어느 쪽에서도 현재 턴 값을 확인하지 못하면 `확인 불가`라고 적고, 이전 턴·기본 설정·사용 가능한 모델 목록으로 대신 채우지 않는다. `effort` 필드가 없으면 추론 수준도 확인 불가로 둔다.

## 단계마다 새로 판정

새 사용자 메시지와 각 독립 구현/검토/테스트 단계의 시작, 핵심 판단 완료 시 GPT-6.1 Sol을 우선 평가한다. 이전 선택을 근거 없이 자동 승계하지 않되 현재 Sol High 유지 선호를 적용한다.

- Sol로 충분하면 유지하고 작업을 계속한다. 기본 모델 유지의 근거로 하위 모델이 부족하다는 설명을 요구하지 않는다.
- Astra가 설계와 핵심 판단을 완료하고 구현·검증만 남으면 GPT-6.1 Sol로 하향 handoff한다.
- Astra를 유지하려면 다음 단계에도 Sol로 해결하기 어려운 상위 판단이 남아 있는 구체적 근거가 필요하다. 중요도·코드 길이·파일 수·남은 작업량·이미 사용 중이라는 사실은 근거가 아니다.
- Astra의 판단 결과를 따르는 구현 중 사소한 설계 선택이 발생해도 자동 재상향하지 않는다. 새로 중대한 미확정 경계·trade-off·충돌 요구가 드러나 상위 판단이 필요한 경우에만 재검토한다.
- 원인·설계·인터페이스 결정, 핵심 알고리즘·transaction·concurrency 해결, TODO 완료, 테스트 실패 원인 확인, 범위 축소 뒤에도 같은 기준으로 재평가한다. Sol의 일이 단순해졌다는 이유만으로 Luna로 하향하지 않는다. 네 조건과 허용 범위, 전환 비용·문맥 손실 위험을 함께 확인한다.
- Luna 작업 중 저위험 조건을 벗어나는 복잡성·판단이 발견되면 안전하게 가능한 독립 작업을 계속한다는 일반 규칙보다 중단·상향 handoff를 우선한다.

**MODEL LEASE EXPIRATION CHECK**는 위 적합성 재평가를 뜻한다. Sol을 우선 평가하고, Astra의 상위 판단이 끝났으면 Sol 복귀를 우선 평가한다. Luna는 제한된 저위험 조건을 모두 만족할 때만 고려하며 적격 작업이라도 전환 비용·문맥 손실 위험이 크면 Sol을 유지한다. 현재 Sol High로 충분하면 불필요한 수준 변경 요청 없이 계속하며 실제 모델 변경만 handoff 사유다.

## 모델 변경 시 강제 handoff

다음 단계에서 **모델이 바뀌어야 하면** 결과를 표시하고 즉시 멈춘다. 상향·하향 모두 같다. 사용자에게 매 단계에서 모델을 고르게 묻는 선택형 질문으로 대체하지 않는다. handoff 사유가 있으면 권고만 한 채 현재 모델로 계속하지 않는다.

```text
[HANDOFF REQUIRED — ESCALATE]
Current: <현재 모델과 추론 수준; 알 수 없으면 확인 불가라고 명시>
Switch to: <권고 모델과 추론 수준>
Reason: <현재 단계에 남은 구체적 위험 또는 설계 판단>
Completed: <완료된 분석·결정>
Remaining: <handoff 뒤의 작업>
```

하향 handoff도 같은 강도로 적용한다.

```text
[HANDOFF REQUIRED — DOWNGRADE]
Current: <현재 모델과 추론 수준>
Switch to: <낮은 비용으로 충분한 모델과 추론 수준>
Reason: <복잡한 단계가 끝났고 다음 작업이 단순해진 근거>
Completed: <완료된 핵심 단계>
Remaining: <다음 모델이 수행할 작업>
```

handoff 뒤에는 모델 전환이 확인될 때까지 다음 파일 수정, 테스트, 문서 작업, TODO 수행을 시작하지 않는다. 다만 이미 시작한 수정이 안전하지 않은 중간 상태라면 그 원자적 수정 단위만 안전한 상태로 마무리한다. 런타임에서 모델을 직접 전환할 수 없으면 전환했다고 주장하지 않고 정확한 다음 모델·추론 수준을 안내한다. 하향도 선택형 권고가 아니라 단계 경계다.

같은 모델 안에서 추론 수준을 바꾸는 것은 모델 handoff가 아니다. 해당 모델·환경에서 지원되는 수준과 High 유지 선호를 적용하며 그 조절만으로 작업을 멈추거나 사용자에게 전환을 요구하지 않는다. 실제 조절 권한이 없으면 설정을 바꿨다고 주장하지 않는다. Astra가 필요한 판단을 추론 수준 상향만으로 대체하지 않는다.

## 재평가 결과

- 테스트·lint·명확한 acceptance 확인은 Sol로 수행한다. 고난도 정합성 분석이 남으면 Sol XHigh/Max를 검토하며 실질적인 상위 판단이 필요하면 Astra를 선택한다.
- Astra의 설계·핵심 판단 완료 뒤 구현·검증은 Sol로 하향한다. 구현 도중 사소한 설계 선택 때문에 재상향하지 않는다.
- Sol에서 transaction·동시성 핵심 문제가 해결된 뒤에도 새로운 단계의 적합성을 다시 평가한다. 반복 적용·문서화라는 작업 이름만으로 Luna를 선택하지 않으며 제한적 허용 조건과 전환 비용·문맥 손실을 확인한다. 현재 High 유지 선호를 적용한다.
- 같은 모델 내 추론 수준 조절은 handoff 없이 진행하고 지원되지 않는 조합이나 실제로 수행하지 않은 변경을 주장하지 않는다.
- handoff 사유는 단계별로 판단한다. 이전에 낸 권고를 근거로 불필요한 추가 모델 전환을 강제하지 않는다.

이 정책은 위험 경계의 검증 의무, 데이터 보존 규칙, 테스트 환경 제한, NAS 배포 절차를 완화하지 않는다. 모델 전환은 그 작업 계약을 대체하지 않는다.
