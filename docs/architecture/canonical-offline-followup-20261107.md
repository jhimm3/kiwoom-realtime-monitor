## N07 분봉·시장 조회와 매매 TR의 연결 선택

개인 서버 모드에서 **API 설정 → NAS 실전계좌·API 키 관리**(또는 모의계좌 관리) → **분봉·시장 조회 TR 연결 불러오기**를 선택한다. 화면에 뜨는 이미 확인한 계좌 중 현재 매매 기준 계좌를 지정한 다음 연결 방식을 적용한다.

| 선택 | 분봉·시장조회 | 계좌·주문 |
|---|---|---|
| 통합 | 매매 기준 계좌의 기존 REST 연결과 요청 한도 공유 | 기존 매매 계좌 설정과 원주문 owner 유지 |
| 분리 | 선택한 데이터 계좌의 기존 REST 연결과 요청 한도 사용 | 잔고·미체결·체결·신규 주문·정정·취소는 각 기존 매매 계좌에 남음 |

초기 미설정은 기존 흐름이다. 같은 검증 계좌를 다른 이름으로 등록해도 별도 한도를 만들지 않는다. 분리에서 시장조회 연결을 잃으면 시장조회만 그 실패를 드러내며 계좌 조회·주문을 데이터 계좌에 넘기지 않는다. 설정 저장/적용 판본·연결 대기·복구 필요를 보여준다. 저장 응답이 유실되면 현재 값을 다시 불러온다. 원주문 관리에서 현재 조건을 다시 판단하는 기존 계약을 유지한다. 실시간 0B는 기존 공통 수신 연결을 별도 표시한다. 이 설정은 실전 자동매매 시작, 주문 계좌 선택, 키 교체나 권한 인계 기능을 대체하지 않는다. 계좌 프로필 관리가 없는 기존 단일 키 로컬 모드에서는 사용할 수 없다.

[키움 공식 호출 한도](https://openapi.kiwoom.com/intro)상 국내주식 조회·주문은 계좌/토큰별 각각 초당 5회이며 모의는 별도 제한이다. 이 변경은 해당 한도나 앱의 기존 큐를 늘리지 않는다. 분리의 이점은 시장 조회와 매매 계좌 조회가 별도 연결 예산을 쓰는 데 있다. 실제 장중 처리량 또는 지연 개선은 측정하지 않았다. [HTTPS/API 계약](../../API_CONTRACT.md) · [저장 계약](../../DB_SCHEMA.md).

## N03 고정 관측 자료의 장후 보관

`python -m kiwoom_monitor.observation_archive`의 `prepare` → `send` → `restore`를 사용한다. `prepare --kind`에는 ranking, minute_bar, daily_bar, top20_membership 중 하나와 시각 범위를 명시한다. 기존 고정 공개 자료의 원본과 manifest를 그대로 보관하며, 부분·미확인·원천 순번·판본을 재해석하지 않는다. 보관할 배치의 수락 영수증은 native 저장을 마친 뒤 반환된다. 요청 응답을 잃어도 보류 배치와 원본은 유지하고 동일 ID의 첫 영수증을 확인한 후 재사용한다. 원본을 삭제하거나 장중 저장을 원격으로 보내지 않는다.

수신기에서 기존 일반/연구 권한과 별개인 `MONITOR_SERVER_OBSERVATION_ARCHIVE_GRANTS_JSON`을 명시한 경우에만 활성화한다. stream별 bearer와 내용 hash를 대조한다. 배치의 전체 UTF-8 JSON 상한은 32 MiB이고 초과 시 저장하지 않는다. 수동 보관은 자료 종류와 범위를 나눌 수 있다. 운영 grant·NAS 배포, 자료 보관 기간, 주문·계좌 자료 전송과 권한 인계는 별도다. [4종 수동 보관·원행 검증](../../tmp/canonical-offline-20261107/archive/REPORT.md).

### 프로그램매매와 시장 관측 장후 자동 보관

실행 PC의 파일 SQLite에서 당일 KST 20:05 이후 TOP20 장후 보완이 성공하면 대기 중인 `0W` 저장을 마치고 `program_flow`를 읽는다. 해당 거래일의 스냅샷은 `0W`, `ka90008` 보완본 및 기존 형식의 스냅샷을 키·저장 시각·payload와 함께 보관한다. 거래일은 스냅샷 키에서 가져오고 payload에 기록된 출처·값·결측을 유지한다. 전날 차트 보완으로 전날 프로그램매매를 확정하거나 새 전송을 만들지 않는다.

`<로컬 DB 파일명>.program-archive/<거래일>/`에 같은 읽기 시점의 자료를 32 MiB 이내 배치로 나누어 한 번에 게시한다. 단일 스냅샷이 상한을 넘으면 로컬 원본을 유지하고 동결 실패를 남긴다. 전송은 별도 작업이 맡는다. 첫 전송에서 대상 URL을 고정하고, NAS 영수증을 확인하면 `.ack.json`을 저장한다. 응답을 잃거나 NAS에 닿지 않으면 고정 파일로 재시도하고, PC를 재시작해도 보류 파일을 이어받는다. NAS는 같은 BLOB 보관 테이블에서 첫 내구 영수증을 재사용한다. `restore`는 보관된 프로그램매매 파일을 복원하며 이 종류의 자료는 연구용 관측 export와 분리한다.

순위·분봉·일봉·TOP20 편입은 같은 장후 완료 신호에서 `observations/<거래일>/`에 동결한다. 거래일 안에 발생하고 완료 시점까지 저장된 관측 판본을 SQLite의 한 읽기 스냅샷에서 가져온다. 오전에 전일 보완을 끝냈으면 그때 확보한 전일 봉도 포함한다. 배치는 종류와 원래 가용일별로 나누며 가용 시각·출처·판본·불완전 표시를 보존한다. 30초 순위 원행은 기존 TOP20 편입 스냅샷에 담긴다. 야간 화면 전용 순위나 사후에 새로 보완한 과거 거래일의 별도 전송은 이 자동 배치 범위 밖이다. 보관 설정은 기존 프로그램매매의 선택 설정을 공유하며 PC에 원본 관측 이력 저장이 켜져 있어야 한다.

기본은 비활성이다. 전환 때 실행 PC에 `MONITOR_SERVER_PROGRAM_ARCHIVE_TARGET_FILE`(기존 연결 JSON 형식의 전용 NAS URL·보관 토큰 파일)과 `MONITOR_SERVER_PROGRAM_ARCHIVE_SOURCE_STREAM`(NAS 보관 grant의 owner)을 명시한다. NAS 보관 수신기는 기존 `MONITOR_SERVER_OBSERVATION_ARCHIVE_GRANTS_JSON`을 사용한다. 이번 확인은 격리 로컬 DB와 HTTP에 한정한다. 실제 운영 설정과 보관 기간은 별도다.

### 뉴스·공시 본문과 전처리 결과의 장후 보관

실행 PC에 기존 보관 목적지와 `MONITOR_SERVER_NEWS_BODY_ARCHIVE_ENABLED=1`을 함께 지정하면 같은 장후 완료 신호에서 뉴스 보관을 예약한다. 기본값은 꺼짐이다. 기존 과거 일괄수집 DB는 이 보관 대상에서 제외한다. 완료 시각까지 저장된 운영 기사·본문 판본, DART·KIND HTML, 해당 판본의 저장된 RULE·사건·AI 결과와 근거를 기존 저장 전용 API에 고정 배치로 전달한다. 작업이 진행 중인 기사와 분류를 마치지 않은 공통 기사 본문은 PC에 두고 이후 장후에 다시 확인한다.

수신기가 배치를 내구 저장한 뒤 해당 배치를 다시 읽어 내용 지문을 대조한다. PC SQLite에서 원문을 정리하고 같은 트랜잭션으로 정확한 보관 위치를 기록한다. 기사 ID·주소·본문 지문, 목록 표시와 분류에 필요한 값, 원공시·사건·정정 연결 및 공급처 진행 위치는 PC에 둔다. 전송이나 확인 조회가 실패하면 PC 원문과 배치가 재시도에 사용된다. 재시작은 같은 배치의 최초 영수증을 재사용한다.

기존 뉴스 목록과 페이지 이동은 PC의 기사 기록을 계속 사용한다. 클릭한 기사 본문이 PC에서 정리됐으면 기존 뉴스 이력 API가 해당 판본만 수신기에서 읽어 같은 화면에 표시한다. NAS에 닿지 않을 때도 목록·사건 연결은 PC에서 유지하며, 보관 본문 요청은 일시적으로 읽을 수 없다고 응답한다. 정리된 SQLite 페이지는 이후 저장에 재사용한다. DB 파일의 즉시 축소와 원문 보관 뒤 별도로 실행한 재분석 결과의 전송은 별도다.

### 실행 PC의 이력과 연구 재현 자료 장후 보관

`MONITOR_SERVER_PC_HISTORY_ARCHIVE_ENABLED=1`을 기존 보관 대상·스트림과 함께 지정하면 같은 장후 완료 신호가 실행 PC 저장소의 이력과 뉴스 보관을 예약한다. 기본값은 꺼짐이다. 확장 모드는 기존 시장 5종을 포함하는 배치를 사용하고, 기존 5종 형식으로 작성된 보류 파일은 기존 전달 경로를 이어간다. 수신기는 배치 원본과 같은 트랜잭션으로 출처·종목·시간 조회 위치를 저장한다. 실행 PC는 수신기에서 그 배치의 기록을 다시 읽어 키·건수·내용을 대조한 뒤 영수증을 남긴다. PC에서 나중에 값이 바뀌었거나 오래된 날짜의 행이 새로 생기면 다음 장후에 새 판본을 보내고, 조회용 기록은 최신 수락 판본을 사용한다.

대상은 순위·봉·수급·지수·VI·테마·시장 입력, 저장된 나스닥 선물과 WTI 등 해외시세, 장전 시황, 뉴스 판정 이력, Shadow 판단, 종료된 주문·체결의 이력, 매매일지와 등록된 완료 연구 DB의 증거다. 공급처 수집 설정은 기존 설정을 사용한다. 미체결 주문, 실행 복구 상태, 계좌 권한은 장후 보관 대상에서 제외한다. 대상·PC 유지 항목·별도 소유·미분류·수신 확인·불일치 건수는 `<PC DB>.program-archive/history/<완료 시각>.report.json`에 구분한다. 미등록 DB·파일, 미분류 저장 항목 또는 수신·대조 미완료가 있으면 전체 검증 완료로 표시하지 않는다.

선택 정리일을 `MONITOR_SERVER_PC_HISTORY_COMPACT_BEFORE=YYYY-MM-DD`로 명시하면 그보다 오래되고 기존 최근 차트 조회에 필요한 기간 밖인 시장 행을 정리할 수 있다. 일봉은 과거 일봉 수집 경로가 읽는 종목·시장별 5,000행을 보유한다. PC에 같은 키의 최신 수정이 있으면 전송한 판본으로 지우지 않는다. 순위·TOP20 편입·프로그램매매의 화면용 저장값과 기존 분봉·일봉 조회는 NAS의 이력과 PC 값을 같은 화면 계약으로 합친다. 로컬 연구용 관측 판본과 원본 주문 원장은 유지한다. 오래된 SQLite 파일을 즉시 축소하는 작업은 별도다.

앱에서 시작한 연구 작업이 완료 결과를 저장하면 `data/research/archive-owned`에 원본 위치와 SHA-256을 기록한다. 앱이 만든 캠페인 동결 입력, 뉴스 검토 결과·분할 계획·개발 입력도 같은 방식으로 기록한다. 기존 캠페인은 앱의 선택 기록과 캠페인 작업에 연결된 완료 실행을 대조한다. 저장 위치를 바꿔도 기록된 실행과 해당 실행의 증거만 보관한다. 한 DB에 섞여 있는 별도 개발 실험, 외부에서 가져온 연구 입력 원본, 수동 연구 폴더와 개발 검증 자료는 자동으로 등록되지 않는다. 별도 PC 시장 DB는 실행 앱의 데이터 폴더에 있는 `monitor.sqlite3`의 허용 표를 보관한다. 실행 중 연구 행, 사용자 설정·인증 정보, 임시 복제본과 전송 보류 경로는 보관 목록에서 제외한다.

파일은 전체 SHA-256을 먼저 대조한 뒤 제한된 크기로 나누어 전송한다. 수신 후 각 조각이 일치해야 파일을 목록에 게시하고, 동결 입력 묶음은 하위 파일이 확인된 뒤 상위 manifest를 게시한다. `python -m kiwoom_monitor.observation_archive restore-research-file --target-connection … --source-stream … --sha256 … --output …`로 파일 한 건을 복원하고, 같은 옵션의 `restore-research-input`은 동결 입력의 manifest SHA-256으로 원래 디렉터리 구조를 복원한다. 연구 원본의 자동 삭제는 별도다. PC 데이터 표는 보관 조회에서 복구할 수 있으며 설정을 포함한 기존 앱 DB 전체를 교체하는 복구와 구분한다.

2026-11-11 로컬 조사에서 `data/research`의 읽힌 용량은 17.26 GiB였다. 별도 개발 결과까지 찾은 넓은 조사에서는 연구 DB 5개·18.72 GiB와 원본·근거의 해시 중복을 뺀 4.63 GiB를 확인했다. 이 수치는 자동 보관량과 구분한다. 현재 개발 체크아웃에는 앱이 작성한 연구 소유 기록과 선택된 기존 캠페인이 없으며, 앱의 별도 시장 DB는 375.43 MiB다. 바탕화면의 과거자료 보완 폴더 1.37 GiB와 미모사 자료는 조사 목록에만 남겼다. 과거 수집 도구의 일부 기본 경로는 바탕화면을 참조한다.

과거 개발 연구에서 직접 저장된 동결 입력이 없는 51건은 기존 원본과 분할 정책으로 입력을 재생성해 저장된 자료 ID·판본 SHA-256·건수 일치를 확인했다. 이 근거와 분류 목록은 로컬 조사 기록으로만 남겼다. 읽기 오류가 난 `historical-strategy-input` 6곳, `historical-reconstruction` 4곳, `historical-development-inputs` 3곳의 용량은 미확인이다. 대용량 과거 뉴스 보관본의 기존 전송 보류를 유지한다.

격리 로컬 수신기에서 NAS 연결 실패 때 PC 사본 유지, 나스닥 선물·WTI와 일지·완료 주문 전달, 분봉·일봉·순위·TOP20·프로그램매매 정리 이후 기존 조회, 전일 수정의 다음 전송을 검증했다. 앱이 완료한 연구 근거와 동결 입력을 전송·복원하고, 같은 DB의 미등록 개발 실행 및 외부 DB가 들어가지 않는지 대조했다. 운영 NAS와 전체 실자료 전송은 별도 검증 범위다.

후속 조회에서 일지 `market_data_observation_meta` 63,657행의 보관 연결 누락을 확인했다. 분봉 41,238행, 일봉 18,542행, 진입 맥락 3,877행이며 로컬 테이블·인덱스 점유는 15,253,504바이트다. 이 기록은 봉·체결 본체와 별도로 당시 가용 시각·출처·완결 상태를 남긴다. 중앙 뉴스의 공급처 수신 근거와 실제 AI 입력·출력 원본도 보관 목록 대조에서 후속으로 분리했다. 해당 중앙 DB가 이 PC에 없어 두 자료의 저장량은 미확인이다. 이 조사는 보관 연결 추가 구현과 구분한다.

### 2026-11-11 GitHub 야간 조회 화면 실패

기능 보존 회귀 `42922943446`은 `2e70be4`에서 조회 전용 화면의 TOP20 결과 슬롯 안에 진입하다 Python/PySide가 비정상 종료했다. Windows 분할 2의 해당 모듈 실패가 집계·필수 판정으로 전파됐으며 필수·확장 PostgreSQL은 통과했다. 같은 커밋의 앞선 push 회귀 `42777908643`은 통과했다. [실패 실행](https://github.com/jhimm3/kiwoom-realtime-monitor/actions/runs/42922943446)

로컬 원래 검사 17건에서는 native abort가 재현되지 않았다. 결과를 통지한 뒤 스레드 반환을 보류하는 제어 검사에서는 GUI callback이 native 종료 전에 실행되는 경계를 재현했다. TOP20 worker가 결과와 오류를 보유하고 MainWindow의 원래 QObject 종료 슬롯이 실제 thread 종료를 확인한 뒤 callback을 한 번 실행하고 정리하도록 바꿨다. 실패 메시지·요청 재시작·중복 억제·늦은 결과의 종료 처리와 실제 가격 저장 ACK를 함께 검증한다. 이 재현과 변경을 native abort의 내부 원인 확정으로 확대하지 않는다.

첫 푸시 `a7c0718`의 실행 `42953616492`에서 이전 실패 분할 2는 통과했다. 분할 0은 기존 일봉 행의 시장 필드가 빠진 상태에서 보관 이력을 합칠 때 실패했다. 요청 시장을 기존 행의 병합 키에 사용하고 원래 행은 그대로 반환한다. 분할 3·6은 뉴스 보관 믹스인의 중첩 상속 때문에 기존 저장소 감사가 중단됐다. 보관 구현을 기존 SQLite 저장소에 직접 조립하고 새 호출 1곳·전달 8곳·메서드 서명 15개만 증분 검토 원장에 반영했다. 기존 일봉과 감사 검사 기준은 유지했다. ## 미정·외부·실행 제외

- 매매 기준/위험 한도/자금과 우선순위/자료·정책 채택은 [12.11](app-target-20261023.md#1211-미정-매매운용-정책)에 남긴다. 다른 복원 우선순위·백업 목표·미정 운영값도 임의로 채우지 않는다. 날짜·입력·판본이 명시된 기존 비교는 연구할 수 있다.
- 실제 장중 입력·DD 원주가/비용·MICRO 호가/VI/체결 순서·키움 상세 조회 및 계좌 범위는 확보된 자료와 실제 권한이 있어야 검증한다. 재구성 봉을 연구에 사용할 수 있으며 미래 판단 정보·없는 봉내 순서·가짜 체결을 추가하지 않는다.
- [키움 국내주식 호출 안내](https://openapi.kiwoom.com/intro)(2026-11-07 확인)는 계좌/토큰별 조회·주문 각 초당 5회와 별도 모의 제한을 제시한다. 이 작업은 현재 제한을 늘리거나 키를 순환하지 않는다. 같은 계좌는 같은 한도를 공유하고, 계좌 분리의 효과는 해당 환경의 실제 수락과 격리 호출 경로를 구분한다.
- 실제 주문·외부 주문 전송, 운영 NAS/DB/설정/서비스 변경, 실제 자료·권한 이전·T0·push·새 외부 CI는 범위 밖이다. 운영 없는 검증에는 가짜 브로커·합성 자료·이미 확보한 적격 사본·격리 DB·기존 빌드 도구만 사용한다.

## 최종 로컬 수락

N01~07에서 현재 환경으로 가능한 개발·검증 범위를 마쳤다. [정본 11.294](app-target-20261023.md#canonical-offline-followup)에 각 종료 판정과 근거를 연결했다. 통합 소스에서 Windows 396·격리 PostgreSQL 3, 실제 연구 자식 witness 1과 보완 역할 5를 확인했다. Windows 설치 후보는 컴파일했고, 같은 빌드의 서버·연구 실행물은 격리 기동했다. 설치 프로그램 자체는 실행하지 않았다. 기존 S12 개발5/5·대표11/11과 새 결과를 합산하지 않는다.

AR 실제 전환의 6조건·17행동, 선택 OS/설치 환경, 장후 운영 grant·스케줄, 연구 자료·매매 정책은 위 재개 조건에 남긴다. 신규 제품 의존성이나 실제 키움 처리량 성능 수치는 없다.
