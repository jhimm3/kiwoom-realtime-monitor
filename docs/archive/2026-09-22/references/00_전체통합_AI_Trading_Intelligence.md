## 0. Codex 작업 지시

**첫 작업은 읽기 중심 현황 조사와 작은 연결 검증이다. 이 문서 전체를 한 번에 구현하거나 실거래를 켜라는 지시가 아니다.**

1. 저장소 지침, 진행 중인 변경, 기존 엔진·시세 수집·뉴스·DB·주문 경로·테스트를 확인한다. 미커밋 작업을 보존한다.
2. ①과 현재 구현의 일치 여부를 확인한다. 재사용할 계약·함수·테이블을 짧게 매핑한다.
3. Top20의 현재 수집물이 진짜 1초 OHLCV인지, 1초 가격 스냅샷인지, 누적 거래대금 차분인지부터 확인한다.
4. 신규 구현은 먼저 **읽기 전용 판단 기록 → 작은 구간 재생 → 비용 포함 결과 검증**까지 진행한다. 학습 모델이 없어도 규칙 기준선을 기록할 수 있어야 한다.
5. 신규 실거래·미수·자동 주문 권한은 기본 OFF다. 기존 수동 주문 기능을 멋대로 바꾸지 않는다.
6. 막힌 외부 연동은 `미지원/미확인`으로 표시하고, 독립적으로 가능한 계약·단위 테스트는 진행한다. 확인 가능한 내용을 사용자에게 반복 질문하며 중단하지 않는다.

최초 산출물은 기존 감사 문서가 있으면 그것을 보완한 `INTEGRATION_AUDIT.md` 하나와, 선정된 최소 범위의 실제 변경·테스트다. 문서용 빈 클래스·테이블·서비스 수십 개를 먼저 만들지 않는다.

## 1. 최종 제품 정의

> **시장과 뉴스를 이해하고, 현재 매매 가능한 기회를 좁힌 뒤, 각 시점의 행동별 비용 차감 기대값과 위험을 비교하여 진입·보유·추가매수·축소·청산·재진입을 제안하고, 검증을 통과한 정책만 자동 실행하는 시스템.**

사람의 경험칙은 연구의 출발점이다. 목표는 경험칙을 무조건 복제하는 것도, LLM이 그럴듯한 설명을 하면 곧바로 주문하는 것도 아니다. **경험을 검증 가능한 가설로 만들고, 실제 성과를 확인하여 유지·수정·폐기한다.**

초기 중심 전략은 사용자가 이해하는 **주도주 돌파**다. 눌림, 스캘핑, 종가베팅, 상한가 접근 매매, 연관종목 매매를 처음부터 모두 구현하지 않는다. 나중에 별도 검증된 정책을 추가할 수 있게 하되, 현재 데이터·지식 밖의 전략을 완성된 것처럼 채우지 않는다.

화면은 단순하게 유지한다.

> 시장 환경 / 관심 후보 / 진입 조건 / 현재 행동 / 무효화 조건 / 근거·데이터 시각

내부 계산이 많아도 유효성이 확인되지 않은 변수는 계속 늘리지 않는다. **내부가 복잡할수록 좋은 모델이라는 가정은 금지**한다.

‘몇 년치 학습’, ‘확률이 높다’, ‘안전한 종목’은 각각 데이터 커버리지, 정의된 사건 확률, 관측된 유동성·위험 조건으로 풀어쓴다. 모호한 표현을 그대로 주문 규칙으로 사용하지 않는다.

## 3. ①·②·③의 책임 경계

| 영역 | 담당 | 입력 | 출력 | 직접 하지 않는 일 |
|---|---|---|---|---|
| ① Market Intelligence | 뉴스·사건·테마·종목 기억·시장 맥락 | 기존 뉴스·일봉·시장 요약 | Market State, Theme, Stock Memory, 근거 있는 가설 | 초단위 주문, 포지션 변경, 손절 실행 |
| ② Trading·타점 Intelligence | 현재 상황과 매매 기회의 해석 | ①의 시점별 결과, Top20, 시세 특징, 현재 포지션 | 시나리오, 후보 상태, Entry/Add/Hold/Reduce/Exit/Re-entry 후보 | 검증 안 된 확률 생성, 최종 주문 허가 |
| ③ Research·EV·Risk·Execution | 연구·성과·행동가치·비중·위험·주문 | 과거/실시간 상태, ②의 행동 후보, 계좌·주문 정보 | 검증된 모델, 행동별 EV, 목표 노출, 허용 주문, 체결 원장 | 뉴스 수집 복제, LLM 설명만으로 위험 제한 해제 |

`Expected Value(EV)`는 기대값, `Risk`는 위험관리, `Execution`은 주문·체결 실행을 의미한다. 아래 구분은 책임 경계이지 모두 별도 서버로 만들라는 뜻이 아니다.

```text
기존 수집·NAS 원본 저장 ───────────────┐
          │                          │
          ▼                          ▼
① Market Intelligence          시세 특징 계산(한 곳)
          │                          │
          └─────────┬────────────────┘
                    ▼
           ② Trading Intelligence
       시나리오 / 현재 상태 / 행동 후보
                    ▼
             ③ EV / Position Policy
          행동 비교 / 목표 노출 제안
                    ▼
                 ③ Risk
       자본·유동성·데이터·권한 한도 검사
                    ▼
               ③ Execution
       모의 또는 승인된 주문 / 실제 체결
                    ▼
          포지션 원장 / 결과 / 복기
                    │
                    ▼
             ③ Research/Learning
       별도 검증 → 후보 버전 → 승인된 승격
```

LLM이 매초 응답해야 주문·손절이 가능한 구조는 만들지 않는다. 로컬 LLM은 ①의 의미 해석과 근거 설명을 담당한다. ②·③의 장중 의사결정은 고정된 데이터 계약과 코드·검증된 모델로 진행한다. 뉴스 분석 지연은 표시하며, 중요한 맥락이 누락되면 그 맥락을 요구하는 신규 위험 확대를 제한한다.

## 4. 서로 다른 종목 집합을 혼동하지 않는다

### 4.1 과거 뉴스 수집 집합

①의 기본값은 **KOSPI·KOSDAQ 통합 일별 거래대금 Top40**, Top30 변경 가능이다. 이는 과거 뉴스를 효율적으로 확보하기 위한 **사후 수집 집합**이다. 그날 확정 거래대금 순위를 그날 아침부터 알고 있었다고 간주하지 않는다.

### 4.2 실시간 관찰 집합

현재 대화의 전제는 기존 **실시간 조회 Top20의 1초 단위 자료**다. 실제 API·수집 로직·갱신주기는 코드에서 확인한다. Top20은 조회순위이지 거래대금 상위20이 아니다. 과거 Top40은 과거 Top20의 복원값이 아니다.

초기에는 Top20 이외 순위의 세밀한 상승 경로를 수집·복원하는 기능을 강제하지 않는다. 다만 이미 수신한 Top20 스냅샷과 편입·이탈 시각은 작은 비용의 기록으로 남겨 연구 집합을 재현한다.

### 4.3 정밀 관찰·보유 집합

현재 후보 중 필요한 종목만 정밀 계산한다. 주도주 후보가 없으면 없는 상태를 정상 출력한다. **보유·미체결·청산 진행 종목은 Top20에서 빠져도 추적을 중단하지 않는다.** 수집 중단으로 결과가 사라진 사례는 손익 0이나 성공으로 처리하지 않는다.

Top20 밖의 뉴스 급등 종목을 자동 추가하는 기능은 향후 명시적 옵션이다. 현재 계약·수집 범위를 조용히 늘리지 않는다. 비주도주 연구를 할 때만 그 연구에 맞는 별도 비교 집합·수집 예산을 정한다.

## 5. 거래대금·시장·시간대의 해석

### 5.1 거래대금의 역할은 분리한다

- **진입 적격성:** 지금 새 위험을 추가할 만큼 거래가 활발한가?
- **상대 강도:** 그 종목의 과거 동일 시간대·시총·유통규모 대비 얼마나 특이한가?
- **가격 반응:** 거래 증가와 함께 돌파·지지·실패 중 무엇이 관측되는가?
- **실행 수용력:** 내 증액분과 전체 보유분을 합리적인 시간·가격 범위에서 처리할 수 있는가?

거래대금은 사고판 금액이며 그 자체가 순자금 유입액은 아니다. 거래대금 감소만으로 매도, 상승·거래대금 증가만으로 매수를 결정하지 않는다. 대형주라는 이유로 자동 제외하지도 않는다.

40억·50억·100억·200억은 이 대화에서 나온 **경험적 연구 후보값**이다. 거래대금 임계값 자체를 연구하면서 그 아래 자료를 먼저 모두 버리면 임계값을 검증할 수 없다. Top20 안의 저거래대금·실패 후보도 기존 경량 자료 범위에서는 남긴다.

### 5.2 시장 상태는 강세·보통·약세 한 축이 아니다

①의 `participation`, `concentration`, `market_assessment`를 재사용하고, 필요한 수치 특징을 공용 경로에서 만든다.

방향, 변동성, 시장 폭, 대형주 편중, 시장 거래대금, 테마 집중·분산, 종목 상대강도, 주도주 후보 유무, 시간대를 구분한다. 특정 두 종목의 지수 비중을 ‘항상 50%’처럼 하드코딩하지 않는다. 지수 기여 자료가 없으면 추정 한계를 표시한다.

`지수 강세 + 중소형주 약세 + 매매할 돌파 후보 없음`과 `지수 약세 + 특정 테마 활발`을 모두 표현할 수 있어야 한다. 어느 쪽의 기대값이 높은지는 데이터로 검증한다.

### 5.3 시간은 맥락이지 절대 명령이 아니다

09:20 전후·10:30 전후는 정책을 비교할 연구 축이다. 09:05에도 전일 연속성·유효한 뉴스·시초 확인·위험 한도가 충족되면 조기 진입 후보가 가능하다. 오후에도 검증된 조건이면 재평가한다. 반대로 오전이라는 이유로 거래를 강제하지 않는다.

개장 초 매도의 주체가 전일 종가베팅 투자자였는지는 시세만으로 확인할 수 없다. ‘초기 매도 압력’, ‘갭 이후 가격 유지’처럼 관측 가능한 값으로 기록한다. KRX·NXT 세션과 실제 거래일 달력은 검증된 공급자 정의를 사용한다.

## 6. 목표 노출 기반 분할 운용

기본 행동 집합은 `WAIT / ENTER / HOLD / ADD / REDUCE / EXIT / REENTER`다. 동일 종목에서 일부 매도 후 다시 매수하는 것이 정상이며, 단순한 매수→매도 1회만 가정하지 않는다.

**숫자 예시는 설명용이며 운용 권장 비중이 아니다.** 기준 자본이 변하지 않는 예에서 목표 노출이 `0 → 0.30 → 0.60 → 0.90 → 0.40 → 0.70 → 1.00 → 0`이라면 각 차이만 매매하려는 의도를 만든다. `90%에서 50% 매도`가 보유량 절반인지 계좌 기준 50%포인트인지 모호하므로 실제 계약은 수량·원화·노출 배수를 명시한다.

실제 노출은 `현재 평가금액 / 정해진 계좌 기준 순자산`으로 정의한다. 목표 노출 계산과 위험 한도에는 실제 잔고뿐 아니라 **미체결 주문·수수료·자금 예약**이 포함된다. 같은 목표 신호가 여러 번 와도 주문이 중복 증가하지 않아야 한다.

수익 중 추가매수도 새 위험이다. 최초 원금 기준 손익, 현재 순자산에서의 예상 감소, 최고 순자산 대비 반납, 급변 시 스트레스 손실을 따로 본다. **손절선을 올려 계산상 원금 손실이 작다고 현재 자산의 위험까지 0인 것은 아니다.**

5배 노출은 연구의 선택지일 수 있지만 초기 구현·모의 검증·실거래의 기본값이 아니다. 사용자가 실제 계좌에서 별도로 승인하지 않은 미수·신용 기능을 켜지 않는다.

## 7. 손절과 예외의 명세

‘순간 이탈을 버티는 것’은 결과를 본 뒤의 설명이 아니라 **이탈 전에 정의되고 검증되는 조건부 관찰 정책**이어야 한다.

관찰 경계(`soft boundary`)는 제한된 이탈 깊이·지속시간·관측 신선도·회복 조건으로 평가한다. 보호 한도(`hard risk limit`)는 모델이 해제할 수 없다. Hard 조건이 발생하면 신규 위험 확대를 차단하고 기존 보호 절차로 청산을 시도한다. **명령 발행과 청산 체결 완료는 다르다.** 키움 공식 안내도 시장가 주문의 실제 체결가격이 직전 가격과 다를 수 있음을 설명한다. [G5]

1초 자료로 0.2초 이탈의 원인·지속시간을 안다고 주장하지 않는다. 당장 지원 가능한 정책과 추후 더 좋은 데이터가 있어야 연구할 정책을 분리한다.

## 8. 계산·학습·실시간 적용을 구분한다

| 작업 | 기본 처리 | 모델 가중치 변경 여부 |
|---|---|---|
| 뉴스·시세 저장 | 신규 자료·정정분 증분 반영 | 아님 |
| RAG 기억 갱신 | 시점 필터와 인덱스 갱신 | 아님 |
| 특징·성과 통계 | 결과가 완결된 자료만 갱신 | 보통 아님 |
| 실시간 확률 재계산 | 고정 모델에 현재 입력 전달 | 아님 |
| 후보 ML 모델 훈련 | 지원 알고리즘의 증분 학습 또는 배치 학습 | 맞음 |
| LLM 파인튜닝 | 목적·검증자료가 준비된 별도 실험 | 맞음 |
| 운영 모델 교체 | 기존 모델과 비교·승격·롤백 | 배포 변경 |

모든 알고리즘이 새 하루 데이터만으로 학습할 수 있는 것은 아니다. scikit-learn도 증분 학습 지원 여부를 별도 능력으로 다룬다. [G1] 따라서 ‘매일 저장하니 재학습은 끝났다’, ‘모든 모델은 반드시 3개월마다 재학습한다’ 둘 다 요구사항으로 고정하지 않는다.

매일 데이터·성과 점검과 **선택적인 후보 학습**은 자동화할 수 있다. 운영 모델은 평가를 통과한 버전만 사용한다. 오늘 만들어진 후보가 곧바로 내일의 실거래 모델이 되어야 하는 것은 아니다.

## 9. 데이터 해상도와 연구 가능 범위

| 자료 | 할 수 있는 연구 | 입증할 수 없는 것 |
|---|---|---|
| 일봉·과거 뉴스 | 사건·종목 기억, 연속성, 일 단위 결과 | 초단위 진입·청산 순서 |
| 확보된 5분/1분봉 | 봉 단위 구조·정책 비교 | 봉 내부 고가·저가 발생 순서와 정확한 체결 |
| 진짜 1초 OHLCV | 초 단위 관측·일부 경로 연구 | 1초 내부의 정확한 틱 경로 |
| 1초 스냅샷·누적값 차분 | 관측 시점 가격·누적 거래 변화 | 누락된 초 내부 고저·체결 건수·방향 |
| 선택적 호가·실제 주문/체결 | 체결 비용·부분체결·실행 모델 검증 | 관측하지 못한 시장 전체 주문 이력 |

1분봉 약 1년, 특정 증권사 5분봉 약 5년은 현재 대화의 **미확인 확보 가능성**이다. 실제 요청 결과와 범위를 확인해 `coverage_manifest`에 기록한다. ‘어느 증권사도 틱을 제공하지 않는다’도 확인된 사실로 고정하지 않는다. 다만 이 프로젝트는 **과거 틱을 필수 전제로 하지 않는 것**을 확정한다.

이미 없는 고해상도를 복원한 것처럼 만들지 않는다. 과거 5년 자료와 앞으로 쌓는 1초 자료는 서로 다른 검증 층으로 운용한다.

## 10. 검증의 기준

가격이 오른 사례를 많이 모았다는 것과 실현 가능한 순수익 전략은 다르다.

- 미래 자료를 입력·후보 선정·정규화·테마 관계·RAG 결과에 섞지 않는다. [G2]
- 날짜순 학습·검증과 겹치는 사건·라벨 구간의 분리를 함께 적용한다. 기본 시간순 분할만으로 프로젝트의 모든 누출이 해결되지는 않는다. [G3]
- 확률은 대상 사건·기간·정책·표본 범위와 보정 결과를 붙인다. LLM 설명의 자신감은 성공확률이 아니다. [G4]
- MFE/MAE는 관측 가격 경로의 특징이지 평균 실현 이익/손실이 아니다. 진입 이후 고점을 항상 파는 정책은 평가하지 않는다.
- 손절·목표가가 같은 봉에서 모두 닿으면 유리한 순서를 지어내지 않는다.
- 모의투자는 신호·로직의 전진 검증이다. 자기 주문의 시장 충격까지 실제와 같다는 증거는 아니다.
- 한 주도주의 연속 1초 행 수를 독립 거래 사례 수로 표시하지 않는다.

전략은 **비용 차감 순손익 + 위험 + 실행 가능성 + 표본·기간 안정성**으로 비교한다. 주도주 전략은 무조건 고비중, 비주도주는 무조건 저비중이라는 결론도 미리 내리지 않는다.

## 11. 거래비용 계약

사용자가 합의한 기본 연구 가정은 **매수 0.015% + 매도 0.215% = 같은 금액 왕복 약 0.23%**다. 매도 0.215%는 수수료·세금 합산값으로 다룬다. 이를 모든 계좌·거래경로·과거 연도·상품의 법정 최대수수료라고 표시하지 않는다. 현재 확인한 키움 FAQ의 HTS·홈페이지 일반 주식 안내와는 부합하지만 실거래 적용값은 해당 계좌·시장·상품 기준으로 재검증한다. [G5]

비용은 **실제 체결금액별**로 부과한다. 동일한 총매수·총매도 금액을 나눴다는 이유만으로 비례 수수료가 주문 횟수 배만큼 증가하지 않는다. 재매수로 회전금액이 늘면 비용이 추가된다. 원단위 절사·최소수수료·별도 부과 방식은 실제 경로 확인 후 모델링한다.

슬리피지·스프레드·시장 충격은 체결가격 또는 별도 비용 중 한 곳에서 반영하여 중복 차감하지 않는다. 상세 공식과 검증 예시는 ③을 따른다.

## 12. 기존 시스템 재사용과 과설계 방지

새 서비스가 기존 원본 뉴스·시세·계좌 원장을 다시 소유하지 않는다. 이미 있는 값을 참조하고 필요한 파생 데이터만 추가한다. ①은 기존 설계대로 독립 정보 서비스로 두되, ②·③의 논리 책임마다 별도 서버·메시지 브로커·DB를 자동 도입하지 않는다.

기존 시장/테마/뉴스/타점/포지션 엔진을 삭제하지 않고 역할을 매핑한다. 규칙을 순수 함수 또는 부작용 없는 모듈로 빼서 재생·실시간이 공유하도록 한다. 성능 개선을 이유로 앱의 5,000줄 파일을 더 키우거나, 반대로 기능 없는 추상 계층을 대량 추가하지 않는다.

기존 DB 안의 논리 테이블과 작업 큐, 버전 있는 파일 아카이브를 우선한다. 새 운영 DB·별도 백필 DB를 상시 만들지 않는다. 테스트용 격리 환경과 재생용 결과 namespace는 별개다.

## 13. 공통 식별·시간·버전 계약

①의 `schema_version / as_of / run_id / computed_at / quality_flags`를 보존한다. 확장은 어댑터 또는 버전 추가로 하며 기존 소비자를 깨뜨리지 않는다.

```text
contract_version                  # 신규 공유 계약 버전
run_id / run_mode                  # 실행·환경 격리
as_of / computed_at                # 판단 기준 / 실제 계산 시각
input_max_available_at             # 판단에 쓴 입력 중 가장 늦은 이용 가능 시각
security_id / venue_scope / session_scope
scenario_id / scenario_version
feature_snapshot_id / feature_set_version
policy_id / policy_version / model_id
cost_model_id / risk_profile_id / execution_model_id
universe_snapshot_id / coverage_ref
quality_flags / evidence_refs
```

`as_of`는 현재 벽시계 시간을 임의로 넣는 것이 아니라 해당 결정이 허용한 정보 시각이다. 실시간은 실제 수신·확정된 입력만 사용한다. 과거 자료의 게시시각 추정과 실제 수신 기록은 구분한다. 당일 장 종료 후 만든 시황 분류를 당일 오전 특징에 넣지 않는다.

내부 시간은 timezone-aware UTC, 화면은 Asia/Seoul을 기본으로 한다. 매매일은 달력 날짜가 아니라 검증된 거래 세션에서 구한다. 이 문서 작성일이 거래일이라는 가정은 하지 않는다.

①의 자체 Phase 번호와 이 통합 단계 번호는 다르다. 이미 끝난 단계를 다시 구현하지 않는다. ① 일부가 미완성이면 계약 fixture 또는 실제 사용 가능한 결과만으로 ②의 독립 테스트를 진행할 수 있으나, fixture를 실분석 성공으로 보고하지 않는다.

## 15. 자원과 일일 운영

초기 백필·특징 생성·정책 탐색과 장중 추론의 부하를 분리한다. 새 하루 자료만 추가 계산하는 부분과 새 모델·특징 도입 때 다시 계산할 부분을 구별한다. 상수 개수의 지표 갱신과 조건 검사부터 실측하고, 모든 상태에서 LLM·전체 역사 검색을 반복하지 않는다.

기존 NAS는 수집·저장·가벼운 서비스, 사용자 Mac은 허용된 로컬 추론·연구, 기존 Windows 환경은 지원되는 증권사 연결 등으로 역할을 조정할 수 있다. 실제 배치와 램·CPU·API 제약은 조사한다. 메인 Mac 상시 가동, NAS 고성능 추론, GPU 학습 필요성을 전제하지 않는다.

관측 주기보다 처리 지연이 계속 길어지면 신규 위험 확대를 제한하고 원인을 기록한다. 먼저 중복 조회·재계산·메모리 일괄 적재를 줄인 뒤 자원 업그레이드를 검토한다. 장중 손절·계좌 감시는 배치 연구보다 우선한다.

## 16. 최종 수용 테스트의 핵심

1. 거래대금 100억→40억, 구조 유지: **거래대금 단독 사유의 자동 매도 없음**.
2. 09:05에 전일 연속성·장전 재료·시초 확인 충족: 09:20 하드 금지 규칙 없음.
3. 지수 상승·시장 폭 약화·후보 부재: ‘시황 좋으니 무조건 매수’ 없음.
4. 매도 후 재진입, 반복 ADD, 부분체결: 실제 수량·미체결을 반영하며 중복 주문 없음.
5. Soft 관찰 도중 hard 조건: 대기 연장·추가매수 없이 보호 절차 우선.
6. Top20 이탈한 보유 종목: 상태·청산 감시 계속 유지.
7. 과거 당일 최종 Top40 또는 미래 라벨: 선행 평가 입력 차단.
8. 1초 스냅샷만 있는 구간: 틱 순서·매수/매도 방향·진짜 OHLC 생성 금지.
9. 매일 통계 갱신: 승인 없이 운영 정책·LLM 가중치·실거래 설정 변화 없음.
10. LLM 중단: 기존 앱·계좌 보호 유지, 미확인 정보는 상태로 표시.
11. 실거래 OFF·미수 OFF: 어떤 LLM 출력·모델 점수로도 자동 활성화 불가.
12. 동일 총체결금액 분할: 비례 비용 합계 동일. 재회전 금액은 추가 비용 반영.

②·③에는 이를 세분화한 테스트를 둔다.

## 0. Codex에게 먼저 전달할 실행 지시

이 문서를 기준으로 개발하라. 전체 기능을 한 번에 구현하지 말고 **Phase 0과 Phase 1을 첫 작업 범위**로 삼아라. 기존 저장소의 지침·테스트·수집기·NAS ingest 경로·DB 구조·진행 중인 변경을 먼저 조사한 다음, 재사용할 부분과 새로 만들 부분을 구분하라.

- 기존 키움모니터의 실시간 조회순위, 시세 수집, 뉴스창, 수동 테마, 주문 기능을 다시 만들거나 임의로 변경하지 않는다.
- 새 기능은 독립 프로세스/서비스로 운영한다. 별도 서비스라는 이유로 원본 뉴스·시세를 복제하거나 **별도 운영 DB·백필 DB를 새로 만들지 않는다.** 기존 NAS 저장·검증·계산 경로를 재사용한다.
- 기존 기능을 실행 시점에 통째로 import해서 GUI 초기화나 실시간 수집을 유발하지 않는다. 기존 내부 API 또는 부작용 없는 공용 모듈로 연결한다.

- 이미 `candidate_days` 등으로 Top50 후보가 확정·저장되어 있다면 원본 계획을 덮어쓰지 않는다. 기존 순위 필드와 범위를 확인하여 뉴스 대상만 Top40으로 제한하는 새 계획 버전을 만든다. 해당 구조의 존재 자체는 코드에서 확인한다.
- 과거 뉴스와 전종목 일봉이 이미 완비되었다고 가정하지 않는다. 확인되지 않은 API 경로, 인증 방식, 과거 제공 범위, 종목코드를 추측해 구현하지 않는다.

- 수집·저장·재개가 검증되기 전에 수년치 전체 실행, 대규모 LLM 분석, 자동 테마 확정을 시작하지 않는다.
- 최종 보고에는 수정 파일, 실행 명령, 실제 수행한 테스트와 결과, 미실행 항목, 데이터 커버리지와 남은 한계를 구분하여 적는다.

**첫 완료 목표:** 작은 과거 구간의 Top40 후보를 만들거나 가져오고, 뉴스 수집 계획을 실행·중단·재개하여 기존 NAS 경로에 중복 없이 저장하며, 수집된 기사와 누락 상태를 화면에서 확인한다. LLM 없이도 이 단계는 완결되어야 한다.

## 1. 제품의 목적과 경계

### 1.1 무엇을 만드는가

단순한 ‘기사별 호재/악재 점수기’가 아니라, 뉴스와 객관적 시장 데이터를 연결해 **한국시장의 배경, 관심 테마, 종목 재료, 과거 시장 기억**을 제공하는 정보 시스템을 만든다.

사용자가 확인할 핵심 질문은 다음과 같다.

| 질문 | 필요한 결과 |
|---|---|
| 오늘 시장은 무엇을 중요하게 받아들이는가? | 주요 사건, 시장 환경, 반대 근거, 불확실성 |
| 어떤 테마가 형성·유지·재활성화되고 있는가? | 근거가 있는 테마 후보와 구성종목 관계 |
| 어떤 종목에 살아 있는 재료가 있는가? | 사건 상태와 후속 뉴스, 관측된 시장 반응 |
| 며칠 전 강했던 종목의 연속성은 어떤가? | 일봉·거래대금 기반 Stock Memory |
| AI는 그날 무엇을 판단했고 언제 바꿨는가? | 변경 불가능한 시점별 판단과 변경 이유 |
| 그 판단은 실제로 도움이 되었는가? | 정의가 명확한 사후 평가와 실패 사례 |

‘돈이 어디로 몰리는가’는 제품의 해석 관점이다. **거래대금 증가만으로 순자금 유입이나 자산 간 실제 자금 이동이 입증됐다고 표현하지 않는다.** 가격·거래대금은 시장 관심과 반응의 관측치로 사용한다.

### 1.2 이번 서비스가 하지 않는 일

실시간 틱 분석, 초단위 진입 판단, 박스 돌파 주문, 손절·익절·불타기, 포지션 관리, 자동매매는 기존/후속 타점·실행 엔진의 영역이다. 이 문서를 이유로 거래 권한을 추가하지 않는다.

LLM 기초모델의 사전학습이나 파인튜닝도 초기 범위가 아니다. **과거 사례를 DB에 저장하고 검색해 제공하는 것과 모델 가중치를 훈련하는 것은 다르다.** 화면에서도 DB 구축 진행률을 ‘모델 학습률’이라고 표시하지 않는다.

### 1.3 이전 설계와의 관계

기존 `NAS_News_Engine_Design.md`의 수집·중복 처리·장기보관 원칙은 재사용한다. 해당 문서의 ‘Gemini 유지’는 기존 앱에 대한 설명으로 남기되, **이번 새 분석 서비스의 기본 실행 경로는 로컬 LLM**으로 변경한다.

이 문서는 기존 프로젝트 전체 설계를 대체하지 않는다. 충돌이 생기면 최신 사용자 제약과 실제 코드의 안전한 통합 경로를 우선하고, 차이를 짧은 결정 기록에 남긴다. 이 문서 작성 과정에서 실제 NAS DB나 최신 레포 전체를 감사한 것은 아니다.

NAS 메모리 증설 여부와 여유 자원은 실행 환경에서 확인한다. 기존 대화의 메모리 수치만으로 신규 서비스의 처리량을 보장하지 않는다.

권장 초기 배치는 아래와 같다. 도식은 역할 구분이며 각각을 별도 마이크로서비스로 쪼개라는 뜻이 아니다.

```text
뉴스 소스 / 과거 거래대금·일봉 소스
                |
        기존 NAS ingest·검증 경로
                |
        기존 PostgreSQL / 원본 보관
                |
     Market Intelligence 서비스
     - 수집 계획·재개
     - 사건·테마·기억
     - 분석 큐·판단 이력
     - 내부 API·웹 화면
                ^
                | 인증된 내부 API로 작업 요청·결과 반환
                |
     Mac의 가벼운 LLM worker
                |
     Mac 네이티브 로컬 런타임
     (초기 후보: Ollama)
                |
        로컬에 내려받은 모델

기존 주식 앱 ← 읽기 전용 Intelligence API
```

Mac worker가 NAS에서 작업을 가져가고 로컬 LLM에 요청하는 방식을 우선한다. 이렇게 하면 NAS가 Mac의 원시 LLM 포트에 직접 접근할 필요가 없다. Mac이 꺼지면 큐에 남고, NAS의 수집은 계속된다.

## 3. 데이터 해상도와 역할 분리

### 3.1 과거 구축에 필요한 최소 데이터

**과거 분석의 종목 가격 데이터는 일봉 중심**으로 시작한다. 단, ‘Top40 종목의 일봉’과 ‘Top40을 결정하기 위한 전체 시장의 거래대금 정보’는 별개다.

| 데이터 | 초기 필요성 | 용도 |
|---|---|---|
| 날짜별 전체 시장 거래대금 순위 또는 거래대금 스냅샷 | 필수 | 그 날짜의 Top40 선정 |
| 선정 종목의 과거 일봉 OHLCV·정확한 거래대금 | 필수 | 종목 기억, 반응 관측, 연속성 연구 |
| 종목 마스터·이름 변경 이력·상장 상태 | 필수 | 과거 종목 검색과 생존편향 관리 |
| 뉴스 제목·URL·출처·공개시각 | 필수 | 검색·사건 연결·시간순 처리 |
| 뉴스 원문 | 확보 가능한 범위에서 우선 | 근거 추출. 미확보와 확보를 구분 |
| KOSPI·KOSDAQ 일별 지표 | 시황 분석 단계의 기본 입력 | 시장 배경과 상대 반응 |
| 해외지수·환율·금리·유가 등 시계열 | 단계적 추가 | 거시 환경의 사실 입력 |
| 당시 시총·유통주식 정보·수급 | 선택 | 상대 거래대금과 맥락 보완 |
| 과거 분봉·틱 | 초기 불필요 | 없으면 장중 선후관계를 검증하지 않음 |

시총·유통주식·종목 마스터는 **그 시점에 해당하는 값**이어야 한다. 현재 시총으로 과거 거래대금 강도를 계산하지 않는다.

전체 종목의 수년치 상세 일봉을 반드시 모두 새로 받아야 시작할 수 있는 것은 아니다. 공급자가 날짜별 공식 Top40 이상 순위를 제공하면 이를 재사용하고, 필요한 종목의 상세 이력만 추가해도 된다. 반대로 일부 관심종목만 저장된 일봉으로 만든 순위를 ‘시장 전체 Top40’이라고 부르지 않는다.

### 3.2 현재 운영에서만 추가하는 장중 요약

현재 등락률, 누적 거래대금, 같은 시간대 대비 거래대금 변화, 상승/하락 종목 수, 테마 구성종목 동조 등을 기존 경로에서 전달받는다. 각 값에는 관측시각과 거래 세션 범위를 붙인다.

Market Intelligence가 원본 틱·1초 데이터를 중복 수집하지 않는다. 장중 자료가 없으면 마지막 완결 일봉과 최신 뉴스만으로 판단하고, 화면에 `장중 확인 전`을 표시한다. 일봉만으로 ‘09:07 발견, 09:11 급등’ 같은 분 단위 선행 성능을 만들어내지 않는다.

## 4. 과거 관심종목: Historical Hot Universe

### 4.1 기본 정책

```yaml
universe:
  policy_id: turnover_top40_v1
  top_n: 40                         # 30으로 변경 가능
  market_scope: combined_kospi_kosdaq
  selection_basis: finalized_daily_turnover
  venue_scope: krx                  # 실제 공급자 정의를 확인 후 고정
  session_scope: regular            # 공급자 자료가 이 범위를 지원할 때만 사용
  instrument_scope: listed_equities
  include_preferred_shares: true
  include_etf_etn: false
  include_spac: false
  additional_candidates_enabled: false
  additional_candidate_limit: 0
```

이는 새 작업의 초기 기본값이다. 기존 수집 자료의 세션 범위가 다르면 원자료를 위 설정과 같다고 가장하지 않고 별도의 `scope`로 기록한다. KOSPI 40개 + KOSDAQ 40개가 아니라 **통합 40개**다.

전일·최근 강세주 기억은 Stock Memory에서 유지한다. 그것이 곧 매일 뉴스 대상 수를 자동으로 수백 종목까지 늘리라는 뜻은 아니다. 추가 수집은 예산이 있는 명시적 옵션으로만 수행한다.

### 4.2 선정 규칙

1. 거래일과 당시 상장 주식 집합 또는 신뢰할 수 있는 전체 순위 자료를 확인한다.
2. 대상 상품·시장·거래 세션 범위에 맞춘다. 같은 종목의 KRX·NXT·통합 자료를 중복 합산하지 않는다.
3. **실제 거래대금** 내림차순으로 정렬한다. 동률은 안정적인 종목 식별자로 정렬해 결과를 재현한다.
4. 상위 N개와 원래 거래대금·순위·선정 근거·자료 버전을 저장한다.
5. 공급자 공식 순위와 계산 순위가 있으면 표본 날짜에서 대조한다.

`종가 × 거래량`은 정확한 거래대금이 아니다. 이를 공식 Top40 복원에 조용히 대체하지 않는다. 대체값밖에 없다면 `approximate_turnover`로 구분하고 공식 순위와 분리한다.

일별 거래대금 상위는 관심종목의 **대리 기준**이다. 과거 키움 실시간 ‘조회순위’를 복원했다고 표시하지 않는다.

### 4.3 커버리지 검사

`complete_market / official_rank / partial_universe / unknown`을 기록한다. 일부 종목만 포함된 데이터에서는 `partial_universe`를 유지하고 시장 전체 순위 생성의 정식 완료를 허용하지 않는다. 공식 순위의 조회 상한이 20위라면 Top40 확보가 완료된 것이 아니다.

현재 살아 있는 종목만 사용하면 과거 상장폐지·합병 종목이 빠질 수 있다. 거래일별 상장 집합을 확보하지 못한 기간은 한계를 기록한다. 종목코드는 문자열로 보관하고, 코드 변경·재사용·회사명 변경을 고려해 내부 식별자를 분리한다.

### 4.4 저장할 후보 정보

```text
plan_id / plan_version
trade_date / selection_available_at
security_id / code_as_of_date / name_as_of_date
turnover / turnover_currency / turnover_unit
turnover_rank / rank_source / coverage_status
venue_scope / session_scope / instrument_scope
selection_reason / raw_snapshot_ref
```

완결 일별 순위는 **그날 종가가 확정되기 전의 장전 후보 선정 근거로 사용할 수 없다.** `selection_available_at`은 날짜만 보고 임의로 장전으로 지정하지 않는다.

## 5. 뉴스 수집 범위와 제공 가능성 확인

### 5.1 첫 실행 구간

장기 목표는 2019년부터, 가능하면 그 이전까지의 자료다. 그러나 먼저 서로 다른 연도의 소규모 구간에서 공급 가능성을 확인한다. 제공 여부가 확인된 소스만 실제 계획에 포함한다.

초기 실행은 한 번의 **유한한 백필 작업**이다. 지정 구간을 처리하면 종료한다. 이를 이유로 기존 실시간 수집기에 반복 작업을 자동 등록하지 않는다.

```yaml
backfill:
  requested_start_date: "2019-01-01"
  requested_end: latest_completed_session
  pilot_mode: true
  pilot_max_trade_dates: 5
  lookback_sessions: 10
  followup_news_sessions: 0
  source_concurrency: 1
  body_fetch_enabled: true
  llm_analysis_enabled: false
  auto_expand_related_stocks: false
```

`pilot_mode`에서는 전체 기간을 실제로 실행하지 않는다. 선택된 5개 거래일은 최근 날짜에만 몰지 않고 과거 제공 가능성을 확인하는 표본으로 정한다. 표본 수·기간·뉴스량은 설정 가능하다.

### 5.2 뉴스 기간 합치기

날짜 D의 Top40에 A가 들어왔다면 기본 수집 창은 **D 이전 10거래일부터 D 종료까지**다. ‘10거래일’을 거래소 달력으로 계산한 다음, 뉴스 검색에는 그 사이 주말·휴일을 포함한 달력 날짜 범위를 사용한다.

반복 선정된 A에 대해 매번 같은 기간을 검색하지 않는다. `종목 + 공급자 + 검색전략 버전`별 수집 완료 구간을 관리하고, 겹치는 요청을 합친 뒤 **누락 구간만** 실행한다. 다만 기간 중간의 실패를 감추는 단일 `최소일~최대일` 표시는 금지한다.

수집 윈도우와 그 윈도우를 요구한 후보 날짜의 연결은 유지한다. 이 때문에 날짜별 Top40과 실제 하루에 검색하는 고유 종목 수는 같지 않을 수 있다. UI에서 선정 종목 수, 검색 작업 수, 실제 기사 수를 분리한다.

후속 뉴스 수집은 기본 OFF로 두되, 나중에 D+5 등으로 확장할 수 있다. 사후 평가용 일봉 D+1·3·5·10 수집과 후속 뉴스 수집 옵션은 별개다.

### 5.3 뉴스 소스의 계약

수집 어댑터는 지원 능력을 명시해야 한다.

```text
provider_id
supports_date_range / supports_historical_search
provides_publisher_timestamp / provides_body
pagination_method / result_cap
oldest_verified_date / verification_evidence
permission_status / permitted_storage_scope
rate_limit_policy / last_verified_at
```

네이버 **공식 뉴스 검색 API**는 문서상 `query`, `display`, `start`, `sort`를 제공하며 `display` 최대 100, `start` 최대 1000이다. 공식 문서에 임의 날짜 범위 검색 파라미터는 열거되어 있지 않다. 따라서 이 API만으로 2019년 전체 뉴스 백필이 가능하다고 구현하지 않는다. 응답의 `description`도 원문 전체가 아니다. [S1]

네이버 웹 날짜검색이나 네이버증권 내부 엔드포인트는 공식 검색 API와 별개다. 과거 대화에서 일부 페이지가 조회되었다는 사실만으로 수년 전체 제공·완전 수집·장기 인터페이스 안정성을 가정하지 않는다. 기존 수집 코드, 실제 응답, 이용 조건을 확인하여 검증된 경로만 추가한다.

DART나 다른 원문 소스는 기존 프로젝트에서 연결·권한·보관 범위가 확인된 경우에만 재사용한다. 검색결과 접근 가능성이 기사 원문 재배포 허용을 의미하지 않는다. 유료 계약·자료 구매를 자동으로 진행하지 않는다.

### 5.4 넓은 시황뉴스와 종목뉴스

종목명 검색만으로는 기업 이름이 없는 정책·산업·해외시장 사건을 놓칠 수 있다. 따라서 구조상 아래 두 입력을 구분한다.

- `stock_targeted`: Top40 중심으로 깊게 수집한다. 첫 단계의 필수 범위다.
- `market_context`: 기존 시장·경제·산업 뉴스 피드를 재사용한다. 과거 제공 범위를 확인한 후 별도 예산으로 확장한다.

시장뉴스가 확보되지 않은 기간을 ‘전체 시황까지 학습 완료’로 표시하지 않는다. 첫 버전부터 과거 모든 경제뉴스를 무제한 수집하도록 범위를 넓히지 않는다.

### 5.5 검색·원문 품질

당시 회사명과 유효한 별칭을 사용한다. 일반 단어와 겹치는 이름, 우선주, 합병 전후 회사명은 코드·본문·회사 식별자로 검증한다. 검색에 걸렸다고 관련 종목으로 확정하지 않는다.

검색결과의 날짜, 원문 최초 게시시각, 수정시각, 네이버 제공시각은 다를 수 있다. 특히 공식 API의 `pubDate` 의미를 원문 최초 게시시각과 무조건 동일시하지 않는다. [S1]

원문을 얻지 못하면 `metadata_only` 또는 `snippet_only`로 보관한다. LLM이 링크만 받고 원문을 읽었다고 간주하거나, 비어 있는 원문을 생성해서 채우지 않는다.

## 6. 수집 작업의 안정성과 기존 시스템 보호

### 6.1 기본 흐름

```text
자료·권한 확인
  → 날짜별 Top40 후보 계획
  → 종목별 뉴스 기간 병합
  → 미수집 구간 작업 생성
  → 검색결과 메타데이터 저장
  → 중복 확인
  → 허용된 원문만 가져오기
  → 기존 ingest로 정규화·저장
  → 커버리지·체크포인트 갱신
  → 유한한 계획 종료
```

원문 수집과 LLM 분석은 별도 상태다. Mac이 꺼져 있거나 모델이 없어도 수집 완료를 막지 않는다.

### 6.2 기존 DB·계산 경로 재사용

기존 뉴스 원본, 시세, 종목 마스터, 계산 함수, 수집 진행표가 있는지 먼저 확인한다. 같은 의미의 원본 테이블을 별도로 만들지 않는다. 새 서비스 전용 상태·분석 이력은 기존 DB의 구분된 테이블/스키마에 추가할 수 있다.

과거 입력에도 기존 검증과 정상화 경로를 사용하되, `ingest_mode=backfill` 등으로 **실시간 알림·최신 상태 덮어쓰기·당일 매매용 부수효과를 억제**한다. 백필과 실시간은 실행·큐·우선순위로 분리하고 원본의 단일 출처는 유지한다.

개발·테스트는 운영과 분리된 임시 테스트 환경을 사용한다. 이는 별도 운영/백필 DB를 상시 추가하라는 뜻이 아니다. 운영 마이그레이션은 백업·롤백 경로를 갖추고 자동으로 파괴적 변경을 하지 않는다.

### 6.3 재시도·재개

작업 상태는 최소 `PENDING / RUNNING / RETRY_WAIT / SUCCEEDED / PARTIAL / FAILED / BLOCKED / CANCELLED`로 구분한다. 검색 결과 없음은 성공한 검색의 `result_count=0`이지 네트워크 실패와 같은 상태가 아니다.

큐를 기존 기능으로 재사용할 수 없다면, 기존 PostgreSQL 안에 작은 작업 테이블을 둔다. 다중 worker가 필요할 경우 `FOR UPDATE SKIP LOCKED`로 짧게 작업을 선점하는 방식이 가능하지만, 이는 일관된 전체 데이터 읽기가 아니라 큐 경합 회피 용도로 제한한다. [S4]

실제 HTTP·LLM 호출 중 DB 트랜잭션/행 잠금을 유지하지 않는다. 작업은 짧은 트랜잭션으로 임대하고 `lease_token`, 만료시각, heartbeat, 시도 횟수로 관리한다. 결과 반영은 유효한 임대 소유자만 하고, 반복 실행되어도 결과가 중복 생성되지 않아야 한다.

페이지별 저장이 커밋된 뒤 체크포인트를 진전시킨다. 중간에 종료되면 마지막 확정 위치부터 재개한다. 자동 재시도 횟수·최대 대기시간은 제한하고 오류를 영구 재시도하지 않는다.

### 6.4 소스 보호와 실패 해석

429 응답은 `Retry-After` 등 공급자 지침을 존중한다. 403·인증 실패·차단 의심은 이유를 기록하고 소스를 일시 정지한다. CAPTCHA, 로그인, 접근제한을 우회하는 코드를 만들지 않는다.

같은 페이지/ID 목록이 반복되면 페이지 종료 또는 오류 가능성을 검사한다. `결과 상한 도달`, `날짜 조건 무시`, `파서 실패`, `원문 접근 불가`를 별도 오류로 남긴다. 검색결과 상한에서 멈춘 구간은 `PARTIAL`이며 완료로 표시하지 않는다.

기존 실시간 조회순위·시세 수집이 최우선이다. 같은 인증키나 한도를 공유하는 작업은 기존 제한 관리자에 참여하고, 백필이 한도를 독점하지 않는다. 새 엔진을 켜도 기존 앱 시작 시간이 늘지 않게 한다.

## 7. 원본·시간·출처 데이터 계약

### 7.1 기사와 기사 버전

논리적으로 다음 정보를 보존한다. 기존 테이블에 이미 있으면 참조하거나 필요한 확장만 한다.

```text
article_id / provider_id / provider_article_id
canonical_url / original_url / publisher
title / body_text / body_hash / language
publisher_published_at / provider_distributed_at / source_modified_at
first_seen_at / fetched_at / timestamp_precision
content_status / source_rights_status / extraction_version
article_version_id / source_snapshot_ref
```

동일 기사 ID의 원문 수정은 새 버전으로 남긴다. 최신 본문으로 옛날 판단 근거를 덮어쓰지 않는다. URL 정규화는 추적용 파라미터만 제거하고 기사 식별에 필요한 파라미터는 유지한다.

고유 기사와 종목의 관계는 다대다다. A·B 두 종목 검색에서 같은 기사가 발견되어도 원문은 한 번만 저장하고 관계만 추가한다. 기사 제목이 같다는 이유만으로 서로 다른 기사를 무조건 하나로 병합하지 않는다.

### 7.2 판단 시각을 명확히 분리

| 필드 | 의미 |
|---|---|
| `event_occurred_at` | 사건이 실제 발생한 시각. 모르면 null |
| `publisher_published_at` | 확인된 원문 게시시각 |
| `first_seen_at` | 우리 시스템이 실제 처음 관측한 시각 |
| `source_available_at` | 출처 자료가 이용 가능했다고 확인되거나 추정된 시각 |
| `availability_basis` | 실시간 관측, 과거 아카이브, 게시시각 추정 등 |
| `as_of` | 이 판단에서 허용하는 정보의 기준 시각 |
| `computed_at` | 실제 계산/LLM 처리를 수행한 현재 시각 |
| `run_id` / `run_mode` | 실시간, 기억 구축, 과거 재생을 구분하는 실행 ID·모드 |

원본 시각은 timezone-aware 형태로 저장하고 내부 기준은 UTC, 화면 표시는 Asia/Seoul로 통일한다. 해외 거래일과 한국 날짜는 자동으로 같다고 처리하지 않는다.

실시간 평가에서는 실제로 수신한 시각을 존중한다. 08:00 기사라도 09:20에 처음 수집했다면 09:00 실시간 판단의 입력이었다고 표시할 수 없다.

과거 백필에서는 `first_seen_at`을 당시 시각으로 위조하지 않는다. 원문 게시시각과 그 버전의 과거 존재 여부를 근거로 ‘당시 이용 가능했을 것으로 추정’할 수는 있지만, **실제 과거 수신 기록과는 구분**한다.

날짜만 있거나 현재 원문에 후속 수정 내용이 섞여 있으면 `timestamp_precision=date_only` 또는 `historical_version_unverified`로 표시한다. 엄밀한 장중 평가에서는 제외하거나 보수적인 사용 가능 시점을 적용한다.

### 7.3 모든 해석에 필요한 공통 메타데이터

```text
schema_version / run_id / as_of / computed_at
model_id / model_digest / quantization / runtime_version
prompt_version / analyzer_version / config_hash
input_article_version_ids / input_market_snapshot_ids
retrieved_case_ids / input_manifest_hash
input_max_available_at / quality_flags
```

시장 데이터와 뉴스가 어떤 버전으로 입력되었는지 재구성 가능해야 한다. 모델명만 같아도 파일·양자화·런타임이 바뀔 수 있으므로 실제 배포 식별자를 남긴다.

## 8. 뉴스가 아니라 Event를 중심으로 기억하기

### 8.1 Article과 Event의 차이

`Article`은 개별 기사이고 `Event`는 그 기사들이 다루는 사건이다. 같은 발표를 여러 매체가 보도했다면 대표 근거로 묶어 중복 분석을 줄인다. 그러나 **같은 Event는 영원히 한 번만 분석한다는 규칙은 금지**한다.

새로운 금액, 조건, 확정 여부, 취소, 정정, 실행 일정은 기존 Event의 중요한 변경일 수 있다. 재전송과 의미 있는 업데이트를 구분하고 `Event Revision`으로 남긴다.

### 8.2 병합·분리 기준

기사의 대상 기업·산업, 행위, 발생 날짜, 계약/정책 식별자, 금액, 핵심 조건을 비교한다. 초기에는 정확한 ID·문자열·규칙으로 처리하고, 의미가 모호할 때만 LLM 후보 판단을 사용한다.

‘투자 검토’와 ‘투자 확정’, ‘수주’와 ‘수주 취소’, 같은 기업의 서로 다른 계약을 이름만 보고 병합하지 않는다. 병합·분리 이력과 근거를 남기고 되돌릴 수 있게 한다. 의미가 불확실하면 둘을 유지하는 편을 기본으로 한다.

### 8.3 사건 사실 상태와 시장 관심 상태를 분리

| 축 | 상태 예시 | 주의 |
|---|---|---|
| 사실·진행 상태 | UNKNOWN, RUMOR, PROPOSED, CONFIRMED, AMENDED, CANCELLED, COMPLETED | 공식 확인과 보도 주장 구분 |
| 시장 관심 상태 | NEW, DORMANT, ACTIVATING, ACTIVE, COOLING, INACTIVE | 가격·거래대금 반응의 관측 상태 |
| 검토 상태 | review_due_at, unresolved_questions | 시간이 지났다는 이유만으로 사건 무효화 금지 |

DORMANT → ACTIVE, COOLING → ACTIVE 등 재활성화를 허용한다. 상태는 반드시 일직선으로 진행할 필요가 없다. 사건이 유효하더라도 시장 관심이 없을 수 있고, 사건이 취소됐어도 취소 뉴스 때문에 거래가 증가할 수 있다.

### 8.4 분리해서 저장할 해석

`사건 내용의 중요성`, `경제적 영향 방향`, `시장 관심`, `가격 반응`, `거래대금 반응`, `후속 일정`, `근거의 신뢰도`를 별개로 저장한다.

‘며칠 동안 주가가 안 올랐다’는 관측만으로 `아직 가격에 반영되지 않은 확실한 호재`라고 단정하지 않는다. ‘이미 반영된 정도’는 직접 측정된 사실이 아니라 불확실한 해석일 수 있으므로 그렇게 표시한다.

며칠 뒤 종목이 오르면 이전 Event는 **설명 후보**가 될 수 있다. 동시에 발생한 다른 뉴스, 시장 전체 상승, 같은 테마의 변화도 함께 확인한다. 시간상 선행했다는 이유만으로 상승 원인으로 확정하지 않는다.

## 9. 자동 테마와 Stock Memory

### 9.1 기업의 업종과 시장의 테마를 분리

정적인 사업 분류와 시장 참여자가 거래하는 테마는 다를 수 있다. `industry`, `market_theme`, `event_specific_basket`을 구분한다.

예를 들어 가상의 지역 산업단지 발표에 대해서는 지역·사업·공시·보도된 시장 인식 등 근거를 통해 후보 관계를 만든다. LLM의 일반 지식만으로 ‘이 회사는 그 지역에 토지가 있다’ 같은 관계를 생성하지 않는다.

### 9.2 테마 관계 계약

```text
security_id / theme_id / relation_type
relation_source: manual | explicit_article | filing | inferred
status: proposed | observed | reviewed | rejected | inactive
valid_from / valid_to / known_as_of
supporting_evidence_ids / contradicting_evidence_ids
first_market_observation_at / last_market_observation_at
review_reason / quality_flags
```

여러 테마 소속, 테마 별칭, 과거 이름, 테마 병합/분리를 지원한다. 초기에는 관계형 DB의 노드·관계 테이블이면 충분하며 별도 그래프 DB를 필수로 도입하지 않는다.

수동 테마는 보존한다. 자동 후보는 별도 레이어에 표시하고 바로 덮어쓰지 않는다. 사용자가 거절한 관계를 동일한 근거만으로 매번 다시 확정하지 않는다. 새 근거가 생기면 무엇이 달라졌는지 보여준다.

같은 기사에 같이 등장하거나 주가가 함께 올랐다는 사실만으로 테마 관계를 확정하지 않는다. 현재 테마 구성을 과거 날짜에 그대로 적용하지 않는다.

### 9.3 ‘상승끼/연속성’의 데이터화

‘예전에 20~30%씩 크게 움직였던 종목이 며칠 뒤 다시 주목받을 수 있다’는 사용자의 관찰을 **검증 가능한 기억 특징**으로 표현한다. 재상승을 보장하는 법칙이나 매수 신호로 고정하지 않는다.

| 특징 | 기본 계산/기록 | 주의 |
|---|---|---|
| 종가 등락 | 공식 기준가 대비 종가 변화 | 기업행사·기준가 변경 고려 |
| 양봉 몸통 | `(close - open) / open` | 전일 대비 등락률과 다른 값 |
| 장중 강세 흔적 | 고가, 시가/기준가 대비 고가 변화 | 고가 도달 시각은 일봉만으로 모름 |
| 종가 위치 | `(close-low)/(high-low)` | high=low 처리 |
| 상대 거래대금 | 오늘 값 / 이전 구간 평균·중앙값 | 기준 구간에서 당일 제외 |
| 반복 강세 | 최근 N거래일 강한 움직임 날짜·횟수 | 임계값과 버전 기록 |
| 가격 유지 | 최근 고점 대비 낙폭·박스 주변 위치 | 계산과 해석을 분리 |
| 주도 역할 | 당시 테마 내 순위·관측 근거 | 현재 기준으로 과거 대장 재선정 금지 |
| 살아 있는 사건 | 연결 Event와 당시 유효 상태 | 잠복 재료와 현재 관심을 분리 |

상한가는 공식 상태/해당 시기 규칙을 사용할 수 있을 때 판정한다. 모든 날짜에 고정 등락률 하나를 대입하지 않는다. 수정주가 여부, 분할·병합·배당·거래정지·신규상장에 대한 계산 정책을 명시한다.

이 특징 계산은 코드가 담당한다. LLM은 결과의 배경 설명을 맡고, 타점 엔진은 이를 받아 현재 진입 조건과 결합한다. 같은 특징 계산을 뉴스 엔진과 타점 엔진 양쪽에 중복 구현하지 않는다.

## 10. 시황 종합 판단: Market State

### 10.1 사실·가설·확인을 나누기

숫자를 버리거나 LLM에게 모든 수치를 추측시키지 않는다.

```text
직접 확인한 시장 수치 + 출처가 있는 뉴스·사건
  → 국내 시장에 대한 해석·가설
  → 현재 KOSPI/KOSDAQ·종목 반응으로 확인/수정
  → 기준시각이 있는 새 판단 스냅샷
```

나스닥, 반도체·메모리 관련 해외시장, 금리, 환율, 유가, 국내 정책·기업 이벤트를 주요 입력 후보로 둔다. 비트코인·금 등은 고정적으로 중요/무의미하다고 분류하지 않고, 변동의 특이성·뉴스·국내 연결 근거에 따라 관심도를 달리할 수 있다.

금리와 채권가격을 혼동하지 않는다. 같은 움직임에서 나온 파생 신호를 서로 독립적인 근거 여러 개처럼 중복 가산하지 않는다. 공급자별 지수·선물·현물·ETF가 다르면 이를 숨겨 하나의 지표처럼 이어 붙이지 않는다.

### 10.2 출력 구조

```text
as_of / run_id / input_freshness
facts[]                         # 수치·사건, 각 근거 ID
market_assessment               # 강세/약세/혼조/불확실 등
participation                   # 지수 집중, 폭넓은 상승 등
concentration                   # 단일 주도, 테마 집중, 수급 분산 등
themes_to_observe[]              # 관심 이유와 반대 근거
stock_contexts[]                # 종목별 재료·기억 연결
hypotheses[]                     # 검증 가능한 가설
confirming_signals[]
contradicting_signals[]
unknowns[]
changes_from_previous[]
evidence_summary                # 사용자가 읽는 짧은 설명
```

다음 변경을 시간순으로 누적한다. 이전 판단은 덮어쓰지 않는다. `시장 전체 약세 → 특정 테마 집중`처럼 방향과 집중도가 함께 변할 수 있으므로 하나의 총점으로 강제 축약하지 않는다.

지수만 오르고 대부분 종목은 약한 상황을 표현할 수 있어야 한다. 확보하지 못한 상승/하락 종목 수나 투자자 수급을 만들어 넣지 않는다.

### 10.3 갱신 방식

중요 Event 업데이트, 장중 요약 신호 변화, 설정한 검토 주기, 수동 요청을 갱신 계기로 사용한다. 모든 기사마다 전체 이력을 LLM에 다시 보내지 않는다.

직전 상태와 새로 확인된 근거를 비교하되, 잘못된 요약이 계속 누적되지 않도록 주기적으로 원본 근거에서 재검토한다. 과거 재생과 현재 운영은 `run_id`와 최신 상태 포인터가 분리되어야 한다.

## 11. 로컬 LLM 실행과 Mac 사용 보호

### 11.1 첫 구현 원칙

초기에는 **실측으로 선택한 로컬 모델 한 개, 동시 추론 한 개**로 시작한다. 7~8B급 양자화 모델은 시험 후보일 뿐 정확도·속도·메모리 적합성이 보장된 권장 사양은 아니다. 큰 모델과 작은 모델을 동시에 상주시켜야만 작동하는 구조는 만들지 않는다.

Mac에서는 네이티브 런타임을 우선한다. Ollama 공식 FAQ는 macOS Docker Desktop에서 GPU 가속을 사용할 수 없다고 설명하므로, NAS의 Docker 배포 방식을 그대로 Mac LLM 서버에 복제하지 않는다. [S2]

실제 모델 ID·파일·라이선스를 확인하고 설정으로 지정한다. 존재하지 않는 모델 태그를 예제 그대로 실행하지 않는다. 분석 전 모델 설치 여부와 구조화 출력 지원을 검사한다.

### 11.2 구조화된 응답과 검증

Ollama는 요청의 `format`에 JSON Schema를 전달하는 구조화 출력을 지원한다. 스키마로 형태를 제한한 뒤 서버에서도 검증한다. 형식이 맞는 JSON이라고 내용이 사실이 되는 것은 아니다. [S3]

다음은 **새 서비스의 예시 계약**이지 실제 종목 분석 결과가 아니다.

```json
{
  "schema_version": "1.0",
  "analysis_type": "event_extraction",
  "as_of": "2020-01-02T08:30:00+09:00",
  "input_article_version_ids": ["demo-article-v1"],
  "event_candidates": [
    {
      "event_type": "industrial_development",
      "factual_status": "PROPOSED",
      "summary": "가상의 산업단지 조성 계획이 보도됨",
      "evidence_refs": ["demo-article-v1:p2"],
      "stock_links": [],
      "theme_candidates": ["지역 산업단지 개발"],
      "impact_direction": "unknown",
      "confidence_label": "low",
      "unknowns": ["실행 확정 여부", "수혜기업의 검증된 연결 근거"]
    }
  ],
  "quality_flags": ["synthetic_example"]
}
```

증거 ID는 실제 입력 문서의 허용된 문단 목록에 존재해야 한다. 주어진 후보 목록에 없는 종목코드를 임의 생성하지 못하게 한다. 근거가 없으면 빈 목록·unknown으로 반환하는 것이 정상이다.

검증 실패 시 제한된 재시도 후 `ANALYSIS_FAILED`로 남긴다. 오류를 숨기기 위해 빈 성공 결과를 넣지 않는다. `confidence_label`은 모델의 해석 자신감이지 상승 확률이 아니다. 확률을 표시하려면 별도 검증·보정이 필요하다.

### 11.3 실행 프로파일

```yaml
llm:
  enabled: false                   # Phase 1에서는 OFF
  provider: ollama_local
  model_id: null                   # 실제 확인한 모델 ID를 설정
  allow_cloud_inference: false
  inference_concurrency: 1
  max_loaded_models: 1
  input_token_budget: 6000         # 초기 시험값; 실제 토크나이저로 측정
  output_token_budget: 1200
  context_window_tokens: 8192      # 모델·런타임 지원 여부 검사
  keep_alive: "2m"
  request_timeout_seconds: 180     # 측정 전 보호 한도, 예상 처리시간 아님
  max_attempts: 2
  backlog_auto_run: false
```

위 키는 앱 설정이다. Codex는 실제 런타임 요청 옵션으로 명시적으로 매핑해야 하며, 앱 설정명을 Ollama가 그대로 지원한다고 가정하지 않는다. 시스템 프롬프트·검색 근거·스키마·출력까지 포함해 컨텍스트 초과를 막는다.

Ollama의 `keep_alive`와 동시 모델·요청 설정을 이용해 상주 시간과 병렬 처리를 제한할 수 있다. 병렬 수나 컨텍스트를 키우면 메모리 요구도 증가할 수 있다. 유휴 상태여도 모델이 메모리에 남을 수 있으므로, ‘요청이 없으니 메모리를 안 쓴다’고 판단하지 않는다. [S2]

### 11.4 사용자 제어

UI에 `분석 시작`, `분석 일시정지`, `백필 분석 허용`, `모델 해제 요청`을 둔다. 사용자 일시정지를 자동으로 풀지 않는다. Mac 사용 중 고부하가 관측되면 새 작업 선점을 멈추고 상태를 표시한다.

메모리 압력과 스왑 증가 등을 측정할 수 있으면 활용하되, 실제 측정하지 않은 값을 표시하지 않는다. CPU 우선순위를 낮췄다는 이유만으로 GPU·통합 메모리 사용량까지 엄격히 제한된다고 보장하지 않는다.

오래된 대기 분석이 재개될 때는 현재 중요 사건을 우선한다. 이미 시효가 지난 ‘실시간 상태 재계산’ 작업은 안전하게 합치거나 대체할 수 있지만, 원본 기사·역사 기록 자체는 삭제하지 않는다. 과거 백필은 별도 저우선순위 작업으로 유지한다.

### 11.5 외부 LLM 차단

Mac worker의 모델 호출 대상은 허용된 로컬 주소만 가능하게 한다. 외부 LLM URL로 자동 fallback하지 않는다. Ollama를 사용할 때는 해당 버전의 로컬 전용 설정을 확인하고 Cloud 기능을 비활성화한다. [S2]

모델 다운로드와 뉴스 수집에 인터넷이 필요한 것은 별개다. ‘외부 LLM 없이’는 ‘네트워크가 전혀 필요 없음’을 뜻하지 않는다. 뉴스 분석 본문이 외부 추론 서비스에 전송되지 않는지를 테스트한다.

## 12. 과거 재생과 미래정보 누출 방지

### 12.1 실행 모드 세 가지

| 모드 | 목적 | 허용되는 해석 |
|---|---|---|
| `MEMORY_BUILD` | 실제로 주목받았던 종목과 과거 기사·사건·반응의 관계 구축 | 사후적 사례 분석. 선행 예측 성과가 아님 |
| `REPLAY_EVAL` | 당시 사용 가능했던 입력만으로 판단 재생 | 시간·표본·자료 버전 제약을 만족한 범위에서 평가 |
| `LIVE_SHADOW` | 현재 들어오는 정보로 실제 시각에 판단만 기록 | 전진 검증. 주문하지 않음 |

첫 대규모 과거 작업의 기본 모드는 **MEMORY_BUILD**다. 이 모드에서 얻은 사례 DB는 유용하지만, ‘그 종목이 오르기 전에 AI가 찾아냈다’는 증거로 사용하지 않는다.

### 12.2 Top40 사후 선정의 한계

D일 거래대금이 큰 종목을 골라 D 이전 뉴스를 역으로 수집하면, 표본 선정에 D일 결과가 사용된다. LLM 프롬프트에서 미래 수치를 숨기는 것만으로 표본 편향이 사라지지 않는다.

엄밀한 D일 장전 검증에서는 D-1까지 확정된 자료로 후보를 정하거나, 당시 실제 수집 대상이 고정되어 있었던 별도 평가 집합을 사용한다. D일 확정 Top40을 사용할 수 있는 가장 이른 시점은 해당 자료가 이용 가능해진 이후다.

대형주·고거래대금 종목에 치우친 자료로 전 종목의 조기발견률을 계산하지 않는다. 전체 뉴스가 없으면 ‘수집된 집합 내 평가’로 명시한다. 반응이 없었던 사건과 종목도 보존하고, 성공 사례만 RAG에 남기지 않는다.

### 12.3 입력 시점 필터

`REPLAY_EVAL`에서는 기사뿐 아니라 다음 항목도 모두 `as_of`를 만족해야 한다.

```text
종목 마스터와 별칭 버전
테마 관계와 상태 버전
해당 시점까지 알려진 Event Revision
당시까지 완결된 가격·시총·수급 자료
당시 이용 가능했던 해외시장·거시 수치
유사 사례의 판단과 이미 완결된 사후 반응 구간
```

예를 들어 과거 사건 X가 D-2에 발생했더라도 X의 D+10 반응은 D 시점에 알 수 없다. RAG에서 사건 날짜만 검사하지 말고 **outcome_window_end와 결과 이용 가능 시각**도 검사한다.

뉴스 본문을 시간 필터링하면서 테마 DB는 최신 상태를 쓰는 식의 우회 누출을 막는다. 과거 재생 run은 실시간 run의 상태·후보 테마·검증 결과를 수정하지 않는다.

### 12.4 오늘 만든 LLM의 과거 지식

현재의 사전학습 모델은 과거 역사나 기업 사건의 사후 결과를 이미 알고 있을 가능성이 있다. ‘미래를 보지 마라’라는 프롬프트와 RAG 시간 필터만으로 이 가능성이 제거되었다고 주장할 수 없다.

따라서 과거 재생 결과에는 사용 모델의 식별 정보와 이 한계를 표시한다. 최종적인 운용 판단은 별도의 **LIVE_SHADOW 전진 기록**으로 확인한다. 모델 교체 후 과거 성과가 높아졌다고 곧바로 예측력 향상이라고 발표하지 않는다.

### 12.5 데이터가 불완전할 때

과거 원문 버전 미확인, 날짜만 있는 기사, 상장폐지 종목 누락, 과거 수급 미확보를 품질 플래그로 보존한다. 이를 무조건 모든 연구에서 버릴 필요는 없지만, 사용 가능한 분석과 불가능한 주장을 분리한다.

시간순 학습·검증에서는 테스트 구간 정보를 전처리·모델 선택에 사용하지 않는 것이 기본이다. 날짜순 분할과 gap을 지원하는 도구가 있어도, 같은 날짜의 종목 행·같은 사건의 반복 기사·겹치는 반응 기간을 프로젝트 수준에서 함께 처리해야 한다. [S5][S6]

## 13. RAG와 사후 시장 반응

### 13.1 초기 검색 방식

처음부터 모든 기사에 임베딩을 생성하지 않는다. Event 유형, 종목, 테마, 시기, 시장 상태, 핵심 키워드로 좁힌 사례 검색부터 만든다. 한국어 검색의 실제 적합성을 확인하고 필요할 때만 임베딩을 추가한다.

벡터 검색을 추가해도 날짜·출처·run·사건 버전 필터는 필수다. 검색이 느리다는 측정이 없는데 벡터 DB나 그래프 DB를 별도 운영하지 않는다.

```text
오늘/재생 시점의 사건
  → 시간 조건에 맞는 유사 사건 후보
  → 중복 기사군과 같은 사건의 반복 사례 제거
  → 성공·실패·미반응 사례 함께 선택
  → 당시 시장 배경과 반응 구간을 짧게 제공
  → LLM이 근거와 차이점을 설명
```

오래된 사례를 많이 보여주는 것만으로 판단 품질이 높아졌다고 가정하지 않는다. 검색 없이, 검색을 넣어서, 규칙만 사용해서 각각 비교한다.

### 13.2 일봉으로 측정하는 반응

처음에는 D+1, D+3, D+5, D+10 **거래일** 구간을 제공한다. 사건 발생이 주말/장중/장후인 경우의 기준일 매핑을 명시하고 버전으로 저장한다.

일봉만 있는 사건은 기본적으로 사건 정보가 이용 가능해진 이후의 첫 적격 거래일 시가를 평가 기준 후보로 삼을 수 있다. 정확한 매핑은 실시간/과거 자료의 시각 신뢰도와 공급자 세션 정의에 따라 결정하고 숨기지 않는다.

```text
reaction_baseline_time / reaction_baseline_price
horizon_sessions / outcome_window_start / outcome_window_end
close_return / benchmark_relative_return
observed_high / observed_low
turnover_ratio / peer_theme_reaction
data_coverage / corporate_action_policy
label_available_at / alternative_events
```

일봉 고가·저가는 관측된 가격 범위다. 그 가격에서 진입·청산 가능했다는 뜻이나 실현 가능 수익률이 아니다. 구간 중 고가와 저가 중 무엇이 먼저였는지 알 수 없으면 순서를 만들어내지 않는다.

‘상승 반응 없음’, ‘하락’, ‘테마 미형성’, ‘원인 불명’도 유효한 결과다. 뉴스 수집 실패와 실제 미반응을 같은 음성 정답으로 취급하지 않는다.

### 13.3 학습과 개선의 경계

LLM이 추출한 테마·영향 설명은 자동 생성 라벨이다. 곧바로 정답 데이터로 확정하지 않는다. 사후 주가 변화 역시 해당 뉴스의 인과적 효과를 단독으로 입증하지 않는다.

개선 과정은 다음처럼 운영한다.

```text
판단 기록 → 실제 반응 연결 → 오류 유형 확인
  → 개선 후보 생성 → 버전 고정 실험
  → 별도 평가·전진 검증 → 채택 여부 결정
```

AI가 매일 스스로 프롬프트·가중치·거래 규칙을 수정하고 적용하는 기능은 초기 범위에서 제외한다. 실제로 모델 훈련을 수행하지 않았는데 ‘학습되어 더 똑똑해졌다’고 표현하지 않는다.

## 14. 논리 데이터 모델과 저장 규칙

아래는 필요한 **논리 엔터티**다. 기존 테이블 매핑을 먼저 작성하고, 각 단계에서 필요한 것만 추가한다. 표 전체를 초기 마이그레이션으로 한꺼번에 생성하지 않는다.

| 엔터티 | 내용 | 도입 단계 |
|---|---|---|
| Run / Plan | 범위, 모드, 버전, 시작·종료, 입력 식별 | Phase 1 |
| Candidate Day | 날짜별 TopN과 선정 근거 | Phase 1, 기존 구조 우선 |
| Collection Coverage | 공급자·검색 대상·기간별 상태와 누락 | Phase 1 |
| Job / Lease | 큐, 재시도, 임대, 완료·오류 | Phase 1 |
| Article / Article Version | 원본·메타데이터·수정 버전 | 기존 데이터 재사용 |
| Security / Daily Bar | 종목 마스터와 일봉 | 기존 데이터 재사용 |
| Article Analysis | 구조화 추출, 모델·프롬프트·근거 버전 | Phase 2 |
| Event / Revision / Evidence Link | 사건과 변경 이력·기사 연결 | Phase 2~3 |
| Theme Relation | 시간축 있는 종목·테마 관계 | Phase 3 |
| Stock Memory Snapshot | 일봉 기반 종목 기억 | Phase 3 |
| Judgment Snapshot | 시장·테마 판단과 변경 이유 | Phase 3 |
| Outcome / Review | 사후 반응, 오류 유형, 검증 결과 | Phase 4 |

`mi_` 접두어나 전용 스키마는 이름 충돌 방지 후보일 뿐 기존 규칙을 무시하고 강제하지 않는다. 수집한 원문·일봉을 별도 ‘AI DB’로 복제하지 않는다.

금액 단위와 통화를 필수로 관리하고, 원본 값은 정밀도를 보존한다. null·미확보·0을 구분한다. JSON으로 유연한 분석 항목을 담을 수 있지만, 날짜·종목·run·상태 등 조회 핵심 필드는 인덱스를 만들 수 있는 명시적 컬럼을 우선한다.

중복 방지는 애플리케이션 검사뿐 아니라 DB의 유일성 제약으로 보장한다. 분석 결과 식별에는 입력 버전, 분석기·모델·프롬프트·설정 버전과 run 범위를 고려한다. 재분석은 새 결과 버전으로 남기고 과거 판단을 덮어쓰지 않는다.

원본과 판단 이력은 임의 만료 삭제하지 않는다. 로그·임시파일은 별도 정책으로 관리한다. 원문 보관은 해당 소스의 허용 범위를 따른다.

## 15. API와 날짜별 판단 대시보드

### 15.1 사용자 화면

초기에는 NAS에서 제공하는 가벼운 웹 화면이면 된다. 별도의 무거운 데스크톱 앱, 앱 설치기, 프런트엔드 프레임워크 여러 개를 만들지 않는다. 기존 웹/API 기술이 있으면 재사용한다.

| 화면 | 보여줄 것 |
|---|---|
| 수집 현황 | 계획 범위, 거래일·후보 수, 검색/원문/분석 상태, 오류, 재개 |
| 오늘/날짜별 판단 | 기준시각, 실제 계산시각, 사실, AI 해석, 반대 근거, 불확실성 |
| 판단 타임라인 | 변경 전후, 변경을 촉발한 기사·시장 데이터, 버전 |
| 사건·테마 | 잠복/활성/재활성 사건, 연결 종목, 근거, 수동 확인 상태 |
| 종목 기억 | 최근 강세·거래대금·과거 테마 역할·살아 있는 Event |
| 복기·평가 | 예측 당시 문장, 평가 규칙, 사후 반응, 미반응·오류 |
| 리소스·설정 | Mac worker 연결, 모델 상태, 대기열, 분석 일시정지 |

Phase 1은 **수집 현황과 기사 목록**만 만든다. 분석 단계가 완성되기 전에 가짜 AI 시황을 채워 넣지 않는다. 데모 데이터는 화면에 뚜렷하게 표시하고 운영 데이터와 분리한다.

### 15.2 시점별 판단 표시 원칙

`당시 입력 → 당시 판단 → 이후 변경 → 사후 결과`를 분리한다. 과거 날짜 화면의 판단 부분에 나중에 추가된 사실을 조용히 섞지 않는다. 재분석 결과는 원래 판단 옆의 별도 버전으로 보여준다.

설명은 **확인 가능한 근거의 요약과 판단 변경 이유**다. 모델의 숨겨진 내부 사고과정을 읽어낸 것처럼 표시하지 않는다. 기사 원문 링크, 근거 문단, 시세 시각, 모델 버전으로 추적 가능하게 한다.

`분석 대기`, `원문 없음`, `순위 자료 일부`, `시세 지연`, `과거 버전 미확인`, `사후 선정 자료`를 정상적인 상태 배지로 보여준다. 미분석을 중립 판단으로 바꾸지 않는다.

분 단위 시세가 없는 날짜에는 ‘몇 분 선행 발견’ 지표를 숨긴다. 자기보고 신뢰도를 상승 확률·승률처럼 표시하지 않는다.

### 15.3 제안 API 계약

기존 라우팅 규칙에 맞춰 아래와 동등한 기능을 제공한다. 아래 경로는 **구현 목표**이지 현재 존재하는 엔드포인트가 아니다.

```text
GET  /api/mi/v1/health
GET  /api/mi/v1/runs
GET  /api/mi/v1/runs/{run_id}/progress
GET  /api/mi/v1/candidates?date=...&plan_id=...
GET  /api/mi/v1/articles?security_id=...&from=...&to=...
GET  /api/mi/v1/market-state?as_of=...&run_id=...
GET  /api/mi/v1/judgments?date=...&run_id=...
GET  /api/mi/v1/events?as_of=...&status=...
GET  /api/mi/v1/themes?as_of=...&status=...
GET  /api/mi/v1/stocks/{security_id}/memory?as_of=...
GET  /api/mi/v1/reviews?date=...&run_id=...

POST /api/mi/v1/runs/{run_id}/pause
POST /api/mi/v1/runs/{run_id}/resume
POST /api/mi/v1/worker/jobs/claim
POST /api/mi/v1/worker/jobs/{job_id}/heartbeat
POST /api/mi/v1/worker/jobs/{job_id}/complete
POST /api/mi/v1/worker/jobs/{job_id}/fail
```

모든 목록은 제한·페이지네이션을 지원한다. 응답에 `schema_version`, `as_of`, `run_id`, 데이터 신선도·품질을 포함한다. 수정/제어 API는 인증·권한 검사를 하고, 작업 완료는 임대 토큰으로 보호한다.

기존 주식 앱에는 우선 읽기 권한만 제공한다. 화면을 열었다는 이유로 전체 백필·재분석이 실행되지 않게 한다. 기존 API 호환성을 유지하면 모델 교체 시 소비자 수정을 줄일 수 있지만, 스키마를 바꾸고도 ‘앱을 절대 수정할 필요 없다’고 보장하지 않는다.

## 16. 최소 코드 구조와 설정

실제 레포에 맞춰 이름을 조정한다. 책임 분리를 유지하되 전달만 하는 클래스, 한 구현만 있는 과도한 계층, 플러그인 프레임워크를 만들지 않는다.

```text
market_intelligence/
  config.py                  # 설정과 검증
  contracts.py               # 입출력 스키마
  integrations.py            # 기존 NAS ingest/API 연결
  universe.py                # TopN 선정과 범위 검사
  backfill.py                # 기간 병합·수집 계획·실행
  sources/                   # 검증된 공급자만
  jobs.py                    # 기존 큐 재사용 또는 작은 작업 큐
  analysis/                  # 이후 Event·LLM·Market State
  replay.py                  # 이후 시간순 재생과 평가
  api.py                     # 내부 API·UI 라우팅
  worker.py                  # Mac 로컬 LLM worker
  cli.py                     # 유한한 배치 진입점
  templates/                 # 가벼운 초기 화면
  tests/
```

최초 작업에서는 이후 단계의 빈 모듈 수십 개를 미리 생성하지 않는다. 존재하지 않는 API에 연결하는 코드를 성공처럼 포장하지 말고, 계약 테스트와 미지원 상태를 제공한다.

`.env.example`에는 설정 이름과 예시만 넣는다. API 키, NAS 인증키, DB 비밀번호, HMAC 키는 코드·문서·로그·테스트 fixture에 포함하지 않는다. 기존 비밀 관리 방식을 우선한다.

아래 명령은 **개발할 CLI의 사용성 요구 예시**다. 실제 명령 이름을 달리 구현하면 README에 실제로 실행되는 명령을 적는다.

```bash
python -m market_intelligence inspect --read-only
python -m market_intelligence sources probe --config config.yaml
python -m market_intelligence universe plan --config config.yaml --dry-run
python -m market_intelligence backfill plan --config config.yaml --pilot
python -m market_intelligence backfill run --plan-id <실제_PLAN_ID>
python -m market_intelligence backfill resume --run-id <실제_RUN_ID>
python -m market_intelligence report --run-id <실제_RUN_ID>
```

연결된 NAS의 실제 경로·호스트·DB명은 조사 후 설정한다. 문서의 플레이스홀더를 운영값으로 추측해 치환하지 않는다. API를 사용할 수 없는 환경에서는 로컬 fixture·테스트를 진행할 수 있지만, 실제 수집을 완료했다고 보고하지 않는다.

## 17. 단계별 구현 순서와 완료 조건

### Phase 0 — 현황 조사와 수집 가능성 확인

읽기 위주로 기존 레포 지침, 실행 진입점, ingest, 스키마, 뉴스 공급자, 일봉 범위, 후보 계획, 시간·단위, 인증·한도 관리, 배포 구조를 조사한다. 비밀값은 출력하지 않는다.

산출물은 짧은 `INTEGRATION_AUDIT.md`다. `확인됨 / 코드상 가능하지만 미실행 / 미확인 / 제약 있음`을 나누고, 어떤 데이터가 재사용되며 무엇이 부족한지 적는다. 특히 전종목 순위 복원에 충분한 데이터인지 확인한다.

**통과 기준:** 공급자·저장 경로·시장 범위가 식별되고 소규모 실제 응답으로 과거 날짜 요청이 검증된다. 미지원 소스는 명확하게 BLOCKED로 기록한다. 막힌 외부 경로가 있어도 독립적인 계약 테스트와 수집 계획 구현은 진행한다.

### Phase 1 — Top40 과거 뉴스 수집 MVP

후보 선정/가져오기, 수집 창 병합, 원본 중복 처리, 기존 ingest 연결, 오류·체크포인트·재개, 진행 상태와 기사 목록 화면을 구현한다. LLM·임베딩·자동 테마·시황 평가는 제외한다.

**통과 기준:** 확인된 작은 구간에서 실제 저장과 중단·재개가 동작한다. 같은 계획을 다시 돌려도 원문·관계가 불필요하게 중복되지 않는다. 부분 수집·결과 없음·실패가 구분된다. 기존 실시간 수집에 회귀가 없다.

실제 과거 소스가 막혀 있다면 테스트 가능한 부분까지 완료하되, 전체 Phase 1을 ‘실수집 검증 완료’라고 표시하지 않는다.

### Phase 2 — 로컬 LLM의 기사·사건 추출

Mac worker, 인증된 작업 교환, 로컬 모델 한 개, 구조화 출력·근거 검증, 모델/프롬프트 버전, 사용자 일시정지와 분석 결과 화면을 구현한다.

**통과 기준:** 외부 LLM 없이 표본 기사가 처리된다. Mac 미접속 중 수집이 계속된다. 시간초과·JSON 오류·없는 근거·없는 종목코드가 검출된다. 실제 Mac 사용 중의 메모리와 지연을 측정한다.

### Phase 3 — 사건 생명주기·테마 후보·종목 기억·일별 시황

Event 변경 이력, 지연 반응·재활성화 상태, 자동 테마 후보와 수동 관계 분리, 일봉 Stock Memory, 근거 기반 Market State와 판단 타임라인을 구현한다.

**통과 기준:** 며칠 전 사건이 사라지지 않고 현재 관측과 연결된다. 확정 근거 없는 테마는 후보로 남는다. 이전 판단을 지우지 않고 변경 근거를 확인할 수 있다. 일봉 특징 계산은 테스트로 재현된다.

### Phase 4 — 과거 사례 DB·RAG·평가

MEMORY_BUILD, 시간 필터 있는 RAG, REPLAY_EVAL, D+1·3·5·10 반응 기록, 표본/시간 누출 검사와 오류 복기를 구현한다. LIVE_SHADOW 기록도 준비한다.

**통과 기준:** 미래 기사·현재 테마 관계·미완결 D+10 결과가 과거 입력으로 들어가지 않는다. 사후 선정 표본은 선행 성능과 분리된다. 실패·미반응 사례가 남고, 지표 분모·구간·자료 누락을 확인할 수 있다.

### Phase 5 — 기존 주식 앱 연결과 규모 확대

검증된 API만 기존 앱에 읽기 전용으로 연결한다. 과거 수집 기간·분석량·추가 후보 수는 측정 결과를 보고 늘린다. 타점 엔진은 Market State·Theme·Stock Memory를 소비하지만 이번 단계에서 주문 로직까지 확대하지 않는다.

**통과 기준:** 새 서비스·Mac이 중단되어도 기존 앱의 시세·주문 기능이 유지되고, 앱은 분석정보 지연만 명확히 표시한다. API 스키마 버전과 호환성 테스트가 존재한다.

| T15 | 과거 뉴스가 기존 ingest로 유입 | 당일 최신 상태·실시간 알림을 오염시키지 않음 |
| T16 | Mac 종료·LLM 미설치·일시정지 | NAS 수집 지속, 분석은 대기. 외부 LLM fallback 없음 |
| T17 | 잘못된 JSON·없는 근거 ID·임의 종목코드 | 검증 실패. 근거 없는 성공으로 처리하지 않음 |
| T18 | 수동 테마와 자동 후보가 충돌 | 수동 원본 보존, 자동 후보는 검토 상태 |
| T19 | 며칠 전 Event 이후 주가 상승 | 재활성/연관 후보 기록. 단독 원인으로 확정하지 않음 |
| T20 | 장대양봉·기업행사·high=low·누락 거래대금 | 정의에 맞는 수치 또는 결측, 0으로 임의 보정하지 않음 |
| T21 | D일 장전 replay에 D일 최종 순위를 제공 | 시간 위반을 차단하거나 MEMORY_BUILD로만 허용 |
| T22 | RAG 후보의 사건은 과거지만 D+10 결과는 미래 | 미래 결과를 검색 입력에서 제외 |
| T23 | 과거 replay가 최신 테마/회사명 버전을 참조 | 해당 시점 버전만 사용, 미확보는 표시 |
| T24 | 날짜만 있는 기사와 일봉만 존재 | 분 단위 선행 발견 성능 계산 금지 |
| T25 | D+10 평가 종료일이 아직 오지 않음 | 미완결/censored로 기록, 실패나 수익률 0으로 처리하지 않음 |
| T26 | 새 모델·프롬프트로 재분석 | 새 버전 생성, 원래 판단 덮어쓰기 금지 |
| T27 | 기사 본문에 지시문·스크립트·내부망 URL 포함 | 지시 실행·UI 스크립트·임의 내부 요청 차단 |
| T28 | 새 서비스 정지·API 지연 | 기존 키움 앱 기능 유지, 분석 지연 상태만 노출 |

기본 정합성 테스트에는 종목코드 선행 0 보존, 금액 단위, timezone 변환, 거래일 캘린더, 수정주가 정책, 고유 제약, 입력 해시 재현도 포함한다.

## 19. 처리량·품질 측정과 규모 확대 조건

### 19.1 처음부터 보장하지 말 것

‘텍스트이므로 가볍다’, ‘M4 24GB면 하루 모든 뉴스를 충분히 처리한다’, ‘한 사건당 몇 초’ 같은 가정을 구현 예산으로 고정하지 않는다. 수년치 원문을 반복 해석하는 작업은 일상적인 소량 분석과 부하가 다르다.

뉴스 수를 `거래일 × 40`으로 계산하지 않는다. 이는 종목·날짜의 선정 횟수일 뿐이며, 실제 검색 페이지 수와 원문 수는 종목별 보도량·기간 겹침·재전송에 따라 달라진다.

### 19.2 반드시 남길 측정값

| 구분 | 측정값 |
|---|---|
| 수집 | 요청 수, 페이지 수, 고유 기사 수, 중복률, 원문 확보율, 오류 유형 |
| 데이터 범위 | 검증된 거래일·종목 범위, 순위 자료 완전성, 원문 시각 신뢰도 |
| LLM | cold/warm 지연, p50/p95, 입력/출력 토큰, JSON 성공률, 근거 검증 실패율 |
| Mac | 실제 메모리 압력·스왑 변화, 사용자가 느끼는 지장, 작업 일시정지 횟수 |
| NAS | CPU·메모리·I/O·DB 지연, 기존 실시간 수집의 지연 변화 |
| 큐 | 새 분석 작업 도착률, 처리율, 우선순위별 대기시간, 가장 오래된 작업 나이 |
| 분석 품질 | 사건 추출 오류, 잘못된 종목 연결, 과도한 테마 생성, 반대 근거 누락 |

완전한 전체 기사 수를 알 수 없는 검색 소스에서는 ‘전체의 100% 수집’이라고 표현하지 않는다. 계획된 질의 처리가 끝났다는 것과 모든 기사를 확보했다는 것을 분리한다.

### 19.3 확대 순서

소규모 날짜·기사 표본 → 한정된 과거 기간 → 더 긴 기간의 수집 → 사건 단위 선별 분석 → 현재 운영 순으로 늘린다. 수집은 끝났어도 모든 원문을 즉시 LLM으로 분석할 필요는 없다.

분석 부하가 커지면 먼저 중복 분석, 불필요한 재요약, 긴 입력, 자동 재시도, 지나친 테마 확장을 줄인다. 백필을 야간/수동 허용으로 제한할 수 있지만 사용자의 Mac이 항상 켜져 있다고 가정하지 않는다.

실측 처리율·대기열·품질이 부족할 때만 모델 또는 추론 장비 변경을 검토한다. 새 하드웨어나 유료 API 구매는 이 명세의 선행 조건이 아니다.

## 20. 보안·운영 안전장치

뉴스 본문과 검색결과는 신뢰하지 않는 입력이다. 본문에 포함된 ‘이전 지시를 무시하라’ 등의 문장을 시스템 지시로 해석하지 않는다. LLM에 셸·SQL 실행, 임의 URL 탐색, 주문, DB 직접 변경 권한을 부여하지 않는다.

원문 fetcher는 허용된 HTTP(S) 대상만 처리하고, 내부망·루프백·클라우드 메타데이터 주소에 대한 임의 요청을 차단한다. 리다이렉트 후 주소도 다시 검사한다. NAS 내부 API 통신은 별도로 명시한 허용 대상만 사용한다.

기사 HTML을 화면에 그대로 삽입하지 않는다. 본문·링크를 정제하고 파일 크기·응답 시간·리다이렉트 수를 제한한다. 원문 접근 실패를 우회하는 브라우저 자동화나 자격증명 공유를 무단 도입하지 않는다.

Mac의 원시 LLM 포트를 인터넷에 노출하지 않는다. NAS API도 기존 인증·내부망/VPN 정책을 따른다. 이 명세를 이유로 공유기 포트포워딩·방화벽 개방·인증 해제를 수행하지 않는다.

운영 DB에서 `DROP`, `TRUNCATE`, 기존 데이터 대량 삭제, 스키마 전면 재작성은 금지한다. 백필은 멱등한 입력과 제한된 추가 변경으로 실행하고, 사용자의 미커밋 작업을 보존한다.

## 21. 이번에 고정하는 결정과 나중에 정할 항목

### 고정된 방향

**외부 LLM 없는 신규 엔진, 기존 앱 보존, 기존 NAS DB·ingest 재사용, Mac 비전용 운영, Top30~40 중심 과거 뉴스, 일봉 중심 기억, 사건의 지연 반응·재활성화, 시간축 있는 자동 테마 후보, 날짜별 판단·복기, 파인튜닝보다 사례 DB 우선**을 지킨다.

### 실측·조사 후 결정할 항목

실제 소스별 과거 제공 범위, 정확한 모델 ID, 추론·메모리 예산, 역사적 순위 자료 범위, 원문 보관 권한, 현재 DB 매핑, 장중 갱신 주기, 검색 방식, 테마 후보 승격 기준은 확인 후 정한다.

모호한 부분을 전부 사용자에게 다시 묻고 멈추지 않는다. 기존 코드와 자료로 확인 가능한 것은 먼저 확인하고, 위험 없는 부분은 보수적인 기본값과 설정으로 구현한다. 다만 파괴적 운영 변경, 유료 서비스 가입, 임의 권한 확대는 추측해서 진행하지 않는다.

## 0. Codex에게 먼저 전달할 실행 지시

기존 시장·테마·뉴스·타점·포지션 엔진과 시세 수집 경로를 먼저 확인하고, 동일 기능을 새로 만들지 마라. ①의 API·스키마는 읽기 중심으로 소비하고 뉴스 원본·Stock Memory 계산을 복제하지 마라.

처음에는 **현재 수집 데이터의 정확한 의미 확인 → 공통 특징 → 돌파 기준선 → 판단 기록·재생**만 구현한다. 실거래·미수·자동 주문은 이 문서만으로 활성화하지 않는다. 후보 신호와 실제 체결 상태를 섞지 않는다.

본 문서의 모듈명·필드·설정·경로는 제안이다. 존재 여부를 조사하고 실제 저장소에 맞춰 최소 변경으로 구현한다. 모델이 아직 없으면 `규칙 기준선`, `확률 미추정`, `분석 대기`가 올바른 결과다.

## 1. 제품이 답해야 하는 질문

1. 오늘/현재 주목할 종목이 있는가? 없으면 쉬는가?
2. 그 종목을 주목하는 뉴스·테마·전일 연속성은 무엇이며, 실제 가격·거래가 이를 확인하는가?
3. 지금 **처음 진입**, **추가매수**, **보유**, **일부 매도**, **전량 청산**, **재진입** 중 무엇을 검토할 상황인가?
4. 그 판단은 어떤 새로운 관측으로 바뀌었고, 무엇이 생기면 무효가 되는가?
5. 자료가 충분한가? 판단을 내리지 않는 편이 맞는가?

②는 이를 구조화하여 ③으로 보낸다. **행동 후보를 찾는 것과 비용 차감 기대값을 검증하는 것, 최종 주문 허가는 각각 다르다.**

## 2. 범위와 초기 전략

### 2.1 초기 중심

사용자가 이해하는 주도주 돌파를 초기 중심으로 한다.

```text
기존 관심 후보
  → 충분한 관측·거래·맥락 확인
  → 이미 정의된 가격 구조에 접근
  → 돌파/확인 조건 관측
  → 최초 진입 후보
  → 확인 강화 시 증액 후보
  → 약화 시 유지·축소·청산 비교
  → 새로운 기회가 생기면 재증액·재진입 후보
```

매매를 한 번의 BUY와 한 번의 SELL로 단순화하지 않는다. 그러나 첫 구현부터 모든 행동의 학습모델을 만들지는 않는다. **Entry/Hold/Exit의 재현 가능한 기준선** 이후 Add/Reduce/Re-entry를 단계적으로 확장한다.

### 2.2 나중에 추가할 전략

주도주 안의 짧은 파동·스캘핑, 비주도주 통계 패턴, 종가베팅, 상한가 관련 전략 등은 별도 정책 ID·데이터 조건·검증 결과가 있을 때 추가한다. ‘스캘핑=몇 %’, ‘주도주=고비중’ 같은 고정 연결은 하지 않는다.

종가베팅은 다음 거래일 갭·야간 위험·세션 종료·결제까지 필요한 다른 정책이므로, 초기 장중 정책을 단순히 장 마감 후까지 켜두는 방식으로 구현하지 않는다.

## 3. 기존 ①과의 연결

①에서 다음을 읽는다.

- `Market State`: 지수 방향뿐 아니라 참여·편중·테마 집중·분산과 확인/반대 근거.
- `Theme`: 수동 관계와 자동 후보를 구분한 시점별 관계·상태.
- `Stock Memory`: 이전 강세·거래대금·주도 역할·살아 있는 사건과 연속성.
- `Event Revision`: 새로운 재료·정정·취소·후속 진행과 근거 시각.

기존 ① 제안 API가 실제 구현되어 있으면 재사용한다.

```text
GET /api/mi/v1/market-state?as_of=...&run_id=...
GET /api/mi/v1/themes?as_of=...&status=...
GET /api/mi/v1/stocks/{security_id}/memory?as_of=...
```

아직 없는 엔드포인트는 구현 완료로 취급하지 않는다. 검증된 기존 내부 계약이나 fixture로 개발하되 상태를 구분한다. 이전 판단을 바꾸지 않고 새 스냅샷을 연결한다.

LLM이 잠시 꺼져도 체결·가격 감시가 멈추지 않는다. 마지막 스냅샷의 신선도와 사용 조건을 검사한다. 맥락이 꼭 필요한 전략은 신규 진입을 대기할 수 있지만, 이미 보유한 포지션의 보호 절차를 LLM 응답까지 기다리지 않는다.

## 4. 종목 집합과 수집 범위

### 4.1 Top20은 현재 관심 후보군

초기에는 기존 실시간 조회 Top20을 재사용한다. 조회순위와 거래대금 순위, 테마 내 주도 순위를 별도 값으로 기록한다. 조회순위만 높다고 주도주·매수 대상으로 확정하지 않는다.

순위가 30초 등 별도 주기로 갱신된다면 마지막으로 수신한 순위를 그 시각과 함께 유지한다. 1초 시세 행에 같은 순위를 복사했다고 1초마다 새 조회순위가 관측된 것은 아니다. Top20 밖의 83위→51위 같은 경로를 추측하지 않는다.

### 4.2 좁게 계산하되 선택 과정을 남긴다

```text
기존 Top20·관심 목록           : 기존 경량 시세 기록
실제 후보·구조 접근 종목       : 공통 특징·상태 평가
보유·미체결·청산 진행 종목     : 우선 감시, 필요한 실행 데이터
```

핵심 후보가 보통 소수일 것이라는 사용자의 관찰은 자원 계획의 출발점이다. 매일 후보 1~2개를 억지로 만들거나, 추가로 나타난 유효 후보를 숫자만으로 숨기지는 않는다. 동시 보유 상한은 별도의 승인된 위험 설정이다.

Top20 이탈 시 경량 관측 종료 여부와 결과 관찰의 지속기간을 명시한다. 보유·미체결 종목은 계속 관리한다. 모델 결과의 관찰기간이 끝나기 전에 수집이 중단되면 `OUTCOME_INCOMPLETE`로 남긴다.

### 4.3 호가·틱은 단계적으로

초기에는 Top20 전체 호가창·원본 틱 저장을 요구하지 않는다. 실제 주문·핵심 후보의 체결 품질을 확인할 때 필요한 수준의 호가만 선택적으로 추가할 수 있다. 저장 가능한 데이터와 현재 API에서 실제 제공되는 필드를 먼저 확인한다.

고해상도 수집을 후보 선정 뒤 시작했다면 그 이전 구간의 호가가 없다는 사실을 보존한다. 나중에 호가를 보고 선정했어야 할 시점을 과거에 알고 있었다고 재생하지 않는다.

## 5. 1초 자료를 먼저 감사한다

‘1초 데이터’라는 이름만으로 진짜 1초봉으로 간주하지 않는다.

| 실제 수집 방식 | 정확한 표현 | 가능한 값 | 생성하면 안 되는 값 |
|---|---|---|---|
| 모든 수신 체결을 초 단위 집계 | 수신 체결 기반 1초 OHLCV | 수신 범위 내 OHLC·량·대금·건수 | 원천 피드 누락이 없었다는 보장 |
| 매초 마지막 가격/누적값 저장 | 1초 스냅샷 | 해당 시점 가격·누적 변화 | 그 초의 실제 고가·저가·체결 건수 |
| 누적 거래대금 차분만 저장 | 초 간 누적값 차분 | 두 관측 사이의 누적 증가 | 큰 단일 매도·매수 주체·호가 취소 |

필수 감사 항목: 원천 이벤트 시각, 실제 수신시각, 저장시각, 공급자 필드·단위, 집계 경계, 중복 처리, 누락 감지, 재연결, 누적값 리셋, 세션 범위, 정정 자료 처리.

사후에 더 정확한 자료가 들어와도 **당시 실시간으로 알고 있던 스냅샷**을 조용히 덮어쓰지 않는다. 정정 버전으로 추가하고 실시간 관측 재생과 정정 자료 연구를 구분한다.

### 5.1 제안 데이터 계약

현재 테이블에 매핑하고 중복 원본 테이블을 만들지 않는다. 실제 수집할 수 없는 필드는 null과 품질 상태로 둔다.

```text
security_id / provider_id / venue_scope / session_scope
observation_kind: second_bar | sampled_snapshot | cumulative_delta
event_time / received_at / stored_at / source_sequence
interval_start / interval_end / available_at
last_price
open / high / low / close                  # 실제 집계가 있을 때만
volume / turnover                         # 실제 값 또는 검증된 차분
cumulative_volume / cumulative_turnover
observed_duration_ms / observed_count
coverage_status / quality_flags / source_ref
```

매수·매도 체결 방향, 최대 단일체결, 호가 취소량 등은 검증된 원천이 있을 때만 확장한다. 가격 상승/하락만으로 거래 주체나 주문 취소를 사실처럼 생성하지 않는다.

### 5.2 거래가 없던 초와 못 받은 초를 구분

정상 연결·관측이 확인된 무체결 초와 연결 장애로 없는 초는 다르다. 누락 구간을 거래대금 0으로 메우면 ‘매도 압력 소멸’ 같은 잘못된 판단이 생길 수 있으므로 결측으로 표시한다.

화면용 가격 forward-fill은 가능하지만 `filled_for_display=true`로 구분하고 원본 실제 체결로 집계하지 않는다. 실제 체결 가능 가격을 화면 보간값에서 가져오지 않는다.

## 6. 특징 계산의 공통 원칙

특징 계산은 한 구현을 실시간·재생·연구가 공유한다. ①의 일봉 Stock Memory와 동일한 값을 ②에서 다시 다르게 계산하지 않는다. 비용이 큰 특징은 후보에만 계산하고 같은 `as_of + input_version`이면 재사용한다.

### 6.1 거래대금 창의 정의

`turnover_rolling_60s`는 **완결된 최근 60초**의 합으로 정의한다. 고정 분봉 거래대금, 현재 진행 중인 분의 누적값, 누적값을 1분으로 단순 환산한 추정치와 구분한다.

초별 구간이 `[09:00:00,09:00:01) ... [09:00:59,09:01:00)`이라면 09:01:00 기준 합계는 정확히 그 60개 구간이다. `59초 값 - 00초 값`이 자동으로 한 분을 대표한다고 가정하지 않는다. 경계·샘플 간격·이용 가능 시각을 테스트한다.

누적값 C를 사용하는 경우 동일 세션·동일 범위의 `C(t)-C(t-60s)`가 기본 관계다. 실제 관측 간격이 다르거나 기준값이 없으면 관측 범위·결측을 함께 표시한다. 리셋·음수 차분을 정상 거래대금으로 사용하지 않는다.

금액 저장은 원화 단위 또는 기존 원천 단위를 명시한다. `40억=4,000,000,000원`, `50억=5,000,000,000원` 변환 오류를 테스트한다.

### 6.2 초기 필수 특징

| 계열 | 필수 또는 우선 특징 | 사용 맥락 |
|---|---|---|
| 가격 구조 | 현재가, 과거 확정 고저, 기준 박스, 돌파 거리, 시가 갭 | 지금 위치와 가설 무효화 |
| 거래 | 최근 60초·수분 대금, 감소/회복, 창 완전성 | 신규 진입·증액 적격성 |
| 상대성 | 이전 거래일 동일 시간대 대비 거래대금 | 절대 대금의 종목·시간 왜곡 보완 |
| 전일 기억 | 전일/최근 강세·거래 집중·연관 Event | 연속성·시초 가설 |
| 시장·테마 | ①의 맥락과 현재 수치·반응 | 지수와 실제 매매 환경 분리 |
| 포지션 | 실제 보유·평단·미체결·시나리오 버전 | 행동의 가능 범위 |
| 품질 | 신선도·결측·관측 시작·지원 필드 | 판단 보류·신뢰 범위 |

VWAP, 유통시총 대비 회전, 호가·체결 상세 등은 자료가 확보되고 독립적인 검증 기여가 있을 때 추가한다. 기존에 이미 계산하는 지표라면 의미와 버전을 맞춰 재사용한다.

### 6.3 상대 거래대금

```text
relative_turnover_same_time
  = 현재 완결된 비교 창 거래대금
    / 이전 거래일의 동일 세션·동일 시간 창 기준값
```

기준값은 평균·중앙값 등 정책 버전으로 고정하고 **당일 미래 구간을 포함하지 않는다**. 신규 상장·거래정지·비교 거래일 부족·분모 0은 별도 상태로 처리한다. 작은 분모로 수백 배가 나왔다고 무조건 가장 강한 종목으로 판정하지 않는다.

```text
turnover_to_float_value
  = 동일 창 거래대금 / 당시 확인 가능한 유통시가총액
```

이 값은 금액 회전의 정규화 특징이지 순유입률이나 유통주주 교체율이 아니다. 주식수·유통비율의 시점과 가격 기준을 기록한다. 이미 유통시총인 분모에 유통비율을 다시 곱하지 않는다.

### 6.4 봉과 가격 구조의 시간적 정확성

진행 중인 봉의 최종 고가·거래대금을 미리 사용하지 않는다. 구간 끝에서 확인한 신호를 같은 봉 시작가에 체결시키지 않는다.

양쪽 미래 봉을 보고 확정하는 스윙 저점·지그재그를 즉시 알려진 지지선처럼 사용하지 않는다. 확인에 미래 관측이 필요하면 `confirmed_at` 이후에만 사용한다. 박스 경계·지지선은 생성 시각과 적용 정책을 기록한다.

## 7. 시장 환경과 주도주 후보

### 7.1 지수 방향과 거래 환경을 분리

①의 판단을 재사용하며, ‘좋은 장’ 한 점수만으로 진입하지 않는다.

예시 상황은 모두 가설적 분류다.

- 지수 상승·대형주 집중·중소형주 거래 약화·돌파 후보 부재.
- 지수 보합·한 테마 집중·관측된 종목 상대강도 유지.
- 지수 하락·시장 폭 약화·독립적 사건이 있는 테마만 활성.
- 전체 거래 활발하지만 여러 테마로 분산되고 돌파 실패가 반복.

상승/하락 종목 비율이나 시장 점유율을 Top20만으로 계산했다면 `Top20 내 비율`로 표시한다. 전체 시장 지표로 이름을 바꾸지 않는다. 테마 내 순위도 관측 커버리지를 명시한다.

### 7.2 주도주 판별은 점수 하나로 확정하지 않는다

관심·절대 대금·상대 대금·가격 반응·테마 역할·전일 연속성·뉴스 근거를 별도 관측으로 둔다. 주가 상승, 신고가, 단기 모멘텀처럼 겹치는 신호를 독립 증거 세 개로 합산하지 않는다.

후보 상태는 `UNASSESSED / WATCH / ELIGIBLE / ACTIVE / WEAKENED / INVALID / DATA_BLOCKED` 등 최소 집합으로 표현할 수 있다. 이름은 기존 엔진에 맞춘다. `ELIGIBLE`은 매수 확정이 아니라 해당 정책의 평가 대상이라는 뜻이다.

당일 나중에 가장 많이 오른 종목을 과거부터 `ACTIVE leader`였던 것처럼 라벨링하지 않는다. 당시 후보 판단과 사후 결과 라벨은 별도 열이다.

## 8. 장전 시나리오 계약

### 8.1 시나리오는 조건부 계획

LLM의 ‘오를 것 같다’를 주문 규칙으로 직접 사용하지 않는다. ①의 근거를 받아 **확인 조건·반대 조건·가격 구조·자료 신선도·정책 식별자**를 가진 계획을 만든다.

```text
scenario_id / scenario_version / security_id
created_at / as_of / valid_until_or_review_due
market_snapshot_ref / event_revision_refs / stock_memory_ref
thesis_summary / supporting_evidence / opposing_evidence
continuity_context
branches[]
  branch_id / required_observations / disqualifying_observations
  candidate_policy_id / required_data_capabilities
  structural_invalidation_rule_ref
  risk_profile_ref
unknowns / quality_flags
```

규칙 참조는 검증된 설정/코드 ID다. 자연어에 있는 임의 가격을 LLM이 주문 가격으로 바로 전송하지 않는다. 실제 수치가 없으면 ‘시초 구조 형성 후 갱신’처럼 보류한다.

### 8.2 강세·보통·약세 분기

시장의 단순 상승률 외에도 집중·분산·시장 폭을 분기 입력으로 사용할 수 있다. 위험 한도와 목표 노출은 ③이 계산한다. ②가 ‘약세면 무조건 25%, 강세면 500%’를 임의 확정하지 않는다.

각 분기에는 **진입하지 않음**이 포함될 수 있다. 장전 관심 후보가 장중 주도주가 되지 않아도 오류를 숨기거나 새로운 이유로 과거 가설을 덮어쓰지 않는다.

## 9. 장 초반과 시간대 정책

09:00~09:20은 기본 관찰 가설, 09:20~10:30은 사용자가 관찰한 활동 집중 가설이다. 검증 없이 하드 시간 제한으로 구현하지 않는다.

### 9.1 조기 진입 후보

전일 주도 연속성·현재 유효한 재료·실제 시초 가격 확인·충분한 거래·구조적 무효화 기준이 있다면 09:20 이전에도 후보 생성이 가능하다. 필요한 관측이 부족하면 장전 설명이 좋아도 기다린다.

초기 돌파가 무조건 우수하거나 무조건 위험하다고 라벨링하지 않는다. 관찰 시간과 놓친 기회, 성급한 진입의 손실을 같은 재생 조건에서 비교한다.

### 9.2 오전 이후

시간 경과만으로 청산하지 않는다. 보유·추세 정책의 종료 조건을 따르고, 새 진입은 해당 시간대의 자료·거래·EV·위험 조건을 다시 평가한다. 종가에 포지션을 남길지 여부는 ③의 세션 정책에서 명시한다.

## 10. 돌파 기준선: 먼저 측정 가능한 한 정의

‘돌파’라는 이름만 두지 말고 최초 기준선을 완전히 정의한다. 다음은 **구현 형식의 예시**이지 검증된 파라미터가 아니다.

```yaml
policy_id: leader_breakout_baseline
policy_version: 0.1
status: research_only
reference_level:
  type: prior_window_high
  window_seconds: null           # 데이터 해상도·기존 코드 확인 후 연구 설정
  exclude_current_interval: true
confirmation:
  mode: observed_price_cross
  min_breakout_ticks: null
  persistence_seconds: null
entry_gate:
  require_data_freshness: true
  require_turnover_gate: true
  turnover_threshold_krw: null    # 40억·50억 등은 연구 후보값
exit_policy:
  structural_rule_ref: null
  hard_risk_profile_ref: null
```

실행에 필요한 null이 남아 있으면 거래 정책을 활성화하지 않는다. 사용자 안전 승인값·기존 검증 설정을 재사용하거나, **주문 없는 연구 구성**에서 후보값을 명시한다. 초기에 박스·VWAP·호가·뉴스·모든 시장 지표를 AND로 강제하지 않는다. 가장 단순한 기준선을 먼저 두고 변수의 추가 효과를 비교한다.

같은 조건의 연속 1초 신호는 개별 독립 돌파 수백 건이 아니라 한 돌파 episode일 수 있다. 신호 시작·유지·실패·재시작을 정의한다.

## 11. 행동 후보와 포지션 정책

### 11.1 행동의 의미

| 행동 | 의미 | 기본 조건 |
|---|---|---|
| WAIT | 현재 신규 위험을 만들지 않음 | 정보·조건·EV 부족 또는 무신호 |
| ENTER | 무포지션에서 새 진입 후보 | 진입 적격·구조·무효화 기준 |
| HOLD | 현재 보유 유지 후보 | 시나리오·보호 조건 유지 |
| ADD | 보유량 증액 후보 | 새 증거·추가 진입 적격·③ 위험 여유 |
| REDUCE | 보유량 일부 축소 후보 | 검증된 익절/약화 정책 또는 위험 제한 |
| EXIT | 전량 청산 의도 | 무효화·보호 한도·정책 종료 |
| REENTER | 청산 후 새 진입 후보 | 새 episode·신호·현재 EV 확인 |

부분 익절 후 보유량이 남아 있는 상태에서 다시 사는 것은 실행상 ADD이고, 사용자 화면에는 ‘재증액’으로 설명할 수 있다. 전량 청산 후 새로 사는 REENTER와 로그를 구별한다.

### 11.2 현재가와 과거 체결가

이전에 10,000원에 사서 팔았다는 이유로 10,500원 재진입을 자동 금지하지 않는다. 그렇다고 고점을 갱신했다는 이유로 허용하지도 않는다. **현재 가격·새 보호선·비용·보유기간 기준의 새 기대값**을 ③에서 평가한다.

원금 회복·평단 낮추기만을 이유로 ADD를 만들지 않는다. ‘가격이 올랐으니 불타기는 언제나 안전’도 금지한다. 손실 중 증액 같은 다른 정책은 초기 범위 밖이며 별도 연구·위험 승인이 필요하다.

### 11.3 목표 노출은 ③이 결정

②는 가능한 행동과 근거를 보낸다. ③의 EV·정책이 목표 노출을 제안하고 Risk가 허용량을 정한다. ②가 신호 하나마다 고정 30% 주문을 누적시키지 않는다.

**설명용 고정 자본 예시:** `0→0.3→0.6→0.9→0.4→0.7→1.0→0`은 각 시점의 총 목표 노출이다. 증감은 목표와 실제·미체결 상태의 차이로 계산한다. 실제 기준 순자산이 변할 때는 숫자를 단순 차감하지 않고 수량을 다시 산정한다.

### 11.4 행동하지 않음도 비교 대상

새 정보가 없고 목표 변화가 작으면 같은 보유 상태를 유지할 수 있다. 조건 충족·해제 문턱 차이, 최소 변화량 등으로 불필요한 매매 반복을 줄이는 정책을 연구한다. 이런 지연·중복 방지 장치가 hard 보호 신호를 늦추면 안 된다.

## 12. 거래대금 감소 중 보유 판단

사용자 의도를 다음과 같이 고정한다.

```text
최근 60초 대금: 100억 → 40억
가격 구조: 유지
시나리오: 유효
위험 상태: 허용

→ 거래대금 감소만을 이유로 EXIT하지 않는다.
→ 신규 ADD 적격성은 별도로 재평가한다.
→ HOLD/REDUCE 등의 비교는 정책·EV·위험 근거에 따른다.
```

반대로 거래대금이 많아도 가격 구조 무효·뉴스 정정·위험 한도 위반이면 EXIT 후보 또는 보호 절차가 가능하다. 거래대금은 방향이 아니라 거래 규모이므로 하락 체결이 많아지는 때에도 증가할 수 있다.

거래대금 급감이 **큰 보유량의 출구 위험**을 높이면 ③의 유동성 위험 모듈이 축소를 요구할 수 있다. 이것은 `분당 50억 미만이면 매도`라는 단독 전략 룰과 다르며, 보유액·탈출 시간·호가·위험 조건을 근거로 기록한다.

## 13. 손절·무효화·조건부 관찰

### 13.1 세 가지를 구분

- **가격 구조 경계:** 돌파·지지 가설을 확인하는 수준.
- **조건부 관찰 정책:** 작은 이탈을 즉시 청산할지 제한적으로 관찰할지 사전 정의한 정책.
- **하드 위험 한도:** 계좌·포지션 보호를 위해 더 이상 모델의 판단을 기다리지 않는 제한.

관찰 경계의 이탈을 전부 ‘손절 위반 허용’이라고 표현하지 않는다. 하드 한도는 높은 확신·전일 주도·수익 중이라는 이유로 해제되지 않는다.

### 13.2 조건부 관찰 요구사항

```text
observation_policy_id / version
trigger_rule_ref
max_observation_duration
max_breach_depth
required_data_capabilities / freshness_limit
recovery_confirmation_rule
timeout_action / deterioration_action
hard_risk_profile_ref
```

초기에는 조건부 대기 기능을 OFF로 두거나, 기존에 검증된 명시적 정책만 재생에서 비교한다. 켜기 전에 실패·미회복 사례를 포함해 검증한다. 관찰 중 신규 ADD는 기본 금지한다. timeout이 반복 초기화되어 무한 대기가 되지 않도록 한다.

회복된 뒤에만 알 수 있는 ‘2초 만에 돌아왔다’를 이탈 직후 판단 특징에 넣지 않는다. t+2에 관측했다면 그때부터만 사용할 수 있다.

### 13.3 1초 해상도 제약

1초 스냅샷만으로 ‘누군가 큰 매도를 한 번 던졌다’, ‘0.2초만 이탈했다’, ‘매도물량을 모두 받아냈다’를 단정하지 않는다. 관측된 가격 이동·회복 샘플 수·누적대금 변화로 한정한다. 원인을 모르면 `unknown`이다.

### 13.4 보호선 상향과 버전

새 박스·지지 구조가 관측되고 정책이 허용하면 보호 기준을 높이는 후보를 만들 수 있다. 기존 구조·새 구조·확인 시각·기존/새 위험을 기록한다. 손실을 회피하려고 롱 포지션의 하드 가격 한도를 아래로 옮기는 기능은 초기 금지다. 보호선 변경과 실제 청산 체결가격은 동일하지 않다. [T2]

## 14. 분할익절·재증액·재진입

고정 수익률 도달, 추세 약화, 가격 구조, 테마 변화 등 정책별 후보를 생성한다. ‘오른 폭이 크다’만으로 항상 매도하거나, ‘주도주라서’ 항상 보유하지 않는다.

한 종목의 하루 흐름은 여러 거래 episode를 포함할 수 있다.

```text
campaign_id           # 하루·종목·시나리오 묶음
  episode_id_1        # flat → 보유·증감 → flat
    decision_ids
    order_ids
    fill_ids
  episode_id_2        # 재진입 후 새로운 flat-to-flat 구간
```

수익 일부를 실현한 뒤 재증액해도 동일 캠페인의 비용·최고 순자산·현재 위험은 이어서 본다. 수익 거래만 분리하고 손실 재진입을 다른 통계로 숨기지 않는다.

장기적으로 추세 물량과 짧은 파동 물량을 구분할 수 있으나, 실제 계좌 주문은 ③의 단일 원장·조정자가 합산한다. 서로 다른 정책이 같은 종목을 동시에 사고팔도록 독립 주문 루프를 만들지 않는다.

## 15. 뉴스·테마 급변 시 재평가

①의 새 Event Revision 또는 시장 상태 변경을 받으면 관련 시나리오만 재평가한다. 모든 뉴스마다 모든 종목의 LLM 분석을 다시 하지 않는다.

신규성·정정/취소·근거 품질·실제 가격 반응·이미 알려진 사건과의 관계를 소비한다. 기사 긍정 점수만으로 ENTER하지 않는다. 연관종목 관계가 `proposed`인 경우 확정 테마처럼 취급하지 않는다.

테마 1등주 강세·상한가 유지·이탈 같은 관찰은 관계가 검증된 범위에서만 특징으로 사용한다. 1등주 변화가 다른 종목 상승/하락을 보장하는 규칙은 아니다. ‘방어/헤지 테마’라는 명칭도 손실이 없다는 뜻으로 표시하지 않는다.

## 16. 상태·행동·주문을 분리한 최소 구조

단일 enum에 모든 조합을 넣어 수백 상태를 만들지 않는다. 다음처럼 직교하는 축을 기존 구조에 맞춰 사용할 수 있다.

```text
scenario_status : pending | active | weakened | invalid | expired
position_status : flat | open | closing | unknown
setup_status    : watching | approaching | triggered | failed | none
order_status    : none | pending | partially_filled | unknown
risk_status     : allowed | limited | reduce_only | halted
```

상태가 `triggered`여도 주문은 없을 수 있다. 주문이 승인되어도 미체결이면 포지션은 늘지 않는다. 잔고를 알 수 없으면 새 위험 확대를 멈추고 ③에 대사를 요청한다.

기존 상태 머신이 이미 같은 의미를 표현한다면 새 상태 체계를 통째로 도입하지 말고 매핑한다.

## 18. 알림과 사용자 화면

기존 Top20 화면·종목창을 무단 교체하지 않는다. 작은 배지·상세 패널·판단 타임라인부터 붙인다. 기본 화면은 다음 정도로 유지한다.

```text
A종목 | 돌파 관찰 | 장전 연속성 유지
거래 조건: 충족 / 가격 구조: 확인 대기
현재 행동: 신규 진입 대기
변경 이유: 거래는 회복했지만 기준 가격 돌파는 아직 미확인
통계: 미검증 기준선 / 자료: 09:06:04 기준
```

알림은 `접근 관찰 / 조건 충족 / 가설 약화 / 무효화 / 위험 제한 / 주문 상태`를 구분한다. ‘접근 관찰’은 상승 예언이나 진입 확정이 아니다. 시각·근거·현재/목표 상태·품질을 포함한다.

같은 조건 유지 중 알림을 매초 반복하지 않는다. 상태 변화·새 근거·중요한 위험만 갱신한다. 알림 수신이 늦으면 당시 기회와 현재 조건을 구별한다. 사용자가 알림을 읽기 전에 가격이 변했을 수 있으므로 주문 단계에서 반드시 재검사한다.

## 19. 최소 코드 구조와 설정

아래는 기능 배치 예시다. 기존 파일에 의미가 있으면 재사용하고, 단계별로 필요한 파일만 만든다.

```text
trading_intelligence/
  contracts.py       # 스냅샷·판단 계약
  features.py        # 실시간/재생 공통 계산
  scenarios.py       # 장전·장중 가설 및 버전
  breakout.py        # 첫 기준선 정책
  decisions.py       # 상태 평가와 행동 후보
  integration.py     # 기존 시세·①·③ 연결
  alerts.py          # 기존 알림 경로 확장
  tests/
```

권한·원장·주문 전송은 여기서 중복 구현하지 않는다. 범용 플러그인 프레임워크 대신 정책 ID와 작은 함수 인터페이스부터 시작한다. 새 전략 추가 시 필요한 계약 변경만 최소화한다.

```yaml
trading_intelligence:
  enabled: false
  mode: live_shadow
  primary_policy: leader_breakout_baseline
  universe_source: existing_realtime_top20
  extra_universe_expansion: false
  keep_monitoring_held_and_pending: true
  require_0920_for_all_entries: false
  exit_on_turnover_drop_alone: false
  full_orderbook_for_all_top20: false
  soft_observation_enabled: false
  allow_live_order_submission: false
  allow_leverage: false
```

설정 키는 이 프로젝트의 제안이다. 외부 API가 위 이름을 지원한다는 뜻이 아니다. 핵심 안전 키는 LLM 응답이나 자동 튜닝이 수정할 수 없도록 권한을 분리한다.

## 20. 구현 순서와 완료 기준

### T0 — 기존 구현·1초 의미 확인

실제 수신 필드·단위·시간·세션·Top20 갱신·보유 유지 여부를 조사한다. 기존 엔진에 매핑하고 `확인됨/미실행/미확인`을 구분한다.

**완료:** 가격 스냅샷과 진짜 1초봉을 구분하고, 누락·리셋·단위의 테스트 fixture를 확보한다.

### T1 — 공통 특징과 판단 기록

기존 Top20 기록과 필요한 공통 특징, ①의 읽기 결과 연결을 만든다. 부족한 맥락은 unknown으로 표시한다.

**완료:** 같은 입력·설정·시각으로 실시간 기록과 재생 특징이 일치한다. 원본을 복제하지 않으며 기존 앱 시작·수집 지연을 측정한다.

### T2 — 한 가지 돌파 기준선

Entry/Hold/Exit, 구조적 무효화, 거래대금 진입 게이트, 시간대 조건부 처리를 구현한다. 주문은 보내지 않는다.

**완료:** 실제 또는 합성 소규모 구간을 차트와 대조해 언제 어떤 정보를 보고 판단했는지 확인된다. 임의 승률이 없다.

### T3 — 분할 행동과 ③ 연결

ADD/REDUCE/REENTER 후보, 캠페인·episode, ③ EV/Risk 응답 소비를 추가한다.

**완료:** 부분 매도 후 재증액·완전 청산 후 재진입이 다르게 기록되고, 실제 잔고·미체결 기준을 유지한다.

### T4 — 확장 연구·경량 알림

통계 검증이 있는 정책만 연결하고 조건부 관찰·새 정책은 별도 실험으로 둔다.

**완료:** 기준선과 비교한 검증 근거, 자료 한계, 신호·알림 지연을 보고한다. 실거래 권한은 이 단계에도 자동 추가되지 않는다.

## 22. 확장 시 지켜야 할 원칙

사람이 붙인 전략 이름은 필수가 아니다. 그러나 이름이 없어도 관측 입력·행동·결과·비용·위험·자료 범위는 명시되어야 한다. 사람이 모르는 패턴 후보를 제시할 수 있지만, 발견과 실전 승격 사이의 검증을 생략하지 않는다.

**핵심:** 시황·주도주·거래대금·타점이라는 간단한 화면 뒤에, 시점과 근거가 명확한 상태·행동 계약을 둔다. 복잡한 설명을 만드는 것이 아니라 같은 상황에서 같은 판단을 재현하고 검증할 수 있게 만든다.

## 0. Codex에게 먼저 전달할 실행 지시

현재 연구·백필·Replay·주문·계좌 원장·비용 계산 코드를 먼저 조사한다. 동일 엔진·운영 DB·백필 DB를 새로 만들지 않는다. ①의 뉴스·시세 원본을 복제하지 않고 기존 NAS 저장·검증 경로와 필요한 파생 스냅샷을 사용한다.

**첫 구현 목표는 수익 모델이 아니라 신뢰할 수 있는 작은 재생이다.** 한 가지 돌파 기준선, 확보된 작은 구간, 명확한 체결 가정, 비용과 수량 대사, 결과와 한계 보고를 완성한다. 자동 학습·자동 배포·미수·강화학습을 한꺼번에 구현하지 않는다.

전략·모델·기간·계좌 한도의 값은 실제 확인 없이 정답으로 채우지 않는다. 승인되지 않은 위험 설정은 연구 전용 또는 미설정 상태로 두며 실거래 활성화를 막는다. 코드를 작성한 것, fixture 테스트 통과, 실제 시세 검증, 모의 체결 검증, 실계좌 검증을 분리해서 보고한다.

## 1. 연구 질문과 목표

사용자가 가진 경험칙의 예시는 다음과 같다.

- 거래대금 40~50억이 어느 종목·시각·계좌 규모에서 유효한 진입 기준인가?
- 같은 돌파도 지수 편중·테마 집중·수급 분산에서 결과가 어떻게 다른가?
- 장전 연속성이 있으면 시초 관찰시간을 줄이는 것이 유리한가?
- 추가매수·분할익절·재증액의 경로가 순손익과 위험에 어떤 차이를 만드는가?
- 작은 구조 이탈은 즉시 청산과 제한 관찰 중 어느 정책이 유효한가?
- 주도주 밖에도 비용·유동성·위험을 통과하는 패턴이 있는가?

질문에 대한 답은 ‘항상’이 아니라 **데이터 범위·상황·정책·비용·검증기간을 명시한 결과**다. 종목·상황마다 임계값을 지나치게 세분화해 사례가 몇 개밖에 남지 않으면 더 정교한 것이 아니라 불확실한 것이다.

초기 목적은 수익률 한 숫자의 최대화가 아니다. **비용 차감 기대값, 계좌 손실·낙폭, 꼬리 손실, 체결 가능성, 데이터 품질, 기간별 안정성**을 함께 비교한다. 위험 한도는 목적함수의 벌점만으로 처리하지 않고 별도 강제 제약을 둔다.

## 2. 전체 역할

```text
Research      : 가설·데이터셋·실험·후보 모델 생성과 검증
EV            : 현재 상태에서 행동별 순손익 분포·불확실성 평가

## 3. 데이터 감사와 커버리지 명세

### 3.1 확보 여부를 추측하지 않는다

requested_from / requested_to
verified_from / verified_to / verified_segments
bar_or_observation_kind / native_resolution
timezone / timestamp_precision / availability_basis
price_adjustment_policy / turnover_definition / units
missing_segments / duplicate_policy / correction_policy
source_refs / permission_status / known_limitations
```

가장 오래된 날짜와 가장 최근 날짜 사이가 모두 채워졌다고 단정하지 않는다. 완결 일봉과 미완결 당일봉, 수정주가와 실제 체결 주가, 거래정지·휴장과 수집 실패를 분리한다.

### 3.2 사용 가능한 해상도별 연구

일봉은 기억·연속성, 분봉은 봉 단위 돌파 정책, 1초 자료는 초 단위 관측 정책을 담당한다. 일봉·분봉을 보간해서 정교한 1초 타점 라벨을 만들지 않는다.

1초 스냅샷은 진짜 OHLC와 다르다. 그 초에 보지 못한 가격 경로를 정답으로 생성하지 않는다. 필요한 호가·방향·개별 체결량이 없으면 해당 특징을 쓰는 정책은 `UNSUPPORTED_BY_DATA`다.

### 3.3 단일 원본·파생 캐시

원본과 관측 이력은 불변 버전으로 보존한다. 특징·라벨·재생 결과는 입력 해시와 버전으로 관리한다. 원본을 별도 ‘AI 학습 DB’로 복제하지 않는다. 필요한 실험 스냅샷·파일 캐시는 원본 참조와 생성 경로가 있는 파생 산출물로 한정한다.

## 4. 연구 집합과 선택 편향

### 4.1 과거 Top40과 실시간 Top20

①의 당일 최종 거래대금 Top40은 **뉴스 기억 구축용 사후 선정 집합**이다. 이 집합에서 D일 이전 뉴스를 모을 수는 있지만, 그 결과만으로 D일 오전 전체 시장에서 종목을 선행 발견했다는 성과를 계산하지 않는다.

선행 평가에는 D-1까지 알 수 있던 후보, 당시 실제 Top20 기록, 또는 이용 가능 시각이 명확한 재생 스캐너를 사용한다. 과거 실제 조회 Top20이 없으면 거래대금 기준 대리 집합이라고 명시하고, 실시간 Top20과 별도 성과를 낸다.

### 4.2 실패와 미거래를 남긴다

성공 주도주만 모으지 않는다. 후보였지만 실패한 돌파, 거래대금 부족, 아무 반응 없음, 조건을 기다리다 종료, 모델이 진입하지 않은 사례를 기록한다.

거래대금 문턱을 연구하면서 문턱 아래 원본을 모두 삭제하지 않는다. 다만 연구 목적상 확보하지 않은 전 종목 고해상도까지 새로 수집할 필요는 없다. **보유한 집합 내 연구의 범위와 한계**를 명확히 한다.

### 4.3 독립 사례 수

동일 종목의 한 돌파를 1초마다 기록해 180행이 생겼다고 독립 성공 사례 180건으로 집계하지 않는다. `signal_event_id`, `episode_id`, `trade_date`, `theme_event_id`를 이용해 겹치는 사건·시장 영향을 그룹으로 평가한다.

보고서에는 최소 행 수, 고유 신호 수, 고유 종목 수, 거래일 수, 시장 국면 분포를 함께 적는다. 충분한 사례 수에 대한 단일 만능 숫자는 두지 않는다.

## 5. 시간 일관성과 미래정보 누출 방지

예측 시점에 사용할 수 없던 자료로 모델을 평가하면 성과가 과대평가될 수 있다. 전처리·특징 선택도 학습 구간에서만 맞춰야 한다. [R1]

모든 실험은 다음 시각을 구분한다.

```text
observation_time          # 시장·기사의 관측 대상 시각
received_at               # 실제 수신 시각
available_at              # 해당 버전을 판단에 사용할 수 있었던 시각
as_of                     # 의사결정의 정보 기준
computed_at               # 계산한 실제 시각
label_window_end          # 결과 관찰 종료 시각
label_available_at        # 결과가 확정되고 사용 가능해진 시각
```

검증 시 `input_max_available_at <= as_of`를 강제한다. 이미 미래를 담고 있는 종목 집합·테마 관계·시총·라벨·RAG 사후 결과도 검사한다.

당일 종료 후 산출한 ‘오늘은 강한 테마장’ 분류를 당일 09:05 특징으로 사용하지 않는다. 당시에 계산된 또는 당시 관측만으로 재현한 시장 상태를 사용한다. 현재 사전학습 LLM이 과거 사건의 이후 결과를 이미 알고 있을 수 있다는 ①의 한계도 유지한다.

현재 모델로 과거를 재설명한 결과와 당시 고정된 모델의 전진 예측을 구별한다. `first_seen_at`을 과거 기사 게시시각으로 위조하지 않는다.

## 6. 특징·라벨·정책 데이터셋

### 6.1 특징은 당시 관측만

②의 FeatureSnapshot을 재사용한다. 종목·시장·테마·뉴스·시간대·포지션·자료 품질을 포함할 수 있으나 처음부터 수백 변수를 만들지 않는다. 초기 기준선과 비교하며 필요성이 검증된 특징만 추가한다.

### 6.2 ‘성공’ 정의를 먼저 정한다

다음 확률은 서로 다르다.

- h분 뒤 가격이 현재보다 높은 확률.
- h분 내 정한 목표에 **보호 경계보다 먼저** 도달할 확률.
- 특정 진입·청산 정책을 적용한 episode의 비용 차감 순손익이 양수일 확률.
- ADD와 HOLD 중 ADD의 이후 계좌 성과가 더 나을 확률.

`p_success`만 저장하지 말고 `event_definition_id`, `horizon`, `exit_policy_id`, `cost_model_id`, `reference_price_basis`를 붙인다. 임의의 5분 상승 확률을 손절을 포함한 수익 확률로 바꾸지 않는다.

### 6.3 MFE·MAE 정의

비교 기준 가격 p0과 구간 [t,t+h]를 명시한다. 연구상 가격 경로 특징의 예시는 다음과 같다.

```text
MFE_return = max(0, max(P(u) / p0 - 1))
MAE_loss   = max(0, max(1 - P(u) / p0))
                u ∈ 관측 가능한 [t,t+h]
```

본 계약은 둘 다 0 이상으로 저장한다. 기존 MAE가 음수 수익률 방식이면 변환·표기를 명시한다. 고가/저가 봉을 쓰는지 관측 가격만 쓰는지 구분한다.

**MFE는 실현 가능한 평균 이익이 아니고, MAE는 실제 손절 평균 손실이 아니다.** 순서·체결·비중·비용이 있는 정책 재생 결과로 손익비와 기대값을 계산한다. 성공 사례의 MAE만 보고 손절선을 정하지 말고 실패·미회복·미관측 사례까지 포함한다.

### 6.4 경로·완결성

라벨에 첫 목표 도달 시각, 첫 보호 경계 도달 시각, 평가 종료, 경로 모호 여부를 남긴다. 같은 봉에서 목표와 보호선이 모두 닿으면 순서를 모른다. 해상도 부족은 `AMBIGUOUS_PATH`로 표시하고 보수 가정·제외·상하한 비교를 별도 보고한다.

관찰 끝이 아직 오지 않았거나 수집이 끊겼으면 `PENDING / CENSORED / MISSING`로 구분한다. 실패·수익률 0으로 자동 변환하지 않는다. 장 마감에 평가를 끝내는 정책과 다음 거래일까지 연장하는 정책도 구별한다.

### 6.5 사람 행동 기록은 선택 사항

사용자의 실제 판단·주문 기록은 모방학습 또는 복기 자료가 될 수 있다. 그러나 숙련 트레이더의 상세 로그가 없다고 시작을 막지 않는다. 초기에는 재현 가능한 규칙 기준선과 관측 가격에서 계산한 결과로 연구한다.

사람의 행동은 정답으로 확정하지 않는다. 매매 후 설명과 매수 당시 기록을 구분하고, LLM이 생성한 이유를 인간이 실제 당시 생각한 근거로 저장하지 않는다.

## 7. 연구 단계: 단순 기준선에서 시작

### 7.1 기준선

한 가지 돌파 정책을 먼저 고정한다. 진입 기준, 참고 가격, 관찰 창, 보호선, 청산 조건, 세션 종료, 비용·체결 가정을 빠짐없이 정의한다. 진입하지 않는 기준선도 비교한다.

### 7.2 제한된 실험

처음부터 모든 파라미터의 곱집합을 전수 탐색하지 않는다. 거래대금 후보 문턱, 시간대, 확인 지연, 손절·익절 한 가지처럼 질문을 나눠 탐색 예산을 제한한다.

예를 들어 40억·50억·80억의 비교를 한다면 선택한 범위·이유·실험 횟수를 기록하고, 주변 값에서도 결과가 유지되는지 확인한다. 한 점에서만 극단적으로 좋은 설정은 별도 의심 대상으로 본다.

### 7.3 조건부 통계·ML

규칙 기준선 → 조건별 통계 → 필요한 경우 작은 분류/회귀/분위수 모델 순으로 비교한다. 알고리즘 이름이나 파라미터 수가 성과를 보장하지 않는다. 같은 데이터·비용·검증 분할에서 비교한다.

### 7.4 행동 경로 연구

Entry/Add/Hold/Reduce/Exit/Re-entry와 목표 노출 경로를 정책 단위로 비교한다. ‘어제 제일 잘 된 30→60→90 경로’를 학습 정답으로 바로 삼지 않는다. 학습 구간에서 찾은 경로를 다음 검증 구간에서 평가한다.

### 7.5 강화학습·LLM 파인튜닝

초기 필수가 아니다. 강화학습은 체결·비용·시장 충격 모델의 허점을 이용한 가짜 성과가 생기지 않는지 검증한 뒤 고려한다. LLM 파인튜닝은 뉴스 추출·시나리오 형식 등 명확한 오류 목표와 평가셋이 있을 때 별도 실험으로 둔다.

LLM에 원시 시세를 많이 보여주는 것만으로 확률·주문·위험 모델 학습이 완료되었다고 표시하지 않는다.

## 8. 검증 설계

### 8.1 시간순 분리

학습 → 모델/정책 선택용 검증 → 최종 평가 구간을 시간순으로 나눈다. 이후 여러 전진 구간을 옮겨가며 반복한다. `TimeSeriesSplit` 같은 도구의 시간순·gap 기능은 참고할 수 있으나, 종목·날짜·사건 그룹과 중첩 라벨 처리는 직접 설계한다. [R2]

정규화, 특징 선택, 거래대금 문턱, 확률 보정, 정책 선택 모두 최종 평가 구간을 보지 않고 정한다. 동일 이벤트의 1초 행을 무작위로 나누지 않는다.

라벨 관찰 구간이 검증 시작을 넘어가는 학습 표본은 제거·분리한다. 경계 주변 간격은 라벨 기간과 종속성에 맞춰 설계하고 단일 고정 gap이 모든 경우를 해결한다고 가정하지 않는다.

### 8.2 과도한 탐색과 선택 편향 관리

실험 ID·시도한 조건·실패한 모델도 기록한다. 수많은 실험 중 최고 한 개만 고르고 탐색 횟수를 숨기지 않는다. 새 아이디어를 최종 평가 결과를 보고 반복 수정했다면 그 구간은 더 이상 최종 미사용 평가셋이 아니다.

날짜·시장 사건 단위 블록 재표집 등으로 불확실성을 볼 수 있다. 한 이벤트 내 행을 독립으로 취급한 지나치게 좁은 신뢰구간은 피한다. 사용 기법과 가정을 보고하고 유의성이 미래 수익을 보장한다고 표현하지 않는다.

### 8.3 필수 결과

```text
거래일·종목·고유 신호·episode·체결 수
총/순손익, 계좌 자산 경로, 비용과 회전율
승률과 정의, 평균 실현 이익/손실, 손익비, 기대값
MFE/MAE와 별도 정책 실현 성과
최대낙폭, 최악의 하루/episode, 연속 손실
노출·보유시간·동시 보유·테마 집중
부분체결·미체결·취소·지연·가격 불리함
시장·시간대·종목규모·자료품질별 성과
누락·미완결·모호 경로·표본 선정 한계
```

MDD는 계좌 순자산 경로에서 정의한다. 단일 종목 최고/최저 수익률로 대체하지 않는다. 익절·재진입을 잘게 쪼개 승률만 높아 보이게 만들지 말고 episode와 전체 계좌 성과를 함께 낸다.

## 9. EV: 현재 행동의 순가치를 비교

### 9.1 고정 정책의 기대값

정의된 정책에서 비용 전 평균 이익 W, 평균 손실 크기 L, 승리확률 p, 기대 비용 C라면 단순 모델은 다음과 같다.

```text
EV_net = p × W - (1-p) × L - C
```

이미 비용이 포함된 순손익 표본이라면 비용을 다시 빼지 않는다. 보합·미체결·여러 청산 결과가 있으면 이항 승패식 대신 실제 결과 분포를 사용한다.

### 9.2 행동별 비교

현재 상태 s와 행동 a에 대해 다음을 평가한다.

```text
V(s,a) = 지정한 미래 정책·기간에서의
         기대 순자산 변화 / 위험·실행 제약 정보

행동 집합: WAIT / ENTER / HOLD / ADD / REDUCE / EXIT / REENTER
```

ADD는 ‘앞으로 오를 확률이 높다’만으로 결정하지 않는다. 같은 출발 상태에서 **ADD 후 정책과 HOLD 후 정책**의 증가분 기대손익·비용·위험을 비교한다. 일부 매도 후 재증액도 동일하다.

보유 중 판단에서는 이미 지불한 매수 비용은 과거의 비용이다. 미래 행동 비교에 재청구하지 않되, 캠페인 전체 성과에는 원래 비용을 유지한다. 청산하면 앞으로 발생할 매도 비용과 남은 위험을 반영한다.

### 9.3 확률·불확실성 계약

```text
prediction_id / model_id / model_version
state_ref / as_of / action / policy_version
event_definition_id / horizon / evaluation_population
p_success / expected_net_pnl / expected_net_return
return_denominator / quantiles / tail_loss_estimate
calibration_report_id / training_cutoff
sample_support / independent_day_count
out_of_distribution_flags / uncertainty_flags
cost_model_id / execution_model_id
```

자료가 부족하면 확률·EV는 null이고 `INSUFFICIENT_EVIDENCE`다. 강한 점수를 임의로 85%로 바꾸지 않는다. 보정은 예측확률과 실제 빈도를 비교하는 과정이며, 보정에 쓰는 자료도 학습/최종 평가와 적절히 분리한다. [R3]

Brier score·log loss·확률 구간별 실제 빈도·표본수를 함께 볼 수 있다. 한 점수가 개선됐다고 확률 보정만 좋아졌다고 단정하지 않는다. 시장·시간대·정책별로 표본 부족 여부도 확인한다. [R3]

### 9.4 다른 행동의 결과를 얼마나 믿을 수 있는가

과거 시세에서 다른 매수·매도 경로를 시뮬레이션할 수 있지만, 내 주문이 가격을 바꿨을 결과까지 직접 관측한 것은 아니다. 특히 큰 노출·낮은 거래대금에서는 체결·시장 충격 가정에 의존한다.

행동가치에는 사용한 시뮬레이터와 거래 규모 지원 범위를 붙인다. 작은 주문으로 검증된 기대값을 수십 배 규모에도 동일하게 적용하지 않는다. 관측되지 않은 행동은 ‘실제 수익 확인’이 아니라 ‘가정하의 비교 결과’다.

## 10. 거래비용과 회계

### 10.1 기본 연구 프로파일

사용자가 정한 비용 가정을 그대로 명시한다.

```yaml
cost_model_id: user_conservative_023_v1
currency: KRW
buy_cost_rate: 0.00015       # 0.015%
sell_cost_rate: 0.00215      # 0.215%, 수수료·세금 합산 가정
same_notional_round_trip_rate: 0.00230
basis: user_selected_comparison_assumption
live_fee_schedule_verified: false
```

현재 확인한 키움 일반 주식 FAQ는 HTS·홈페이지 수수료 0.015%와 매도 시 세금 0.20%를 안내한다. 다만 거래 매체·주문 특성에 따라 수수료가 달라질 수 있다고도 명시한다. [R4] 이 연구 프로파일을 모든 계좌·상품·과거 시기의 공식 최대비용이라고 주장하지 않는다.

두 비교 방식을 분리할 수 있다.

- **동일 가정 비교:** 과거 전 구간에 사용자가 고른 비용을 적용해 전략 간 비교.
- **역사/실거래 재현:** 확인된 날짜·상품·시장·계좌별 비용표를 사용.

보고서에 어떤 방식을 썼는지 명시한다. 미수·신용 이자·기타 비용이 생기면 확인한 조건에 따라 별도 추가한다.

### 10.2 실제 체결금액별 계산

총매수 체결금액 B, 총매도 체결금액 S라면 위 프로파일의 기본 비용은 다음과 같다.

```text
explicit_cost = 0.00015 × B + 0.00215 × S
```

같은 가격에 1억 원어치 사고 1억 원어치 팔면 비용은 **230,000원**이다. 매도 가격·금액이 달라지면 정확한 비용은 최종 보유금액에 0.23% 한 번을 곱한 값과 다르다.

가격 수익률 g로 한 번 사고 전량 팔았을 때, 최초 매수 **명목금액** 대비 순손익률은 다음과 같다.

```text
r_net_on_buy_notional = (1+g) × (1-0.00215) - (1+0.00015)
```

따라서 가격 기준 손익분기 수익률은 약 **0.23050%**다. 실제 투자 현금 전체를 분모로 쓰면 수익률 분모에 매수 비용까지 포함한다. 화면·실험은 분모 정의를 표시한다. 이 계산은 슬리피지·추가 비용·원단위 처리 전의 수학 예시다.

### 10.3 분할과 회전을 구별

동일 가격·동일 총금액·순수 비례 비용을 가정하면 1억을 한 번에 사는 것과 2천만 원씩 다섯 번 사는 것의 **매수 수수료 합계는 같다**. 주문 횟수만큼 왕복 0.23%를 중복 차감하지 않는다.

반면 5천만 원을 팔고 다시 5천만 원을 매수하면 총 회전금액이 늘어 해당 체결들의 비용이 추가된다. 주문별 절사·최소수수료가 실제로 있다면 그 규칙을 따로 구현한다. 분할의 장단점은 가격·체결·시장 충격·회전과 함께 검증한다.

### 10.4 슬리피지 이중 계산 방지

실제/모의 체결가격에 스프레드·불리한 가격 이동·시장 충격을 반영했다면 동일 항목을 손익에서 또 빼지 않는다. 반대로 참조가격만 사용했다면 별도 명시한 실행 비용 모델을 적용한다.

```text
execution_price_policy: modeled_fill | observed_fill | reference_plus_cost
included_components[]
additional_cost_components[]
```

체결이 불확실한데 중간가격에서 전량 즉시 체결되는 기본값을 쓰지 않는다. 키움 안내도 시장가가 원하는 직전 가격과 다르게 체결될 수 있음을 설명한다. [R4]

### 10.5 원장

주문·체결 단위로 수량, 가격, 매수 비용, 매도 비용, 통화, 원단위 처리, 실제/추정 여부를 남긴다. 수익 실현 계산의 원가법은 기존 계좌 표시와 일치시키거나 차이를 설명한다.

포지션 PnL과 계좌 순자산 변화가 맞아야 한다. 현금·평가액·부채·누적 비용·실현손익을 이중 반영하지 않는다. 미결제 매도대금·주문가능금액·현재 순자산을 같은 값으로 취급하지 않는다. 브로커가 제공하는 상태를 각각 저장하고 매핑한다.

## 11. Position: 목표 노출과 분할 경로

### 11.1 단위

```text
E_t = 정의한 방식의 현재 계좌 순자산
V_i = 종목 i의 현재 평가금액
exposure_i = V_i / E_t
portfolio_gross_exposure = Σ abs(V_i) / E_t
```

초기 롱 전용 정책에서 음수 수량은 오류다. 분모 E_t가 0 이하·미확인·오래된 값이면 신규 위험을 확대하지 않는다. 100%=1.0배, 500%=5.0배 **명목 노출**이며 수익률·손실률이 아니다.

위험예산의 분모는 현재 순자산·세션 시작 순자산 등 별도 정책일 수 있다. 노출 분모와 섞지 말고 `equity_basis`와 시점을 기록한다.

### 11.2 목표와 실제의 차이

목표 평가액을 수량으로 바꿀 때 호가 단위·수량 단위·비용·주문가능금액을 반영한다. 계획 기준은 다음 관계다.

```text
effective_projected_qty
  = filled_position_qty
    + pending_buy_remaining_qty
    - pending_sell_remaining_qty

desired_delta_qty = target_qty - effective_projected_qty
```

이 식은 중복 의도를 줄이는 **계획용 근사**다. 매수·매도 미체결이 모두 체결된다고 위험을 낙관하면 안 된다. 실제 Risk는 ‘매수만 모두 체결’, ‘매도 미체결’ 등 불리한 상태도 검사한다. 취소 확인 전 주문은 계속 살아 있을 수 있다.

### 11.3 작은 차이에 계속 주문하지 않는다

목표 변화 최소 단위, 주문 갱신 주기, 같은 방향 중복 억제, 반대 의도 전환 절차를 둔다. 파라미터는 비용·체결 지연·전략 기간을 고려해 검증한다. 단, 보호 청산을 일반 재조정 대기시간 때문에 지연하지 않는다.

### 11.4 장기 연구 선택지

고정 비중, 단계형 증감, 조건부 목표 노출, 위험예산 기반 증감 등을 같은 검증 구간에서 비교한다. 완벽한 미래 확률을 안다고 가정한 최적 레버리지를 운영 기본값으로 쓰지 않는다.

주도주 정책과 비주도주 정책에 비중을 미리 서열화하지 않는다. 각 정책의 불확실성·순기대값·공통 위험·실행 가능성이 배분의 근거다.

## 12. Risk: 모델보다 우선하는 보호

### 12.1 위험의 네 기준

1. **최초 캠페인 자본 대비 손익:** 최초 진입부터 얼마나 벌거나 잃었는가.
2. **현재 순자산에서의 추가 손실:** 지금 보유를 유지하면 얼마를 더 잃을 수 있는가.
3. **최고 순자산 대비 반납:** 이미 만들어진 이익이 얼마나 줄어드는가.
4. **스트레스 손실:** 계획한 가격·시간에 청산이 안 되는 경우의 손실.

불타기가 이전 원금 기준으로 이익을 남기더라도 현재 순자산을 크게 잃을 수 있다. 평가이익·실현이익 모두 자산이며 공짜 위험예산으로 취급하지 않는다.

### 12.2 손절선과 위험예산의 수학

간단한 가격 모델에서는 `허용 손실 / 진입가와 청산 가정의 차이`로 수량 후보를 구할 수 있다. 그러나 가까운 보호선 하나만으로 수량이 무한히 커지지 않도록 노출·체결·스트레스·계좌 한도를 함께 적용한다.

현재가 P, 보유수량 q, 청산 가정가 S라면 현재 시점의 가격상 되돌림은 대략 `q × (P-S)`다. 여기에 추가 비용과 다른 포지션 위험을 반영한다. **이는 보호 가격에 체결된다는 조건부 예상값이며 실제 최대 손실 보장이 아니다.**

### 12.3 불타기 예시: 원금 보호와 현재 위험은 다르다

아래는 비용·세금을 제외한 계산 예시다.

```text
기존 10,000주 × 10,000원 = 100,000,000원
추가  5,000주 × 10,300원 =  51,500,000원
총원가                     151,500,000원
총수량                         15,000주
평균단가                       10,100원

현재가                         10,300원
계획 청산가                    10,150원
```

10,150원에서 전량 청산된다고 가정하면 원가 대비 이익은 **750,000원**이다. 하지만 현재가 10,300원에서 청산가까지 반납하는 평가액은 **2,250,000원**이다. ‘손절해도 원금은 남는다’와 ‘현재 위험이 작다’는 다른 판단이다. 실제 비용·청산 불리함을 추가하면 두 값은 더 달라진다.

### 12.4 강제 제약

```text
계좌별 live 허가·전략 허가
실제 주문가능금액·미수/신용 권한
단일 주문·종목·테마·계좌 총노출
거래·일일·누적 손실·최고 순자산 반납 한도
데이터 신선도·계좌 대사·주문 상태 확인
시장/상품/세션·거래정지·변동성 완화 상태
청산 가능성·스트레스 손실·보유기간
```

값은 승인된 위험 프로파일로 관리한다. 모델이 순기대값을 높게 평가하더라도 제한을 해제하지 않는다. 보호 제한은 검증된 코드와 계좌 상태로 실행한다.

### 12.5 미수·신용·주문가능금액

‘5배까지 연구 가능’과 실제 계좌에서 가능한 배수는 다르다. 종목·시장·계좌·증거금·주문가능금액·결제 조건을 브로커에서 확인한다. 평가이익이 생겼다는 이유로 같은 금액만큼 즉시 신용한도가 늘었다고 계산하지 않는다.

초기 신규 자동매매는 현금·소액 승인 범위다. 미수/신용 연구가 켜져도 실거래 권한은 별도 OFF다. 실거래 확대는 사용자의 별도 승인과 해당 규모의 체결·위험 검증이 필요하다.

### 12.6 Soft와 Hard

Soft 관찰은 ②의 사전 정의 정책을 검증해 적용한다. Hard 조건은 Soft timer·LLM 대기·새 확률·쿨다운보다 우선한다. Hard 발동 후 신규 ADD를 중지하고 미체결 증액을 안전하게 처리하며 청산을 시도한다.

하드 스톱이 있다고 가격 점프·거래 중단·상대 주문 부재의 손실이 사라지는 것은 아니다. 청산 의도·전송·접수·부분체결·완료를 각각 기록한다. 체결을 보장하지 않는다. [R4]

## 13. Capacity·Liquidity: 들어갈 때와 나올 때

### 13.1 거래대금은 출발점이지 보장서가 아니다

과거 1분에 100억이 거래되었다고 현재 큰 매도 주문을 같은 가격에 받아줄 매수호가가 남아 있다는 뜻은 아니다. 대금·호가·스프레드·주문 크기·시간·시장 상태를 함께 고려한다.

```text
historical_turnover_ratio
  = 내 계획 주문금액 / 최근 관측 구간 거래대금
```

이 값은 과거 거래와의 규모 비교값이다. 실제 주문 집행 구간의 시장 거래량 대비 체결 비중인 **실현 참여율**이나 체결 확률과 동일하지 않다. 주문금액과 비교하는 시간창을 맞추고 두 값을 이름부터 구분한다.

### 13.2 증액분뿐 아니라 전체 출구

2억을 추가하기 쉽더라도 이미 20억을 보유했다면 비상청산은 전체 보유량의 문제다. 새 주문과 현재+잠재 체결 보유량 모두에 대해 출구 위험을 평가한다.

미래 거래대금·호가 유지가 불확실하면 최근 평균을 그대로 확정치로 사용하지 않는다. 보수 추정·스트레스 시나리오·최대 집행시간·부분체결 가정을 사용하고 근거를 남긴다. 급변 시 대금 증가가 곧 유리한 청산을 뜻하지 않는다.

### 13.3 제한 결과

상한을 단순히 여러 숫자의 최솟값으로 끝내지 말고 최종 포트폴리오 상태를 재검사한다. 단일 종목 허용량이 작아져도 기존 보유·다른 테마와의 합산·미체결의 불리한 체결 조합이 계좌 한도를 넘을 수 있다.

```text
ALLOW / CAP / NO_NEW_RISK / REDUCE_ONLY / EXIT_REQUIRED / HALT_NEW_ORDERS
```

거래대금 감소만으로 보유를 버리는 전략 룰은 사용하지 않지만, 출구 위험이 승인된 한도를 넘으면 위험 모듈은 축소를 요구할 수 있다. 이때 사유는 대금 문턱 하나가 아니라 **보유 규모 대비 청산 위험**이다.

## 14. Replay와 체결 시뮬레이터

### 14.1 재생 순서

```text
원천 관측/수신 가능 이벤트
  → 특징·① 시점별 맥락
  → ② 행동 후보
  → EV/Position
  → Risk
  → 주문 의도
  → 지연·호가/시세·유동성 조건하의 체결
  → 비용·원장·다음 관측
```

순서를 바꾸어 한 봉의 미래 가격으로 신호를 만들고 같은 봉의 더 좋은 가격에 채우지 않는다. 체결가격·수량은 주문이 시장에 도착할 수 있는 시점 이후의 자료로 처리한다.

### 14.2 해상도별 체결 가정

분봉만 있으면 다음 적격 봉 가격·보수 비용 등 명시한 모델로 비교할 수 있다. 1초 자료가 있으면 다음 관측 이후 가능한 체결 가정을 사용한다. **‘고가/저가에 닿음=지정가 전량 체결’은 기본값이 아니다.**

호가가 없으면 큐 순서·잔량을 알 수 없다는 한계를 표시한다. 부분체결·미체결 시나리오를 비교하고, 보수 가정에서 기대값이 사라지는 정책은 실전 검증 우선순위를 낮추거나 보류한다.

### 14.3 시장제도·상태

세션별 주문 유형, 호가단위, 가격 제한, 변동성 완화·거래정지, 종목별 주문 가능 여부는 검증된 브로커/거래소 상태와 버전 규칙을 이용한다. 모든 과거 날짜에 현재 규칙을 그대로 적용하지 않는다. 미지원 구간은 거래 불가 또는 명시적 근사 상태다.

### 14.4 규모 민감도

작은 고정 금액과 큰 금액을 같은 즉시 전량 체결로 비교하지 않는다. 전략의 지원 주문 규모, 거래대금·호가 수준, 비용 민감도를 결과에 함께 남긴다. 시장 충격을 알 수 없는 규모는 `CAPACITY_UNVERIFIED`다.

## 15. Execution: 주문 의도에서 실제 체결까지

### 15.1 단일 주문 책임자

계좌·종목의 주문은 하나의 조정자가 소유한다. ②·LLM·개별 전략 worker가 증권사 주문 API를 직접 호출하지 않는다. 실거래 자격증명은 승인된 실행 경로에서만 읽는다.

새 문서를 이유로 기존 주문 기능을 다시 작성하지 않는다. 기존 기능의 멱등성·대사·권한이 충분하면 이를 어댑터로 재사용한다. 부족한 부분만 단계적으로 보완한다.

### 15.2 주문 의도 계약

```text
intent_id / decision_id / idempotency_key
run_id / execution_mode / account_ref
security_id / venue / session
policy_id / policy_version / model_id
as_of / expires_at
side / target_qty_or_delta_qty
order_type / limit_price / urgency
risk_approval_id / risk_snapshot_ref
position_version / order_ledger_version
reason_codes / evidence_refs
```

실제 계좌번호·키를 분석 문서·프롬프트·로그에 노출하지 않는다. `account_ref`는 내부 참조다. 식별 키는 동일 판단의 재시도와 새로운 판단을 구분한다.

### 15.3 전송 직전 재검사

신호 생성과 주문 전송 사이에 가격·잔고·미체결·계좌 권한이 바뀔 수 있다. 전송 직전에 만료·거래상태·자료 신선도·수량·금액·Risk 승인 유효성·현재 포지션 버전을 재검사한다.

낡은 snapshot으로 얻은 승인이라면 재평가한다. 전략 확신도만 다시 확인하고 계좌 상태를 생략하지 않는다.

### 15.4 상태 머신

```text
CREATED → RISK_APPROVED → SUBMITTING → ACKNOWLEDGED
                                  ├→ REJECTED
                                  └→ UNKNOWN
ACKNOWLEDGED → PARTIALLY_FILLED → FILLED
            → CANCEL_REQUESTED → CANCELLED / 추가 체결 확인
            → EXPIRED 또는 지원되는 종료 상태
```

전송 timeout은 주문 실패 확정이 아니다. 브로커 접수 여부를 조회·대사하고, 확인 없이 같은 주문을 다시 보내지 않는다. API가 자체 멱등성을 지원하지 않으면 로컬 의도/브로커 주문번호 매핑과 조회 기반 복구를 구현한다.

취소 요청 중에도 체결이 올 수 있다. `CANCEL_REQUESTED`를 즉시 미체결 0으로 바꾸지 않는다. 지연·중복·순서가 바뀐 체결 이벤트를 실제 체결 ID와 원장 규칙으로 처리한다.

### 15.5 재시작과 계좌 대사

시작 시 로컬 원장, 브로커 보유, 미체결 주문, 최근 체결, 주문가능금액을 대조한다. 차이가 있으면 신규 위험 확대를 막고 이유를 표시한다. 프로세스가 재시작됐다고 이전 주문을 모두 없던 것으로 간주하지 않는다.

수동 주문이 들어오면 기존 계좌 변화를 받아들여 원장에 반영하고 전략 목표를 재평가한다. 자동 정책이 수동 청산 직후 즉시 원래 목표로 재매수하지 않도록 사용자 일시정지·소유권 정책을 둔다.

### 15.6 비상정지의 의미

`신규 진입 중지`, `미체결 신규매수 취소`, `감액만 허용`, `전량 청산 시도`는 다른 동작이다. 하나의 불명확한 Kill Switch로 감추지 않는다.

기본 비상정지는 신규 위험 확대를 막되 기존 보호·대사는 유지한다. 모든 연결이 끊겼을 때 실제 청산을 보장하지 않는다. 사용자에게 **주문이 확인되지 않음/잔고 확인 필요**를 명확히 알리고 복구 절차를 제공한다.

### 15.7 브로커 능력 확인

현재 키움 연동 방식이 REST·OpenAPI+ 중 무엇인지, 주문·취소·정정·체결 통보·조회·모의환경·KRX/NXT·주문유형·호출 제한을 실제 공식 문서와 계좌 설정에서 확인한다. 이 문서의 추상 기능을 모두 지원한다고 추측하지 않는다.

기존 호출 제한 관리자를 재사용한다. 시세 수집·계좌 보호·주문 대사가 백필·대규모 연구 때문에 지연되지 않게 우선순위를 둔다.

## 16. 여러 전략이 같은 종목을 다룰 때

초기에는 하나의 주도주 돌파 정책만 사용한다. 나중에 추세 정책과 스캘핑 정책을 동시에 쓰더라도 계좌·종목 단위의 최종 목표를 하나로 합성한다.

상반된 매수·매도 의도를 그대로 각각 시장에 내지 않는다. 전략별 가상 기여와 실제 순주문·비용을 기록한다. 내부 상쇄가 있었다면 실제 체결이 발생한 것처럼 거래량·수수료·수익을 생성하지 않는다.

동일 테마 여러 종목의 기회는 독립하지 않을 수 있으므로 공통 위험을 합산한다. 전략별 모의 자금이 각각 계좌 전액을 사용할 수 있는 것처럼 합산 성과를 보고하지 않는다.

## 17. 모의 검증과 실전 승격

| 단계 | 확인하는 것 | 확인했다고 말할 수 없는 것 |
|---|---|---|
| 과거 재생 | 정의된 가정하의 정책 성과·회계·누출 | 당시 실제 주문 체결 |
| LIVE_SHADOW | 실제 수신시각의 신호·계산·품질·지연 | 실행 가능한 최종 순수익 |
| 내부 Paper | 실시간 자료+체결모델로 가상 원장 | 실제 시장 충격 |
| 증권사 모의 | 지원 범위에서 API 주문·접수·체결 연동 | 실계좌와 동일한 체결·세금·신용 |
| 소액 실계좌 | 해당 규모의 실제 비용·체결·운영 | 더 큰 규모·5배 노출의 동일 성과 |
| 점진 확대 | 승인된 다음 규모의 성과·위험 | 미래 수익 보장 |

증권사 모의가 선택한 API·상품을 지원하는지 먼저 확인한다. 미지원이면 내부 Paper를 만들 수 있으나 증권사 모의 검증을 통과했다고 보고하지 않는다.

승격 조건은 실험 전에 정한다. 최소 관찰·분산된 날짜/상황·순기대값 불확실성·낙폭·체결 성능·회귀 테스트·장애 대응 등을 포함한다. 단일 주간 수익이 높다는 이유로 자동 승격하지 않는다.

실거래는 별도 사용자 승인·정확한 계좌·현금 한도·정책 버전이 필요하다. 이 문서를 받은 Codex가 실제 주문을 실행할 권한을 얻는 것은 아니다.

## 18. 매일 갱신과 모델 재학습

### 18.1 ‘매일 학습’의 분해

```text
오늘 수집·정정 확정
  → 당일 특징과 관측 상태 확정
  → 관찰기간이 끝난 결과만 생성
  → 패턴·계좌·실행 통계 갱신
  → drift·자료 품질·성능 점검
  → 필요하고 지원되는 경우 후보 모델 훈련
  → 기존 운영 모델과 별도 검증
  → 승인된 경우에만 배포
```

RAG 인덱스 업데이트, DB append, 고정 모델로 오늘 확률 계산은 가중치 학습과 다르다. 미래 h일 결과가 필요한 사례는 오늘 장 마감만으로 정답이 되지 않는다.

### 18.2 증분 학습과 배치 학습

증분 학습 지원은 알고리즘마다 다르다. scikit-learn의 `partial_fit` 지원 모델처럼 명시적 능력을 확인해야 한다. [R5]

```text
trainer_capabilities:
  supports_incremental_update
  requires_replay_sample
  supports_feature_schema_change
  supports_new_target_classes
  batch_training_supported
```

새 하루 데이터만 더해도 되는 모델, 일정 창을 다시 학습해야 하는 모델, 구조가 바뀌면 초기화해야 하는 모델을 구별한다. warm-start나 트리 추가를 과거 전체 재학습과 항상 동일하다고 취급하지 않는다.

### 18.3 주기보다 조건

3개월·6개월은 의무 주기가 아니다. 특징·라벨·정책 변경, 보정 악화, 데이터 분포 변화, 새로운 자료, 누적 계산 오차·모델 한계가 재검토 계기다. 반대로 후보가 계속 기존 모델보다 나쁘면 기존 모델을 유지할 수 있다.

최근 자료에 높은 가중치를 주는 방법도 연구 대상이다. ‘최근이 항상 더 중요’나 ‘5년 자료면 모든 미래 국면 포함’을 고정하지 않는다. 과거 드문 국면의 기억과 현재 적합성을 별도 평가한다.

### 18.4 온라인 후보의 평가 순서

후보 온라인 모델도 새 표본의 결과를 배우기 전에 그 표본에 대한 예측을 기록한다. 결과를 본 뒤 바뀐 모델로 같은 시점 예측을 다시 써서 성과를 계산하지 않는다.

동일 데이터셋 해시·훈련 cutoff·가중치·시드·패키지 버전을 기록하고 모델 파일 checksum을 저장한다. 모델 교체 시 과거 결정에 연결된 모델 ID를 덮어쓰지 않는다.

운영 모델과 후보 모델은 동시에 같은 입력을 관찰할 수 있지만, 후보의 제안이 실제 원장을 바꾸면 안 된다.

값이 null이면 0 위험을 뜻하지 않는다. 필요한 검사 항목이 미확인인 상태에서 거래를 승인하지 않는다. 위험 감소 행동의 가능 여부는 잔고·세션·권한을 확인한 별도 보호 정책으로 처리한다.

## 21. 자원·배치·재개

초기 백필·특징 재계산·정책 탐색은 무거울 수 있지만, 장중에는 소수 후보의 현재 상태만 처리한다. 새로운 특징·모델을 도입하면 과거 재계산이 다시 필요할 수 있으므로 ‘초기에 한 번이면 영원히 종료’라고 설계하지 않는다.

파일·DB를 날짜·자료 버전·종목 범위로 나누고 필요한 부분을 읽는다. 모든 1초 기록을 매번 RAM에 올리지 않는다. 지원 알고리즘의 out-of-core 처리를 활용할 수 있으나 모든 모델이 외부 메모리 학습을 지원하는 것은 아니다. [R5]

실험은 입력 구간·결과 저장 단위별 체크포인트로 중단·재개한다. 같은 결과를 중복 집계하지 않도록 실행 ID와 데이터 버전을 키로 쓴다. 배치가 중단되어도 실시간 원장·시세 수집에 영향을 주지 않는다.

현재 장비에서 표본 실험의 CPU·메모리·스왑·I/O·지연을 측정하고 병목을 먼저 확인한다. 새 PC·특정 GPU·유료 API를 이 명세의 선행 조건으로 두지 않는다. ①의 로컬 LLM·Mac 사용자 제어를 유지한다.

## 22. 보안과 변경 통제

뉴스·LLM 응답·모델 산출물은 외부 입력이다. 셸·SQL·임의 주문 명령으로 실행하지 않는다. 모델은 허용된 스키마·정책 ID만 반환하며 최종 Risk가 검증한다.

원본·과거 판단·체결·계좌 대사 이력은 모델이 수정할 수 없다. 키·토큰·HMAC·계좌 비밀을 프롬프트·문서·테스트에 넣지 않는다. 라이브 자격증명과 모의 설정을 분리하고 잘못된 환경 연결을 감지한다.

실거래·미수·위험 한도·네트워크 개방·유료 결제·원본 대량 삭제는 별도 명시적 승인 없이는 실행하지 않는다. 학습 파라미터 검색 공간에 이 권한 키들을 넣지 않는다.

## 23. 최소 코드 구조

기존 연구/백테스트/주문 모듈을 우선한다. 아래는 책임 배치 예시다.

```text
research/
  datasets.py        # 범위·시점·분할
  labels.py          # 결과·완결성
  experiments.py     # 가설·실험 기록
  evaluation.py      # 순손익·위험·품질
  training.py        # 이후 후보 학습
replay/
  runner.py          # 시간순 재생
  fills.py           # 체결 가정
  ledger.py          # 기존 회계 재사용
trading_runtime/
  action_value.py    # 이후 EV 추론
  allocation.py      # 목표 노출
  risk.py            # 최종 보호
  execution.py       # 기존 주문 어댑터
  reconciliation.py # 기존 대사 재사용
```

첫 버전에서는 필요한 파일만 만든다. 전달만 하는 엔진·추상 factory·서비스 수십 개를 추가하지 않는다. 복잡성을 줄여도 시점·원장·권한의 경계는 생략하지 않는다.

## 24. 단계별 완료 기준

### R0 — 감사와 공통 계약

자료 범위, 원본 의미, 기존 연구·계좌·주문·수수료 코드를 확인한다.

**완료:** 작은 실제 구간 또는 명시한 fixture로 금액·시간·자료 품질의 검증 가능성이 확인되고 필요한 계약이 매핑된다.

### R1 — 재현 가능한 돌파 재생

한 기준선, 비용, 단순하지만 명시적인 체결 모델, 원장·결과 기록을 만든다.

**완료:** 같은 입력·버전·시드로 결과가 재현되고 수량·현금·비용 대사가 맞는다. 같은 봉 내 순서 모호·누락·상태 정지를 처리한다.

### R2 — 제한된 탐색·검증

거래대금·시간·확인 지연 등의 소수 가설을 시간순 비교한다.

**완료:** 시도 수·검증 구간·실패 결과·표본 범위·비용 민감도·불확실성을 보고한다. 승률·MFE만으로 성공 선언하지 않는다.

### R3 — 행동 EV·분할 정책

ADD/REDUCE/REENTER와 목표 노출 정책을 추가하고 ②에 결과를 제공한다.

**완료:** 서로 다른 행동의 비교 가정, 계좌 위험, 비용·회전·출구 제한이 일관되게 계산된다.

### R4 — 후보 학습·Shadow·Paper

학습 능력 확인, 후보 모델 기록, 전진 예측, 내부 Paper 또는 지원 확인된 브로커 모의를 연결한다.

**완료:** 과거와 실시간 차이, 데이터 지연, 모의 체결 한계, 실제 적용 안 된 후보 모델이 구분된다. 자동 live 승격 없음.

### R5 — 별도 승인된 소액 현금 실거래

사용자의 정확한 계좌·한도·정책 승인 후 실행·대사·정지·재시작을 검증한다.

**완료:** 실제 체결·비용·계좌 차이·장애 처리 결과를 보고한다. 더 큰 규모 성과로 일반화하지 않는다.

### R6 — 선택 확장

스캘핑·비주도주·새 모델·규모 확대·미수 연구를 개별 실행한다.

**완료:** 해당 자료·정책·규모의 별도 근거와 승인. 기존 위험 제한·원장·검증 분리 유지.
