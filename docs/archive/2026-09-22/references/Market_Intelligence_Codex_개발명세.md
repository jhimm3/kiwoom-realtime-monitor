# Market Intelligence — Codex 개발 명세

> 버전: 1.0 · 작성일: 2026-09-20  
> 대상: 기존 키움모니터와 연결되는 독립형 정보 분석 서비스  
> 핵심: **거래대금 Top30~40 중심 과거 뉴스 수집 → 사건·테마·종목 기억 구축 → 로컬 LLM 해석 → 날짜별 판단·복기 화면**  
> 문서 성격: 사용자와의 설계를 구현 가능한 요구사항으로 정리한 명세. 아래 모듈명·API·테이블명은 **새 구현의 제안 계약**이며, 기존 코드에 실제로 존재한다는 뜻이 아니다.

## 0. Codex에게 먼저 전달할 실행 지시

이 문서를 기준으로 개발하라. 전체 기능을 한 번에 구현하지 말고 **Phase 0과 Phase 1을 첫 작업 범위**로 삼아라. 기존 저장소의 지침·테스트·수집기·NAS ingest 경로·DB 구조·진행 중인 변경을 먼저 조사한 다음, 재사용할 부분과 새로 만들 부분을 구분하라.

- 기존 키움모니터의 실시간 조회순위, 시세 수집, 뉴스창, 수동 테마, 주문 기능을 다시 만들거나 임의로 변경하지 않는다.
- 새 기능은 독립 프로세스/서비스로 운영한다. 별도 서비스라는 이유로 원본 뉴스·시세를 복제하거나 **별도 운영 DB·백필 DB를 새로 만들지 않는다.** 기존 NAS 저장·검증·계산 경로를 재사용한다.
- 기존 기능을 실행 시점에 통째로 import해서 GUI 초기화나 실시간 수집을 유발하지 않는다. 기존 내부 API 또는 부작용 없는 공용 모듈로 연결한다.
- 첫 뉴스 수집 범위는 **KOSPI·KOSDAQ 통합 일별 거래대금 Top40**이다. Top30으로 바꿀 수 있게 한다. 급등주·상한가·연관종목을 자동으로 더하는 기능은 기본 OFF다.
- 이미 `candidate_days` 등으로 Top50 후보가 확정·저장되어 있다면 원본 계획을 덮어쓰지 않는다. 기존 순위 필드와 범위를 확인하여 뉴스 대상만 Top40으로 제한하는 새 계획 버전을 만든다. 해당 구조의 존재 자체는 코드에서 확인한다.
- 과거 뉴스와 전종목 일봉이 이미 완비되었다고 가정하지 않는다. 확인되지 않은 API 경로, 인증 방식, 과거 제공 범위, 종목코드를 추측해 구현하지 않는다.
- 새 엔진에는 Gemini 등 외부 LLM 의존성을 두지 않는다. 기존 앱의 Gemini 기능은 별개이므로 무단 삭제하지 않는다. 로컬 LLM이 없으면 `분석 대기`가 정상 동작이다.
- 수집·저장·재개가 검증되기 전에 수년치 전체 실행, 대규모 LLM 분석, 자동 테마 확정을 시작하지 않는다.
- 최종 보고에는 수정 파일, 실행 명령, 실제 수행한 테스트와 결과, 미실행 항목, 데이터 커버리지와 남은 한계를 구분하여 적는다.

**첫 완료 목표:** 작은 과거 구간의 Top40 후보를 만들거나 가져오고, 뉴스 수집 계획을 실행·중단·재개하여 기존 NAS 경로에 중복 없이 저장하며, 수집된 기사와 누락 상태를 화면에서 확인한다. LLM 없이도 이 단계는 완결되어야 한다.

## 1. 제품의 목적과 경계

### 1.1 무엇을 만드는가

단순한 ‘기사별 호재/악재 점수기’가 아니라, 뉴스와 객관적 시장 데이터를 연결해 **한국시장의 배경, 관심 테마, 종목 재료, 과거 시장 기억**을 제공하는 정보 시스템을 만든다.

사용자가 확인할 핵심 질문은 다음과 같다.

| 질문 | 필요한 결과 |
|---|---|
| 오늘 시장은 무엇을 중요하게 받아들이는가? | 주요 사건, 시장 환경, 반대 근거, 불확실성 |
| 어떤 테마가 형성·유지·재활성화되고 있는가? | 근거가 있는 테마 후보와 구성종목 관계 |
| 어떤 종목에 살아 있는 재료가 있는가? | 사건 상태와 후속 뉴스, 관측된 시장 반응 |
| 며칠 전 강했던 종목의 연속성은 어떤가? | 일봉·거래대금 기반 Stock Memory |
| AI는 그날 무엇을 판단했고 언제 바꿨는가? | 변경 불가능한 시점별 판단과 변경 이유 |
| 그 판단은 실제로 도움이 되었는가? | 정의가 명확한 사후 평가와 실패 사례 |

‘돈이 어디로 몰리는가’는 제품의 해석 관점이다. **거래대금 증가만으로 순자금 유입이나 자산 간 실제 자금 이동이 입증됐다고 표현하지 않는다.** 가격·거래대금은 시장 관심과 반응의 관측치로 사용한다.

### 1.2 이번 서비스가 하지 않는 일

실시간 틱 분석, 초단위 진입 판단, 박스 돌파 주문, 손절·익절·불타기, 포지션 관리, 자동매매는 기존/후속 타점·실행 엔진의 영역이다. 이 문서를 이유로 거래 권한을 추가하지 않는다.

LLM 기초모델의 사전학습이나 파인튜닝도 초기 범위가 아니다. **과거 사례를 DB에 저장하고 검색해 제공하는 것과 모델 가중치를 훈련하는 것은 다르다.** 화면에서도 DB 구축 진행률을 ‘모델 학습률’이라고 표시하지 않는다.

### 1.3 이전 설계와의 관계

기존 `NAS_News_Engine_Design.md`의 수집·중복 처리·장기보관 원칙은 재사용한다. 해당 문서의 ‘Gemini 유지’는 기존 앱에 대한 설명으로 남기되, **이번 새 분석 서비스의 기본 실행 경로는 로컬 LLM**으로 변경한다.

이 문서는 기존 프로젝트 전체 설계를 대체하지 않는다. 충돌이 생기면 최신 사용자 제약과 실제 코드의 안전한 통합 경로를 우선하고, 차이를 짧은 결정 기록에 남긴다. 이 문서 작성 과정에서 실제 NAS DB나 최신 레포 전체를 감사한 것은 아니다.

## 2. 장비와 운영 원칙

| 위치 | 역할 | 제약 |
|---|---|---|
| Synology DS920+ | 수집 계획, 원본 저장, 중복 검사, 가벼운 계산, 작업 큐, API·대시보드 | 기존 서비스와 공존. 로컬 LLM·대규모 임베딩 실행을 기본으로 하지 않음 |
| Mac mini M4, 통합 메모리 24GB | 필요할 때 로컬 LLM 추론 | 사용자의 실제 메인 컴퓨터. 전용 서버나 24시간 가동을 가정하지 않음 |
| 기존 키움모니터/시세 수집 경로 | 시장·종목 시세와 장중 요약 데이터 공급, 결과 소비 | 기존 실시간 우선순위·호출 제한 보존 |

NAS 메모리 증설 여부와 여유 자원은 실행 환경에서 확인한다. 기존 대화의 메모리 수치만으로 신규 서비스의 처리량을 보장하지 않는다.

권장 초기 배치는 아래와 같다. 도식은 역할 구분이며 각각을 별도 마이크로서비스로 쪼개라는 뜻이 아니다.

```text
뉴스 소스 / 과거 거래대금·일봉 소스
                |
        기존 NAS ingest·검증 경로
                |
        기존 PostgreSQL / 원본 보관
                |
     Market Intelligence 서비스
     - 수집 계획·재개
     - 사건·테마·기억
     - 분석 큐·판단 이력
     - 내부 API·웹 화면
                ^
                | 인증된 내부 API로 작업 요청·결과 반환
                |
     Mac의 가벼운 LLM worker
                |
     Mac 네이티브 로컬 런타임
     (초기 후보: Ollama)
                |
        로컬에 내려받은 모델

기존 주식 앱 ← 읽기 전용 Intelligence API
```

Mac worker가 NAS에서 작업을 가져가고 로컬 LLM에 요청하는 방식을 우선한다. 이렇게 하면 NAS가 Mac의 원시 LLM 포트에 직접 접근할 필요가 없다. Mac이 꺼지면 큐에 남고, NAS의 수집은 계속된다.

## 3. 데이터 해상도와 역할 분리

### 3.1 과거 구축에 필요한 최소 데이터

**과거 분석의 종목 가격 데이터는 일봉 중심**으로 시작한다. 단, ‘Top40 종목의 일봉’과 ‘Top40을 결정하기 위한 전체 시장의 거래대금 정보’는 별개다.

| 데이터 | 초기 필요성 | 용도 |
|---|---|---|
| 날짜별 전체 시장 거래대금 순위 또는 거래대금 스냅샷 | 필수 | 그 날짜의 Top40 선정 |
| 선정 종목의 과거 일봉 OHLCV·정확한 거래대금 | 필수 | 종목 기억, 반응 관측, 연속성 연구 |
| 종목 마스터·이름 변경 이력·상장 상태 | 필수 | 과거 종목 검색과 생존편향 관리 |
| 뉴스 제목·URL·출처·공개시각 | 필수 | 검색·사건 연결·시간순 처리 |
| 뉴스 원문 | 확보 가능한 범위에서 우선 | 근거 추출. 미확보와 확보를 구분 |
| KOSPI·KOSDAQ 일별 지표 | 시황 분석 단계의 기본 입력 | 시장 배경과 상대 반응 |
| 해외지수·환율·금리·유가 등 시계열 | 단계적 추가 | 거시 환경의 사실 입력 |
| 당시 시총·유통주식 정보·수급 | 선택 | 상대 거래대금과 맥락 보완 |
| 과거 분봉·틱 | 초기 불필요 | 없으면 장중 선후관계를 검증하지 않음 |

시총·유통주식·종목 마스터는 **그 시점에 해당하는 값**이어야 한다. 현재 시총으로 과거 거래대금 강도를 계산하지 않는다.

전체 종목의 수년치 상세 일봉을 반드시 모두 새로 받아야 시작할 수 있는 것은 아니다. 공급자가 날짜별 공식 Top40 이상 순위를 제공하면 이를 재사용하고, 필요한 종목의 상세 이력만 추가해도 된다. 반대로 일부 관심종목만 저장된 일봉으로 만든 순위를 ‘시장 전체 Top40’이라고 부르지 않는다.

### 3.2 현재 운영에서만 추가하는 장중 요약

현재 등락률, 누적 거래대금, 같은 시간대 대비 거래대금 변화, 상승/하락 종목 수, 테마 구성종목 동조 등을 기존 경로에서 전달받는다. 각 값에는 관측시각과 거래 세션 범위를 붙인다.

Market Intelligence가 원본 틱·1초 데이터를 중복 수집하지 않는다. 장중 자료가 없으면 마지막 완결 일봉과 최신 뉴스만으로 판단하고, 화면에 `장중 확인 전`을 표시한다. 일봉만으로 ‘09:07 발견, 09:11 급등’ 같은 분 단위 선행 성능을 만들어내지 않는다.

## 4. 과거 관심종목: Historical Hot Universe

### 4.1 기본 정책

```yaml
universe:
  policy_id: turnover_top40_v1
  top_n: 40                         # 30으로 변경 가능
  market_scope: combined_kospi_kosdaq
  selection_basis: finalized_daily_turnover
  venue_scope: krx                  # 실제 공급자 정의를 확인 후 고정
  session_scope: regular            # 공급자 자료가 이 범위를 지원할 때만 사용
  instrument_scope: listed_equities
  include_preferred_shares: true
  include_etf_etn: false
  include_spac: false
  additional_candidates_enabled: false
  additional_candidate_limit: 0
```

이는 새 작업의 초기 기본값이다. 기존 수집 자료의 세션 범위가 다르면 원자료를 위 설정과 같다고 가장하지 않고 별도의 `scope`로 기록한다. KOSPI 40개 + KOSDAQ 40개가 아니라 **통합 40개**다.

전일·최근 강세주 기억은 Stock Memory에서 유지한다. 그것이 곧 매일 뉴스 대상 수를 자동으로 수백 종목까지 늘리라는 뜻은 아니다. 추가 수집은 예산이 있는 명시적 옵션으로만 수행한다.

### 4.2 선정 규칙

1. 거래일과 당시 상장 주식 집합 또는 신뢰할 수 있는 전체 순위 자료를 확인한다.
2. 대상 상품·시장·거래 세션 범위에 맞춘다. 같은 종목의 KRX·NXT·통합 자료를 중복 합산하지 않는다.
3. **실제 거래대금** 내림차순으로 정렬한다. 동률은 안정적인 종목 식별자로 정렬해 결과를 재현한다.
4. 상위 N개와 원래 거래대금·순위·선정 근거·자료 버전을 저장한다.
5. 공급자 공식 순위와 계산 순위가 있으면 표본 날짜에서 대조한다.

`종가 × 거래량`은 정확한 거래대금이 아니다. 이를 공식 Top40 복원에 조용히 대체하지 않는다. 대체값밖에 없다면 `approximate_turnover`로 구분하고 공식 순위와 분리한다.

일별 거래대금 상위는 관심종목의 **대리 기준**이다. 과거 키움 실시간 ‘조회순위’를 복원했다고 표시하지 않는다.

### 4.3 커버리지 검사

`complete_market / official_rank / partial_universe / unknown`을 기록한다. 일부 종목만 포함된 데이터에서는 `partial_universe`를 유지하고 시장 전체 순위 생성의 정식 완료를 허용하지 않는다. 공식 순위의 조회 상한이 20위라면 Top40 확보가 완료된 것이 아니다.

현재 살아 있는 종목만 사용하면 과거 상장폐지·합병 종목이 빠질 수 있다. 거래일별 상장 집합을 확보하지 못한 기간은 한계를 기록한다. 종목코드는 문자열로 보관하고, 코드 변경·재사용·회사명 변경을 고려해 내부 식별자를 분리한다.

### 4.4 저장할 후보 정보

```text
plan_id / plan_version
trade_date / selection_available_at
security_id / code_as_of_date / name_as_of_date
turnover / turnover_currency / turnover_unit
turnover_rank / rank_source / coverage_status
venue_scope / session_scope / instrument_scope
selection_reason / raw_snapshot_ref
```

완결 일별 순위는 **그날 종가가 확정되기 전의 장전 후보 선정 근거로 사용할 수 없다.** `selection_available_at`은 날짜만 보고 임의로 장전으로 지정하지 않는다.

## 5. 뉴스 수집 범위와 제공 가능성 확인

### 5.1 첫 실행 구간

장기 목표는 2019년부터, 가능하면 그 이전까지의 자료다. 그러나 먼저 서로 다른 연도의 소규모 구간에서 공급 가능성을 확인한다. 제공 여부가 확인된 소스만 실제 계획에 포함한다.

초기 실행은 한 번의 **유한한 백필 작업**이다. 지정 구간을 처리하면 종료한다. 이를 이유로 기존 실시간 수집기에 반복 작업을 자동 등록하지 않는다.

```yaml
backfill:
  requested_start_date: "2019-01-01"
  requested_end: latest_completed_session
  pilot_mode: true
  pilot_max_trade_dates: 5
  lookback_sessions: 10
  followup_news_sessions: 0
  source_concurrency: 1
  body_fetch_enabled: true
  llm_analysis_enabled: false
  auto_expand_related_stocks: false
```

`pilot_mode`에서는 전체 기간을 실제로 실행하지 않는다. 선택된 5개 거래일은 최근 날짜에만 몰지 않고 과거 제공 가능성을 확인하는 표본으로 정한다. 표본 수·기간·뉴스량은 설정 가능하다.

### 5.2 뉴스 기간 합치기

날짜 D의 Top40에 A가 들어왔다면 기본 수집 창은 **D 이전 10거래일부터 D 종료까지**다. ‘10거래일’을 거래소 달력으로 계산한 다음, 뉴스 검색에는 그 사이 주말·휴일을 포함한 달력 날짜 범위를 사용한다.

반복 선정된 A에 대해 매번 같은 기간을 검색하지 않는다. `종목 + 공급자 + 검색전략 버전`별 수집 완료 구간을 관리하고, 겹치는 요청을 합친 뒤 **누락 구간만** 실행한다. 다만 기간 중간의 실패를 감추는 단일 `최소일~최대일` 표시는 금지한다.

수집 윈도우와 그 윈도우를 요구한 후보 날짜의 연결은 유지한다. 이 때문에 날짜별 Top40과 실제 하루에 검색하는 고유 종목 수는 같지 않을 수 있다. UI에서 선정 종목 수, 검색 작업 수, 실제 기사 수를 분리한다.

후속 뉴스 수집은 기본 OFF로 두되, 나중에 D+5 등으로 확장할 수 있다. 사후 평가용 일봉 D+1·3·5·10 수집과 후속 뉴스 수집 옵션은 별개다.

### 5.3 뉴스 소스의 계약

수집 어댑터는 지원 능력을 명시해야 한다.

```text
provider_id
supports_date_range / supports_historical_search
provides_publisher_timestamp / provides_body
pagination_method / result_cap
oldest_verified_date / verification_evidence
permission_status / permitted_storage_scope
rate_limit_policy / last_verified_at
```

네이버 **공식 뉴스 검색 API**는 문서상 `query`, `display`, `start`, `sort`를 제공하며 `display` 최대 100, `start` 최대 1000이다. 공식 문서에 임의 날짜 범위 검색 파라미터는 열거되어 있지 않다. 따라서 이 API만으로 2019년 전체 뉴스 백필이 가능하다고 구현하지 않는다. 응답의 `description`도 원문 전체가 아니다. [S1]

네이버 웹 날짜검색이나 네이버증권 내부 엔드포인트는 공식 검색 API와 별개다. 과거 대화에서 일부 페이지가 조회되었다는 사실만으로 수년 전체 제공·완전 수집·장기 인터페이스 안정성을 가정하지 않는다. 기존 수집 코드, 실제 응답, 이용 조건을 확인하여 검증된 경로만 추가한다.

DART나 다른 원문 소스는 기존 프로젝트에서 연결·권한·보관 범위가 확인된 경우에만 재사용한다. 검색결과 접근 가능성이 기사 원문 재배포 허용을 의미하지 않는다. 유료 계약·자료 구매를 자동으로 진행하지 않는다.

### 5.4 넓은 시황뉴스와 종목뉴스

종목명 검색만으로는 기업 이름이 없는 정책·산업·해외시장 사건을 놓칠 수 있다. 따라서 구조상 아래 두 입력을 구분한다.

- `stock_targeted`: Top40 중심으로 깊게 수집한다. 첫 단계의 필수 범위다.
- `market_context`: 기존 시장·경제·산업 뉴스 피드를 재사용한다. 과거 제공 범위를 확인한 후 별도 예산으로 확장한다.

시장뉴스가 확보되지 않은 기간을 ‘전체 시황까지 학습 완료’로 표시하지 않는다. 첫 버전부터 과거 모든 경제뉴스를 무제한 수집하도록 범위를 넓히지 않는다.

### 5.5 검색·원문 품질

당시 회사명과 유효한 별칭을 사용한다. 일반 단어와 겹치는 이름, 우선주, 합병 전후 회사명은 코드·본문·회사 식별자로 검증한다. 검색에 걸렸다고 관련 종목으로 확정하지 않는다.

검색결과의 날짜, 원문 최초 게시시각, 수정시각, 네이버 제공시각은 다를 수 있다. 특히 공식 API의 `pubDate` 의미를 원문 최초 게시시각과 무조건 동일시하지 않는다. [S1]

원문을 얻지 못하면 `metadata_only` 또는 `snippet_only`로 보관한다. LLM이 링크만 받고 원문을 읽었다고 간주하거나, 비어 있는 원문을 생성해서 채우지 않는다.

## 6. 수집 작업의 안정성과 기존 시스템 보호

### 6.1 기본 흐름

```text
자료·권한 확인
  → 날짜별 Top40 후보 계획
  → 종목별 뉴스 기간 병합
  → 미수집 구간 작업 생성
  → 검색결과 메타데이터 저장
  → 중복 확인
  → 허용된 원문만 가져오기
  → 기존 ingest로 정규화·저장
  → 커버리지·체크포인트 갱신
  → 유한한 계획 종료
```

원문 수집과 LLM 분석은 별도 상태다. Mac이 꺼져 있거나 모델이 없어도 수집 완료를 막지 않는다.

### 6.2 기존 DB·계산 경로 재사용

기존 뉴스 원본, 시세, 종목 마스터, 계산 함수, 수집 진행표가 있는지 먼저 확인한다. 같은 의미의 원본 테이블을 별도로 만들지 않는다. 새 서비스 전용 상태·분석 이력은 기존 DB의 구분된 테이블/스키마에 추가할 수 있다.

과거 입력에도 기존 검증과 정상화 경로를 사용하되, `ingest_mode=backfill` 등으로 **실시간 알림·최신 상태 덮어쓰기·당일 매매용 부수효과를 억제**한다. 백필과 실시간은 실행·큐·우선순위로 분리하고 원본의 단일 출처는 유지한다.

개발·테스트는 운영과 분리된 임시 테스트 환경을 사용한다. 이는 별도 운영/백필 DB를 상시 추가하라는 뜻이 아니다. 운영 마이그레이션은 백업·롤백 경로를 갖추고 자동으로 파괴적 변경을 하지 않는다.

### 6.3 재시도·재개

작업 상태는 최소 `PENDING / RUNNING / RETRY_WAIT / SUCCEEDED / PARTIAL / FAILED / BLOCKED / CANCELLED`로 구분한다. 검색 결과 없음은 성공한 검색의 `result_count=0`이지 네트워크 실패와 같은 상태가 아니다.

큐를 기존 기능으로 재사용할 수 없다면, 기존 PostgreSQL 안에 작은 작업 테이블을 둔다. 다중 worker가 필요할 경우 `FOR UPDATE SKIP LOCKED`로 짧게 작업을 선점하는 방식이 가능하지만, 이는 일관된 전체 데이터 읽기가 아니라 큐 경합 회피 용도로 제한한다. [S4]

실제 HTTP·LLM 호출 중 DB 트랜잭션/행 잠금을 유지하지 않는다. 작업은 짧은 트랜잭션으로 임대하고 `lease_token`, 만료시각, heartbeat, 시도 횟수로 관리한다. 결과 반영은 유효한 임대 소유자만 하고, 반복 실행되어도 결과가 중복 생성되지 않아야 한다.

페이지별 저장이 커밋된 뒤 체크포인트를 진전시킨다. 중간에 종료되면 마지막 확정 위치부터 재개한다. 자동 재시도 횟수·최대 대기시간은 제한하고 오류를 영구 재시도하지 않는다.

### 6.4 소스 보호와 실패 해석

429 응답은 `Retry-After` 등 공급자 지침을 존중한다. 403·인증 실패·차단 의심은 이유를 기록하고 소스를 일시 정지한다. CAPTCHA, 로그인, 접근제한을 우회하는 코드를 만들지 않는다.

같은 페이지/ID 목록이 반복되면 페이지 종료 또는 오류 가능성을 검사한다. `결과 상한 도달`, `날짜 조건 무시`, `파서 실패`, `원문 접근 불가`를 별도 오류로 남긴다. 검색결과 상한에서 멈춘 구간은 `PARTIAL`이며 완료로 표시하지 않는다.

기존 실시간 조회순위·시세 수집이 최우선이다. 같은 인증키나 한도를 공유하는 작업은 기존 제한 관리자에 참여하고, 백필이 한도를 독점하지 않는다. 새 엔진을 켜도 기존 앱 시작 시간이 늘지 않게 한다.

## 7. 원본·시간·출처 데이터 계약

### 7.1 기사와 기사 버전

논리적으로 다음 정보를 보존한다. 기존 테이블에 이미 있으면 참조하거나 필요한 확장만 한다.

```text
article_id / provider_id / provider_article_id
canonical_url / original_url / publisher
title / body_text / body_hash / language
publisher_published_at / provider_distributed_at / source_modified_at
first_seen_at / fetched_at / timestamp_precision
content_status / source_rights_status / extraction_version
article_version_id / source_snapshot_ref
```

동일 기사 ID의 원문 수정은 새 버전으로 남긴다. 최신 본문으로 옛날 판단 근거를 덮어쓰지 않는다. URL 정규화는 추적용 파라미터만 제거하고 기사 식별에 필요한 파라미터는 유지한다.

고유 기사와 종목의 관계는 다대다다. A·B 두 종목 검색에서 같은 기사가 발견되어도 원문은 한 번만 저장하고 관계만 추가한다. 기사 제목이 같다는 이유만으로 서로 다른 기사를 무조건 하나로 병합하지 않는다.

### 7.2 판단 시각을 명확히 분리

| 필드 | 의미 |
|---|---|
| `event_occurred_at` | 사건이 실제 발생한 시각. 모르면 null |
| `publisher_published_at` | 확인된 원문 게시시각 |
| `first_seen_at` | 우리 시스템이 실제 처음 관측한 시각 |
| `source_available_at` | 출처 자료가 이용 가능했다고 확인되거나 추정된 시각 |
| `availability_basis` | 실시간 관측, 과거 아카이브, 게시시각 추정 등 |
| `as_of` | 이 판단에서 허용하는 정보의 기준 시각 |
| `computed_at` | 실제 계산/LLM 처리를 수행한 현재 시각 |
| `run_id` / `run_mode` | 실시간, 기억 구축, 과거 재생을 구분하는 실행 ID·모드 |

원본 시각은 timezone-aware 형태로 저장하고 내부 기준은 UTC, 화면 표시는 Asia/Seoul로 통일한다. 해외 거래일과 한국 날짜는 자동으로 같다고 처리하지 않는다.

실시간 평가에서는 실제로 수신한 시각을 존중한다. 08:00 기사라도 09:20에 처음 수집했다면 09:00 실시간 판단의 입력이었다고 표시할 수 없다.

과거 백필에서는 `first_seen_at`을 당시 시각으로 위조하지 않는다. 원문 게시시각과 그 버전의 과거 존재 여부를 근거로 ‘당시 이용 가능했을 것으로 추정’할 수는 있지만, **실제 과거 수신 기록과는 구분**한다.

날짜만 있거나 현재 원문에 후속 수정 내용이 섞여 있으면 `timestamp_precision=date_only` 또는 `historical_version_unverified`로 표시한다. 엄밀한 장중 평가에서는 제외하거나 보수적인 사용 가능 시점을 적용한다.

### 7.3 모든 해석에 필요한 공통 메타데이터

```text
schema_version / run_id / as_of / computed_at
model_id / model_digest / quantization / runtime_version
prompt_version / analyzer_version / config_hash
input_article_version_ids / input_market_snapshot_ids
retrieved_case_ids / input_manifest_hash
input_max_available_at / quality_flags
```

시장 데이터와 뉴스가 어떤 버전으로 입력되었는지 재구성 가능해야 한다. 모델명만 같아도 파일·양자화·런타임이 바뀔 수 있으므로 실제 배포 식별자를 남긴다.

## 8. 뉴스가 아니라 Event를 중심으로 기억하기

### 8.1 Article과 Event의 차이

`Article`은 개별 기사이고 `Event`는 그 기사들이 다루는 사건이다. 같은 발표를 여러 매체가 보도했다면 대표 근거로 묶어 중복 분석을 줄인다. 그러나 **같은 Event는 영원히 한 번만 분석한다는 규칙은 금지**한다.

새로운 금액, 조건, 확정 여부, 취소, 정정, 실행 일정은 기존 Event의 중요한 변경일 수 있다. 재전송과 의미 있는 업데이트를 구분하고 `Event Revision`으로 남긴다.

### 8.2 병합·분리 기준

기사의 대상 기업·산업, 행위, 발생 날짜, 계약/정책 식별자, 금액, 핵심 조건을 비교한다. 초기에는 정확한 ID·문자열·규칙으로 처리하고, 의미가 모호할 때만 LLM 후보 판단을 사용한다.

‘투자 검토’와 ‘투자 확정’, ‘수주’와 ‘수주 취소’, 같은 기업의 서로 다른 계약을 이름만 보고 병합하지 않는다. 병합·분리 이력과 근거를 남기고 되돌릴 수 있게 한다. 의미가 불확실하면 둘을 유지하는 편을 기본으로 한다.

### 8.3 사건 사실 상태와 시장 관심 상태를 분리

| 축 | 상태 예시 | 주의 |
|---|---|---|
| 사실·진행 상태 | UNKNOWN, RUMOR, PROPOSED, CONFIRMED, AMENDED, CANCELLED, COMPLETED | 공식 확인과 보도 주장 구분 |
| 시장 관심 상태 | NEW, DORMANT, ACTIVATING, ACTIVE, COOLING, INACTIVE | 가격·거래대금 반응의 관측 상태 |
| 검토 상태 | review_due_at, unresolved_questions | 시간이 지났다는 이유만으로 사건 무효화 금지 |

DORMANT → ACTIVE, COOLING → ACTIVE 등 재활성화를 허용한다. 상태는 반드시 일직선으로 진행할 필요가 없다. 사건이 유효하더라도 시장 관심이 없을 수 있고, 사건이 취소됐어도 취소 뉴스 때문에 거래가 증가할 수 있다.

### 8.4 분리해서 저장할 해석

`사건 내용의 중요성`, `경제적 영향 방향`, `시장 관심`, `가격 반응`, `거래대금 반응`, `후속 일정`, `근거의 신뢰도`를 별개로 저장한다.

‘며칠 동안 주가가 안 올랐다’는 관측만으로 `아직 가격에 반영되지 않은 확실한 호재`라고 단정하지 않는다. ‘이미 반영된 정도’는 직접 측정된 사실이 아니라 불확실한 해석일 수 있으므로 그렇게 표시한다.

며칠 뒤 종목이 오르면 이전 Event는 **설명 후보**가 될 수 있다. 동시에 발생한 다른 뉴스, 시장 전체 상승, 같은 테마의 변화도 함께 확인한다. 시간상 선행했다는 이유만으로 상승 원인으로 확정하지 않는다.

## 9. 자동 테마와 Stock Memory

### 9.1 기업의 업종과 시장의 테마를 분리

정적인 사업 분류와 시장 참여자가 거래하는 테마는 다를 수 있다. `industry`, `market_theme`, `event_specific_basket`을 구분한다.

예를 들어 가상의 지역 산업단지 발표에 대해서는 지역·사업·공시·보도된 시장 인식 등 근거를 통해 후보 관계를 만든다. LLM의 일반 지식만으로 ‘이 회사는 그 지역에 토지가 있다’ 같은 관계를 생성하지 않는다.

### 9.2 테마 관계 계약

```text
security_id / theme_id / relation_type
relation_source: manual | explicit_article | filing | inferred
status: proposed | observed | reviewed | rejected | inactive
valid_from / valid_to / known_as_of
supporting_evidence_ids / contradicting_evidence_ids
first_market_observation_at / last_market_observation_at
review_reason / quality_flags
```

여러 테마 소속, 테마 별칭, 과거 이름, 테마 병합/분리를 지원한다. 초기에는 관계형 DB의 노드·관계 테이블이면 충분하며 별도 그래프 DB를 필수로 도입하지 않는다.

수동 테마는 보존한다. 자동 후보는 별도 레이어에 표시하고 바로 덮어쓰지 않는다. 사용자가 거절한 관계를 동일한 근거만으로 매번 다시 확정하지 않는다. 새 근거가 생기면 무엇이 달라졌는지 보여준다.

같은 기사에 같이 등장하거나 주가가 함께 올랐다는 사실만으로 테마 관계를 확정하지 않는다. 현재 테마 구성을 과거 날짜에 그대로 적용하지 않는다.

### 9.3 ‘상승끼/연속성’의 데이터화

‘예전에 20~30%씩 크게 움직였던 종목이 며칠 뒤 다시 주목받을 수 있다’는 사용자의 관찰을 **검증 가능한 기억 특징**으로 표현한다. 재상승을 보장하는 법칙이나 매수 신호로 고정하지 않는다.

| 특징 | 기본 계산/기록 | 주의 |
|---|---|---|
| 종가 등락 | 공식 기준가 대비 종가 변화 | 기업행사·기준가 변경 고려 |
| 양봉 몸통 | `(close - open) / open` | 전일 대비 등락률과 다른 값 |
| 장중 강세 흔적 | 고가, 시가/기준가 대비 고가 변화 | 고가 도달 시각은 일봉만으로 모름 |
| 종가 위치 | `(close-low)/(high-low)` | high=low 처리 |
| 상대 거래대금 | 오늘 값 / 이전 구간 평균·중앙값 | 기준 구간에서 당일 제외 |
| 반복 강세 | 최근 N거래일 강한 움직임 날짜·횟수 | 임계값과 버전 기록 |
| 가격 유지 | 최근 고점 대비 낙폭·박스 주변 위치 | 계산과 해석을 분리 |
| 주도 역할 | 당시 테마 내 순위·관측 근거 | 현재 기준으로 과거 대장 재선정 금지 |
| 살아 있는 사건 | 연결 Event와 당시 유효 상태 | 잠복 재료와 현재 관심을 분리 |

상한가는 공식 상태/해당 시기 규칙을 사용할 수 있을 때 판정한다. 모든 날짜에 고정 등락률 하나를 대입하지 않는다. 수정주가 여부, 분할·병합·배당·거래정지·신규상장에 대한 계산 정책을 명시한다.

이 특징 계산은 코드가 담당한다. LLM은 결과의 배경 설명을 맡고, 타점 엔진은 이를 받아 현재 진입 조건과 결합한다. 같은 특징 계산을 뉴스 엔진과 타점 엔진 양쪽에 중복 구현하지 않는다.

## 10. 시황 종합 판단: Market State

### 10.1 사실·가설·확인을 나누기

숫자를 버리거나 LLM에게 모든 수치를 추측시키지 않는다.

```text
직접 확인한 시장 수치 + 출처가 있는 뉴스·사건
  → 국내 시장에 대한 해석·가설
  → 현재 KOSPI/KOSDAQ·종목 반응으로 확인/수정
  → 기준시각이 있는 새 판단 스냅샷
```

나스닥, 반도체·메모리 관련 해외시장, 금리, 환율, 유가, 국내 정책·기업 이벤트를 주요 입력 후보로 둔다. 비트코인·금 등은 고정적으로 중요/무의미하다고 분류하지 않고, 변동의 특이성·뉴스·국내 연결 근거에 따라 관심도를 달리할 수 있다.

금리와 채권가격을 혼동하지 않는다. 같은 움직임에서 나온 파생 신호를 서로 독립적인 근거 여러 개처럼 중복 가산하지 않는다. 공급자별 지수·선물·현물·ETF가 다르면 이를 숨겨 하나의 지표처럼 이어 붙이지 않는다.

### 10.2 출력 구조

```text
as_of / run_id / input_freshness
facts[]                         # 수치·사건, 각 근거 ID
market_assessment               # 강세/약세/혼조/불확실 등
participation                   # 지수 집중, 폭넓은 상승 등
concentration                   # 단일 주도, 테마 집중, 수급 분산 등
themes_to_observe[]              # 관심 이유와 반대 근거
stock_contexts[]                # 종목별 재료·기억 연결
hypotheses[]                     # 검증 가능한 가설
confirming_signals[]
contradicting_signals[]
unknowns[]
changes_from_previous[]
evidence_summary                # 사용자가 읽는 짧은 설명
```

다음 변경을 시간순으로 누적한다. 이전 판단은 덮어쓰지 않는다. `시장 전체 약세 → 특정 테마 집중`처럼 방향과 집중도가 함께 변할 수 있으므로 하나의 총점으로 강제 축약하지 않는다.

지수만 오르고 대부분 종목은 약한 상황을 표현할 수 있어야 한다. 확보하지 못한 상승/하락 종목 수나 투자자 수급을 만들어 넣지 않는다.

### 10.3 갱신 방식

중요 Event 업데이트, 장중 요약 신호 변화, 설정한 검토 주기, 수동 요청을 갱신 계기로 사용한다. 모든 기사마다 전체 이력을 LLM에 다시 보내지 않는다.

직전 상태와 새로 확인된 근거를 비교하되, 잘못된 요약이 계속 누적되지 않도록 주기적으로 원본 근거에서 재검토한다. 과거 재생과 현재 운영은 `run_id`와 최신 상태 포인터가 분리되어야 한다.

## 11. 로컬 LLM 실행과 Mac 사용 보호

### 11.1 첫 구현 원칙

초기에는 **실측으로 선택한 로컬 모델 한 개, 동시 추론 한 개**로 시작한다. 7~8B급 양자화 모델은 시험 후보일 뿐 정확도·속도·메모리 적합성이 보장된 권장 사양은 아니다. 큰 모델과 작은 모델을 동시에 상주시켜야만 작동하는 구조는 만들지 않는다.

Mac에서는 네이티브 런타임을 우선한다. Ollama 공식 FAQ는 macOS Docker Desktop에서 GPU 가속을 사용할 수 없다고 설명하므로, NAS의 Docker 배포 방식을 그대로 Mac LLM 서버에 복제하지 않는다. [S2]

실제 모델 ID·파일·라이선스를 확인하고 설정으로 지정한다. 존재하지 않는 모델 태그를 예제 그대로 실행하지 않는다. 분석 전 모델 설치 여부와 구조화 출력 지원을 검사한다.

### 11.2 구조화된 응답과 검증

Ollama는 요청의 `format`에 JSON Schema를 전달하는 구조화 출력을 지원한다. 스키마로 형태를 제한한 뒤 서버에서도 검증한다. 형식이 맞는 JSON이라고 내용이 사실이 되는 것은 아니다. [S3]

다음은 **새 서비스의 예시 계약**이지 실제 종목 분석 결과가 아니다.

```json
{
  "schema_version": "1.0",
  "analysis_type": "event_extraction",
  "as_of": "2020-01-02T08:30:00+09:00",
  "input_article_version_ids": ["demo-article-v1"],
  "event_candidates": [
    {
      "event_type": "industrial_development",
      "factual_status": "PROPOSED",
      "summary": "가상의 산업단지 조성 계획이 보도됨",
      "evidence_refs": ["demo-article-v1:p2"],
      "stock_links": [],
      "theme_candidates": ["지역 산업단지 개발"],
      "impact_direction": "unknown",
      "confidence_label": "low",
      "unknowns": ["실행 확정 여부", "수혜기업의 검증된 연결 근거"]
    }
  ],
  "quality_flags": ["synthetic_example"]
}
```

증거 ID는 실제 입력 문서의 허용된 문단 목록에 존재해야 한다. 주어진 후보 목록에 없는 종목코드를 임의 생성하지 못하게 한다. 근거가 없으면 빈 목록·unknown으로 반환하는 것이 정상이다.

검증 실패 시 제한된 재시도 후 `ANALYSIS_FAILED`로 남긴다. 오류를 숨기기 위해 빈 성공 결과를 넣지 않는다. `confidence_label`은 모델의 해석 자신감이지 상승 확률이 아니다. 확률을 표시하려면 별도 검증·보정이 필요하다.

### 11.3 실행 프로파일

```yaml
llm:
  enabled: false                   # Phase 1에서는 OFF
  provider: ollama_local
  model_id: null                   # 실제 확인한 모델 ID를 설정
  allow_cloud_inference: false
  inference_concurrency: 1
  max_loaded_models: 1
  input_token_budget: 6000         # 초기 시험값; 실제 토크나이저로 측정
  output_token_budget: 1200
  context_window_tokens: 8192      # 모델·런타임 지원 여부 검사
  keep_alive: "2m"
  request_timeout_seconds: 180     # 측정 전 보호 한도, 예상 처리시간 아님
  max_attempts: 2
  backlog_auto_run: false
```

위 키는 앱 설정이다. Codex는 실제 런타임 요청 옵션으로 명시적으로 매핑해야 하며, 앱 설정명을 Ollama가 그대로 지원한다고 가정하지 않는다. 시스템 프롬프트·검색 근거·스키마·출력까지 포함해 컨텍스트 초과를 막는다.

Ollama의 `keep_alive`와 동시 모델·요청 설정을 이용해 상주 시간과 병렬 처리를 제한할 수 있다. 병렬 수나 컨텍스트를 키우면 메모리 요구도 증가할 수 있다. 유휴 상태여도 모델이 메모리에 남을 수 있으므로, ‘요청이 없으니 메모리를 안 쓴다’고 판단하지 않는다. [S2]

### 11.4 사용자 제어

UI에 `분석 시작`, `분석 일시정지`, `백필 분석 허용`, `모델 해제 요청`을 둔다. 사용자 일시정지를 자동으로 풀지 않는다. Mac 사용 중 고부하가 관측되면 새 작업 선점을 멈추고 상태를 표시한다.

메모리 압력과 스왑 증가 등을 측정할 수 있으면 활용하되, 실제 측정하지 않은 값을 표시하지 않는다. CPU 우선순위를 낮췄다는 이유만으로 GPU·통합 메모리 사용량까지 엄격히 제한된다고 보장하지 않는다.

오래된 대기 분석이 재개될 때는 현재 중요 사건을 우선한다. 이미 시효가 지난 ‘실시간 상태 재계산’ 작업은 안전하게 합치거나 대체할 수 있지만, 원본 기사·역사 기록 자체는 삭제하지 않는다. 과거 백필은 별도 저우선순위 작업으로 유지한다.

### 11.5 외부 LLM 차단

Mac worker의 모델 호출 대상은 허용된 로컬 주소만 가능하게 한다. 외부 LLM URL로 자동 fallback하지 않는다. Ollama를 사용할 때는 해당 버전의 로컬 전용 설정을 확인하고 Cloud 기능을 비활성화한다. [S2]

모델 다운로드와 뉴스 수집에 인터넷이 필요한 것은 별개다. ‘외부 LLM 없이’는 ‘네트워크가 전혀 필요 없음’을 뜻하지 않는다. 뉴스 분석 본문이 외부 추론 서비스에 전송되지 않는지를 테스트한다.

## 12. 과거 재생과 미래정보 누출 방지

### 12.1 실행 모드 세 가지

| 모드 | 목적 | 허용되는 해석 |
|---|---|---|
| `MEMORY_BUILD` | 실제로 주목받았던 종목과 과거 기사·사건·반응의 관계 구축 | 사후적 사례 분석. 선행 예측 성과가 아님 |
| `REPLAY_EVAL` | 당시 사용 가능했던 입력만으로 판단 재생 | 시간·표본·자료 버전 제약을 만족한 범위에서 평가 |
| `LIVE_SHADOW` | 현재 들어오는 정보로 실제 시각에 판단만 기록 | 전진 검증. 주문하지 않음 |

첫 대규모 과거 작업의 기본 모드는 **MEMORY_BUILD**다. 이 모드에서 얻은 사례 DB는 유용하지만, ‘그 종목이 오르기 전에 AI가 찾아냈다’는 증거로 사용하지 않는다.

### 12.2 Top40 사후 선정의 한계

D일 거래대금이 큰 종목을 골라 D 이전 뉴스를 역으로 수집하면, 표본 선정에 D일 결과가 사용된다. LLM 프롬프트에서 미래 수치를 숨기는 것만으로 표본 편향이 사라지지 않는다.

엄밀한 D일 장전 검증에서는 D-1까지 확정된 자료로 후보를 정하거나, 당시 실제 수집 대상이 고정되어 있었던 별도 평가 집합을 사용한다. D일 확정 Top40을 사용할 수 있는 가장 이른 시점은 해당 자료가 이용 가능해진 이후다.

대형주·고거래대금 종목에 치우친 자료로 전 종목의 조기발견률을 계산하지 않는다. 전체 뉴스가 없으면 ‘수집된 집합 내 평가’로 명시한다. 반응이 없었던 사건과 종목도 보존하고, 성공 사례만 RAG에 남기지 않는다.

### 12.3 입력 시점 필터

`REPLAY_EVAL`에서는 기사뿐 아니라 다음 항목도 모두 `as_of`를 만족해야 한다.

```text
종목 마스터와 별칭 버전
테마 관계와 상태 버전
해당 시점까지 알려진 Event Revision
당시까지 완결된 가격·시총·수급 자료
당시 이용 가능했던 해외시장·거시 수치
유사 사례의 판단과 이미 완결된 사후 반응 구간
```

예를 들어 과거 사건 X가 D-2에 발생했더라도 X의 D+10 반응은 D 시점에 알 수 없다. RAG에서 사건 날짜만 검사하지 말고 **outcome_window_end와 결과 이용 가능 시각**도 검사한다.

뉴스 본문을 시간 필터링하면서 테마 DB는 최신 상태를 쓰는 식의 우회 누출을 막는다. 과거 재생 run은 실시간 run의 상태·후보 테마·검증 결과를 수정하지 않는다.

### 12.4 오늘 만든 LLM의 과거 지식

현재의 사전학습 모델은 과거 역사나 기업 사건의 사후 결과를 이미 알고 있을 가능성이 있다. ‘미래를 보지 마라’라는 프롬프트와 RAG 시간 필터만으로 이 가능성이 제거되었다고 주장할 수 없다.

따라서 과거 재생 결과에는 사용 모델의 식별 정보와 이 한계를 표시한다. 최종적인 운용 판단은 별도의 **LIVE_SHADOW 전진 기록**으로 확인한다. 모델 교체 후 과거 성과가 높아졌다고 곧바로 예측력 향상이라고 발표하지 않는다.

### 12.5 데이터가 불완전할 때

과거 원문 버전 미확인, 날짜만 있는 기사, 상장폐지 종목 누락, 과거 수급 미확보를 품질 플래그로 보존한다. 이를 무조건 모든 연구에서 버릴 필요는 없지만, 사용 가능한 분석과 불가능한 주장을 분리한다.

시간순 학습·검증에서는 테스트 구간 정보를 전처리·모델 선택에 사용하지 않는 것이 기본이다. 날짜순 분할과 gap을 지원하는 도구가 있어도, 같은 날짜의 종목 행·같은 사건의 반복 기사·겹치는 반응 기간을 프로젝트 수준에서 함께 처리해야 한다. [S5][S6]

## 13. RAG와 사후 시장 반응

### 13.1 초기 검색 방식

처음부터 모든 기사에 임베딩을 생성하지 않는다. Event 유형, 종목, 테마, 시기, 시장 상태, 핵심 키워드로 좁힌 사례 검색부터 만든다. 한국어 검색의 실제 적합성을 확인하고 필요할 때만 임베딩을 추가한다.

벡터 검색을 추가해도 날짜·출처·run·사건 버전 필터는 필수다. 검색이 느리다는 측정이 없는데 벡터 DB나 그래프 DB를 별도 운영하지 않는다.

```text
오늘/재생 시점의 사건
  → 시간 조건에 맞는 유사 사건 후보
  → 중복 기사군과 같은 사건의 반복 사례 제거
  → 성공·실패·미반응 사례 함께 선택
  → 당시 시장 배경과 반응 구간을 짧게 제공
  → LLM이 근거와 차이점을 설명
```

오래된 사례를 많이 보여주는 것만으로 판단 품질이 높아졌다고 가정하지 않는다. 검색 없이, 검색을 넣어서, 규칙만 사용해서 각각 비교한다.

### 13.2 일봉으로 측정하는 반응

처음에는 D+1, D+3, D+5, D+10 **거래일** 구간을 제공한다. 사건 발생이 주말/장중/장후인 경우의 기준일 매핑을 명시하고 버전으로 저장한다.

일봉만 있는 사건은 기본적으로 사건 정보가 이용 가능해진 이후의 첫 적격 거래일 시가를 평가 기준 후보로 삼을 수 있다. 정확한 매핑은 실시간/과거 자료의 시각 신뢰도와 공급자 세션 정의에 따라 결정하고 숨기지 않는다.

```text
reaction_baseline_time / reaction_baseline_price
horizon_sessions / outcome_window_start / outcome_window_end
close_return / benchmark_relative_return
observed_high / observed_low
turnover_ratio / peer_theme_reaction
data_coverage / corporate_action_policy
label_available_at / alternative_events
```

일봉 고가·저가는 관측된 가격 범위다. 그 가격에서 진입·청산 가능했다는 뜻이나 실현 가능 수익률이 아니다. 구간 중 고가와 저가 중 무엇이 먼저였는지 알 수 없으면 순서를 만들어내지 않는다.

‘상승 반응 없음’, ‘하락’, ‘테마 미형성’, ‘원인 불명’도 유효한 결과다. 뉴스 수집 실패와 실제 미반응을 같은 음성 정답으로 취급하지 않는다.

### 13.3 학습과 개선의 경계

LLM이 추출한 테마·영향 설명은 자동 생성 라벨이다. 곧바로 정답 데이터로 확정하지 않는다. 사후 주가 변화 역시 해당 뉴스의 인과적 효과를 단독으로 입증하지 않는다.

개선 과정은 다음처럼 운영한다.

```text
판단 기록 → 실제 반응 연결 → 오류 유형 확인
  → 개선 후보 생성 → 버전 고정 실험
  → 별도 평가·전진 검증 → 채택 여부 결정
```

AI가 매일 스스로 프롬프트·가중치·거래 규칙을 수정하고 적용하는 기능은 초기 범위에서 제외한다. 실제로 모델 훈련을 수행하지 않았는데 ‘학습되어 더 똑똑해졌다’고 표현하지 않는다.

## 14. 논리 데이터 모델과 저장 규칙

아래는 필요한 **논리 엔터티**다. 기존 테이블 매핑을 먼저 작성하고, 각 단계에서 필요한 것만 추가한다. 표 전체를 초기 마이그레이션으로 한꺼번에 생성하지 않는다.

| 엔터티 | 내용 | 도입 단계 |
|---|---|---|
| Run / Plan | 범위, 모드, 버전, 시작·종료, 입력 식별 | Phase 1 |
| Candidate Day | 날짜별 TopN과 선정 근거 | Phase 1, 기존 구조 우선 |
| Collection Coverage | 공급자·검색 대상·기간별 상태와 누락 | Phase 1 |
| Job / Lease | 큐, 재시도, 임대, 완료·오류 | Phase 1 |
| Article / Article Version | 원본·메타데이터·수정 버전 | 기존 데이터 재사용 |
| Security / Daily Bar | 종목 마스터와 일봉 | 기존 데이터 재사용 |
| Article Analysis | 구조화 추출, 모델·프롬프트·근거 버전 | Phase 2 |
| Event / Revision / Evidence Link | 사건과 변경 이력·기사 연결 | Phase 2~3 |
| Theme Relation | 시간축 있는 종목·테마 관계 | Phase 3 |
| Stock Memory Snapshot | 일봉 기반 종목 기억 | Phase 3 |
| Judgment Snapshot | 시장·테마 판단과 변경 이유 | Phase 3 |
| Outcome / Review | 사후 반응, 오류 유형, 검증 결과 | Phase 4 |

`mi_` 접두어나 전용 스키마는 이름 충돌 방지 후보일 뿐 기존 규칙을 무시하고 강제하지 않는다. 수집한 원문·일봉을 별도 ‘AI DB’로 복제하지 않는다.

금액 단위와 통화를 필수로 관리하고, 원본 값은 정밀도를 보존한다. null·미확보·0을 구분한다. JSON으로 유연한 분석 항목을 담을 수 있지만, 날짜·종목·run·상태 등 조회 핵심 필드는 인덱스를 만들 수 있는 명시적 컬럼을 우선한다.

중복 방지는 애플리케이션 검사뿐 아니라 DB의 유일성 제약으로 보장한다. 분석 결과 식별에는 입력 버전, 분석기·모델·프롬프트·설정 버전과 run 범위를 고려한다. 재분석은 새 결과 버전으로 남기고 과거 판단을 덮어쓰지 않는다.

원본과 판단 이력은 임의 만료 삭제하지 않는다. 로그·임시파일은 별도 정책으로 관리한다. 원문 보관은 해당 소스의 허용 범위를 따른다.

## 15. API와 날짜별 판단 대시보드

### 15.1 사용자 화면

초기에는 NAS에서 제공하는 가벼운 웹 화면이면 된다. 별도의 무거운 데스크톱 앱, 앱 설치기, 프런트엔드 프레임워크 여러 개를 만들지 않는다. 기존 웹/API 기술이 있으면 재사용한다.

| 화면 | 보여줄 것 |
|---|---|
| 수집 현황 | 계획 범위, 거래일·후보 수, 검색/원문/분석 상태, 오류, 재개 |
| 오늘/날짜별 판단 | 기준시각, 실제 계산시각, 사실, AI 해석, 반대 근거, 불확실성 |
| 판단 타임라인 | 변경 전후, 변경을 촉발한 기사·시장 데이터, 버전 |
| 사건·테마 | 잠복/활성/재활성 사건, 연결 종목, 근거, 수동 확인 상태 |
| 종목 기억 | 최근 강세·거래대금·과거 테마 역할·살아 있는 Event |
| 복기·평가 | 예측 당시 문장, 평가 규칙, 사후 반응, 미반응·오류 |
| 리소스·설정 | Mac worker 연결, 모델 상태, 대기열, 분석 일시정지 |

Phase 1은 **수집 현황과 기사 목록**만 만든다. 분석 단계가 완성되기 전에 가짜 AI 시황을 채워 넣지 않는다. 데모 데이터는 화면에 뚜렷하게 표시하고 운영 데이터와 분리한다.

### 15.2 시점별 판단 표시 원칙

`당시 입력 → 당시 판단 → 이후 변경 → 사후 결과`를 분리한다. 과거 날짜 화면의 판단 부분에 나중에 추가된 사실을 조용히 섞지 않는다. 재분석 결과는 원래 판단 옆의 별도 버전으로 보여준다.

설명은 **확인 가능한 근거의 요약과 판단 변경 이유**다. 모델의 숨겨진 내부 사고과정을 읽어낸 것처럼 표시하지 않는다. 기사 원문 링크, 근거 문단, 시세 시각, 모델 버전으로 추적 가능하게 한다.

`분석 대기`, `원문 없음`, `순위 자료 일부`, `시세 지연`, `과거 버전 미확인`, `사후 선정 자료`를 정상적인 상태 배지로 보여준다. 미분석을 중립 판단으로 바꾸지 않는다.

분 단위 시세가 없는 날짜에는 ‘몇 분 선행 발견’ 지표를 숨긴다. 자기보고 신뢰도를 상승 확률·승률처럼 표시하지 않는다.

### 15.3 제안 API 계약

기존 라우팅 규칙에 맞춰 아래와 동등한 기능을 제공한다. 아래 경로는 **구현 목표**이지 현재 존재하는 엔드포인트가 아니다.

```text
GET  /api/mi/v1/health
GET  /api/mi/v1/runs
GET  /api/mi/v1/runs/{run_id}/progress
GET  /api/mi/v1/candidates?date=...&plan_id=...
GET  /api/mi/v1/articles?security_id=...&from=...&to=...
GET  /api/mi/v1/market-state?as_of=...&run_id=...
GET  /api/mi/v1/judgments?date=...&run_id=...
GET  /api/mi/v1/events?as_of=...&status=...
GET  /api/mi/v1/themes?as_of=...&status=...
GET  /api/mi/v1/stocks/{security_id}/memory?as_of=...
GET  /api/mi/v1/reviews?date=...&run_id=...

POST /api/mi/v1/runs/{run_id}/pause
POST /api/mi/v1/runs/{run_id}/resume
POST /api/mi/v1/worker/jobs/claim
POST /api/mi/v1/worker/jobs/{job_id}/heartbeat
POST /api/mi/v1/worker/jobs/{job_id}/complete
POST /api/mi/v1/worker/jobs/{job_id}/fail
```

모든 목록은 제한·페이지네이션을 지원한다. 응답에 `schema_version`, `as_of`, `run_id`, 데이터 신선도·품질을 포함한다. 수정/제어 API는 인증·권한 검사를 하고, 작업 완료는 임대 토큰으로 보호한다.

기존 주식 앱에는 우선 읽기 권한만 제공한다. 화면을 열었다는 이유로 전체 백필·재분석이 실행되지 않게 한다. 기존 API 호환성을 유지하면 모델 교체 시 소비자 수정을 줄일 수 있지만, 스키마를 바꾸고도 ‘앱을 절대 수정할 필요 없다’고 보장하지 않는다.

실제 레포에 맞춰 이름을 조정한다. 책임 분리를 유지하되 전달만 하는 클래스, 한 구현만 있는 과도한 계층, 플러그인 프레임워크를 만들지 않는다.

```text
market_intelligence/
  config.py                  # 설정과 검증
  contracts.py               # 입출력 스키마
  integrations.py            # 기존 NAS ingest/API 연결
  universe.py                # TopN 선정과 범위 검사
  backfill.py                # 기간 병합·수집 계획·실행
  sources/                   # 검증된 공급자만
  jobs.py                    # 기존 큐 재사용 또는 작은 작업 큐
  analysis/                  # 이후 Event·LLM·Market State
  replay.py                  # 이후 시간순 재생과 평가
  api.py                     # 내부 API·UI 라우팅
  worker.py                  # Mac 로컬 LLM worker
  cli.py                     # 유한한 배치 진입점
  templates/                 # 가벼운 초기 화면
  tests/
```

최초 작업에서는 이후 단계의 빈 모듈 수십 개를 미리 생성하지 않는다. 존재하지 않는 API에 연결하는 코드를 성공처럼 포장하지 말고, 계약 테스트와 미지원 상태를 제공한다.

`.env.example`에는 설정 이름과 예시만 넣는다. API 키, NAS 인증키, DB 비밀번호, HMAC 키는 코드·문서·로그·테스트 fixture에 포함하지 않는다. 기존 비밀 관리 방식을 우선한다.

아래 명령은 **개발할 CLI의 사용성 요구 예시**다. 실제 명령 이름을 달리 구현하면 README에 실제로 실행되는 명령을 적는다.

```bash
python -m market_intelligence inspect --read-only
python -m market_intelligence sources probe --config config.yaml
python -m market_intelligence universe plan --config config.yaml --dry-run
python -m market_intelligence backfill plan --config config.yaml --pilot
python -m market_intelligence backfill run --plan-id <실제_PLAN_ID>
python -m market_intelligence backfill resume --run-id <실제_RUN_ID>
python -m market_intelligence report --run-id <실제_RUN_ID>
```

연결된 NAS의 실제 경로·호스트·DB명은 조사 후 설정한다. 문서의 플레이스홀더를 운영값으로 추측해 치환하지 않는다. API를 사용할 수 없는 환경에서는 로컬 fixture·테스트를 진행할 수 있지만, 실제 수집을 완료했다고 보고하지 않는다.

## 17. 단계별 구현 순서와 완료 조건

### Phase 0 — 현황 조사와 수집 가능성 확인

읽기 위주로 기존 레포 지침, 실행 진입점, ingest, 스키마, 뉴스 공급자, 일봉 범위, 후보 계획, 시간·단위, 인증·한도 관리, 배포 구조를 조사한다. 비밀값은 출력하지 않는다.

산출물은 짧은 `INTEGRATION_AUDIT.md`다. `확인됨 / 코드상 가능하지만 미실행 / 미확인 / 제약 있음`을 나누고, 어떤 데이터가 재사용되며 무엇이 부족한지 적는다. 특히 전종목 순위 복원에 충분한 데이터인지 확인한다.

**통과 기준:** 공급자·저장 경로·시장 범위가 식별되고 소규모 실제 응답으로 과거 날짜 요청이 검증된다. 미지원 소스는 명확하게 BLOCKED로 기록한다. 막힌 외부 경로가 있어도 독립적인 계약 테스트와 수집 계획 구현은 진행한다.

### Phase 1 — Top40 과거 뉴스 수집 MVP

후보 선정/가져오기, 수집 창 병합, 원본 중복 처리, 기존 ingest 연결, 오류·체크포인트·재개, 진행 상태와 기사 목록 화면을 구현한다. LLM·임베딩·자동 테마·시황 평가는 제외한다.

**통과 기준:** 확인된 작은 구간에서 실제 저장과 중단·재개가 동작한다. 같은 계획을 다시 돌려도 원문·관계가 불필요하게 중복되지 않는다. 부분 수집·결과 없음·실패가 구분된다. 기존 실시간 수집에 회귀가 없다.

실제 과거 소스가 막혀 있다면 테스트 가능한 부분까지 완료하되, 전체 Phase 1을 ‘실수집 검증 완료’라고 표시하지 않는다.

### Phase 2 — 로컬 LLM의 기사·사건 추출

Mac worker, 인증된 작업 교환, 로컬 모델 한 개, 구조화 출력·근거 검증, 모델/프롬프트 버전, 사용자 일시정지와 분석 결과 화면을 구현한다.

**통과 기준:** 외부 LLM 없이 표본 기사가 처리된다. Mac 미접속 중 수집이 계속된다. 시간초과·JSON 오류·없는 근거·없는 종목코드가 검출된다. 실제 Mac 사용 중의 메모리와 지연을 측정한다.

### Phase 3 — 사건 생명주기·테마 후보·종목 기억·일별 시황

Event 변경 이력, 지연 반응·재활성화 상태, 자동 테마 후보와 수동 관계 분리, 일봉 Stock Memory, 근거 기반 Market State와 판단 타임라인을 구현한다.

**통과 기준:** 며칠 전 사건이 사라지지 않고 현재 관측과 연결된다. 확정 근거 없는 테마는 후보로 남는다. 이전 판단을 지우지 않고 변경 근거를 확인할 수 있다. 일봉 특징 계산은 테스트로 재현된다.

### Phase 4 — 과거 사례 DB·RAG·평가

MEMORY_BUILD, 시간 필터 있는 RAG, REPLAY_EVAL, D+1·3·5·10 반응 기록, 표본/시간 누출 검사와 오류 복기를 구현한다. LIVE_SHADOW 기록도 준비한다.

**통과 기준:** 미래 기사·현재 테마 관계·미완결 D+10 결과가 과거 입력으로 들어가지 않는다. 사후 선정 표본은 선행 성능과 분리된다. 실패·미반응 사례가 남고, 지표 분모·구간·자료 누락을 확인할 수 있다.

### Phase 5 — 기존 주식 앱 연결과 규모 확대

검증된 API만 기존 앱에 읽기 전용으로 연결한다. 과거 수집 기간·분석량·추가 후보 수는 측정 결과를 보고 늘린다. 타점 엔진은 Market State·Theme·Stock Memory를 소비하지만 이번 단계에서 주문 로직까지 확대하지 않는다.

**통과 기준:** 새 서비스·Mac이 중단되어도 기존 앱의 시세·주문 기능이 유지되고, 앱은 분석정보 지연만 명확히 표시한다. API 스키마 버전과 호환성 테스트가 존재한다.

## 19. 처리량·품질 측정과 규모 확대 조건

### 19.1 처음부터 보장하지 말 것

‘텍스트이므로 가볍다’, ‘M4 24GB면 하루 모든 뉴스를 충분히 처리한다’, ‘한 사건당 몇 초’ 같은 가정을 구현 예산으로 고정하지 않는다. 수년치 원문을 반복 해석하는 작업은 일상적인 소량 분석과 부하가 다르다.

뉴스 수를 `거래일 × 40`으로 계산하지 않는다. 이는 종목·날짜의 선정 횟수일 뿐이며, 실제 검색 페이지 수와 원문 수는 종목별 보도량·기간 겹침·재전송에 따라 달라진다.

### 19.2 반드시 남길 측정값

| 구분 | 측정값 |
|---|---|
| 수집 | 요청 수, 페이지 수, 고유 기사 수, 중복률, 원문 확보율, 오류 유형 |
| 데이터 범위 | 검증된 거래일·종목 범위, 순위 자료 완전성, 원문 시각 신뢰도 |
| LLM | cold/warm 지연, p50/p95, 입력/출력 토큰, JSON 성공률, 근거 검증 실패율 |
| Mac | 실제 메모리 압력·스왑 변화, 사용자가 느끼는 지장, 작업 일시정지 횟수 |
| NAS | CPU·메모리·I/O·DB 지연, 기존 실시간 수집의 지연 변화 |
| 큐 | 새 분석 작업 도착률, 처리율, 우선순위별 대기시간, 가장 오래된 작업 나이 |
| 분석 품질 | 사건 추출 오류, 잘못된 종목 연결, 과도한 테마 생성, 반대 근거 누락 |

완전한 전체 기사 수를 알 수 없는 검색 소스에서는 ‘전체의 100% 수집’이라고 표현하지 않는다. 계획된 질의 처리가 끝났다는 것과 모든 기사를 확보했다는 것을 분리한다.

### 19.3 확대 순서

소규모 날짜·기사 표본 → 한정된 과거 기간 → 더 긴 기간의 수집 → 사건 단위 선별 분석 → 현재 운영 순으로 늘린다. 수집은 끝났어도 모든 원문을 즉시 LLM으로 분석할 필요는 없다.

분석 부하가 커지면 먼저 중복 분석, 불필요한 재요약, 긴 입력, 자동 재시도, 지나친 테마 확장을 줄인다. 백필을 야간/수동 허용으로 제한할 수 있지만 사용자의 Mac이 항상 켜져 있다고 가정하지 않는다.

실측 처리율·대기열·품질이 부족할 때만 모델 또는 추론 장비 변경을 검토한다. 새 하드웨어나 유료 API 구매는 이 명세의 선행 조건이 아니다.

## 20. 보안·운영 안전장치

뉴스 본문과 검색결과는 신뢰하지 않는 입력이다. 본문에 포함된 ‘이전 지시를 무시하라’ 등의 문장을 시스템 지시로 해석하지 않는다. LLM에 셸·SQL 실행, 임의 URL 탐색, 주문, DB 직접 변경 권한을 부여하지 않는다.

원문 fetcher는 허용된 HTTP(S) 대상만 처리하고, 내부망·루프백·클라우드 메타데이터 주소에 대한 임의 요청을 차단한다. 리다이렉트 후 주소도 다시 검사한다. NAS 내부 API 통신은 별도로 명시한 허용 대상만 사용한다.

기사 HTML을 화면에 그대로 삽입하지 않는다. 본문·링크를 정제하고 파일 크기·응답 시간·리다이렉트 수를 제한한다. 원문 접근 실패를 우회하는 브라우저 자동화나 자격증명 공유를 무단 도입하지 않는다.

Mac의 원시 LLM 포트를 인터넷에 노출하지 않는다. NAS API도 기존 인증·내부망/VPN 정책을 따른다. 이 명세를 이유로 공유기 포트포워딩·방화벽 개방·인증 해제를 수행하지 않는다.

운영 DB에서 `DROP`, `TRUNCATE`, 기존 데이터 대량 삭제, 스키마 전면 재작성은 금지한다. 백필은 멱등한 입력과 제한된 추가 변경으로 실행하고, 사용자의 미커밋 작업을 보존한다.

## 21. 이번에 고정하는 결정과 나중에 정할 항목

### 고정된 방향

**외부 LLM 없는 신규 엔진, 기존 앱 보존, 기존 NAS DB·ingest 재사용, Mac 비전용 운영, Top30~40 중심 과거 뉴스, 일봉 중심 기억, 사건의 지연 반응·재활성화, 시간축 있는 자동 테마 후보, 날짜별 판단·복기, 파인튜닝보다 사례 DB 우선**을 지킨다.

### 실측·조사 후 결정할 항목

실제 소스별 과거 제공 범위, 정확한 모델 ID, 추론·메모리 예산, 역사적 순위 자료 범위, 원문 보관 권한, 현재 DB 매핑, 장중 갱신 주기, 검색 방식, 테마 후보 승격 기준은 확인 후 정한다.

모호한 부분을 전부 사용자에게 다시 묻고 멈추지 않는다. 기존 코드와 자료로 확인 가능한 것은 먼저 확인하고, 위험 없는 부분은 보수적인 기본값과 설정으로 구현한다. 다만 파괴적 운영 변경, 유료 서비스 가입, 임의 권한 확대는 추측해서 진행하지 않는다.
