# 추가 수집자료 활용 재점검

기준: 2026-09-12 작업본과 NAS `2026.09.12-vi-hot-cohort-v1`의 읽기 전용 API 확인.
단순히 API가 200을 반환하는 것과 자료가 실제 연결·소비되는 것을 구분한다.

뉴스 상세 소비, 서버 수집 보완, confirmed N3 기사의 종목 뉴스 목록 병합을 구현했고, 현재 누적 작업본은 D3a를 더한 `2026.09.12-d3a-minute-revisions-v1`, 스키마 v14이다. 병목 수정 당시 관련 회귀 65개와 전체 핵심 회귀 624개(`273+351`, 두 묶음 종료 코드 0)가 통과했고 D2 뒤 핵심 회귀는 639개(`287+352`)가 통과했다. 테스트 범위는 서로 겹치므로 합산하지 않는다. 세 번의 실환경 빌드에서 이어진 CPU 점유와 health timeout은 진단 스택에서 `news_sources._targets → _exact_company_name → re.compile` 호출로 확인됐다. 기사마다 전체 KRX 회사명 정규식을 다시 만들던 경로에 부분문자열 선검사와 이름별 패턴 캐시를 적용하고, 페이지 단위 종목 연결 계산은 서버 이벤트 루프 밖에서 수행한다. 병목 형태의 30만 후보 검사는 개발 PC에서 0.0176초에 끝났고, 본문에 없는 이름의 패턴 생성 수는 0이었다. 1회 스택 진단 설정은 제거했다.

## 실측으로 확인한 뉴스 활용 장애

1. 9개 검색어 source가 실행되고 저장 본문이 존재한다. 한 조회 시점에 fulltext 2,912개, summary_only 104개, 작업 COMPLETED 3,016개/PENDING 10,391개/RUNNING 1개였다. 이는 관측 시점의 상태이며 하루 수집량이 아니다.
2. 같은 시점의 target 상태는 unresolved 10,024개, RULE 결과는 비어 있었다. 종목 연결이 실제로 작동한다고 보고할 근거가 아직 없다.
3. 최근 GLOBAL article revision 1,000개 중 반복 횟수가 많은 기사 6개를 비교했다. 각 기사의 제목·링크는 하나이고 요약·hash는 3~4종류인데 revision은 12~14개였다. 검색어별 요약 차이를 마지막 GLOBAL hash 한 개와 비교하므로 같은 변형이 번갈아 새 BODY 작업을 만드는 경로가 확인됐다.
4. `/news/sources`의 `summary.raw_count`가 `limit=1`에서 100, `limit=20`에서 2,000으로 달라졌다. 현재 구현은 잘린 runs 배열만 합산하므로 이를 요청 기간 전체 누적량으로 사용하면 안 된다.

뉴스 종목 목록의 영속 원본(`stock_catalog`)은 TOP20의 순위 갱신에서만 초기화된다. 뉴스 source는 독립 실행하지만 이 원본을 읽기만 한다. 따라서 장외·주말 최초 실행 또는 TOP20 비활성 환경의 빈 카탈로그에서는 회사명이 명시된 기사도 미연결된다. **현재 NAS 카탈로그의 실제 내용은 공개 API로 확인하지 못했으므로, 현재 unresolved 전체의 단일 원인으로 확정하지 않는다.**

별도 임시 SQLite에서 수정 전 동작도 재현했다(실제 사용자 DB 변경 없음).

- 검색어 a/요약 A → b/B → a/A → b/B: 매번 새 기사 판본을 만들어 신규 판본 수가 `[1, 1, 1, 1]`이었다. 수정 후 기대는 `[1, 1, 0, 0]`이다. 같은 검색어의 실제 내용 변경 A → B → A는 세 판본을 보존해야 한다.
- 같은 4회 관측의 `raw_count`가 상세행 `limit=1`에서는 1, `limit=20`에서는 4였다. 기간 전체 합계는 두 경우 모두 4여야 한다.
- GLOBAL 기사 본문을 먼저 저장한 뒤 같은 기사를 confirmed 종목 관계와 재수집해도 RULE 작업 수가 0이었다. 뒤늦은 종목 연결도 기존 본문으로 RULE 작업 하나를 예약해야 한다.

## 이번 적용 계약

- 뉴스 상세의 기존 선택 흐름에 비동기 조회 worker를 연결한다. 실행 worker는 하나, 대기 요청은 가장 최근 선택 하나로 제한한다.
- 종목·기사 identity·판본 참조를 확인한다. GLOBAL 본문은 같은 기사를 찾는 대체 경로로 사용하고, 다른 종목의 사건 판단은 가져오지 않는다.
- 기사 선택/종목 변경 후 늦게 도착한 응답이 새 선택의 상세를 덮어쓰면 안 된다.
- 가져온 본문/근거는 HTML을 이스케이프한다. 본문 조회만으로 유료 AI를 실행하지 않는다.
- 원문 전체, 검색 요약만 존재, 미수집/처리 대기, 조회 실패를 구분한다. 자료가 없을 때도 기존 요약과 버튼은 사용 가능하다.
- 현재 목록 기사와 저장 판본 내용이 다르면 판본 차이를 알리고 그 규칙을 현재 기사의 최종 판단으로 합치지 않는다.
- 신규 로컬 DB나 공통설정은 만들지 않는다. 데이터가 부족한 H1/D5/시장 이벤트를 점수나 매수·매도 판단에 강제로 연결하지 않는다.

서버 보완의 범위도 위 재현과 직접 연결된 네 가지로 제한한다.

| 보완 | 입력·출력 계약 | 완료를 판단할 검증 |
| --- | --- | --- |
| 검색어별 반복 요약 재사용 | source+identity의 직전 관측 내용이 같으면 같은 article/body 작업을 참조하고 새 관측만 추가. 실제 같은 source의 정정은 보존 | 검색어 교차 A/B/A/B에서 신규 판본 2개, 같은 source A/B/A에서 3개. 관측 수는 모두 보존 |

| 뒤늦은 종목 연결 | 같은 기사 판본에 confirmed 관계가 생기면 이미 있는 완료 body로 RULE 한 개를 예약. 재수집은 중복 예약하지 않음 | body 먼저/target 나중과 target 먼저/body 나중 모두 같은 종목별 분류로 도달 |

기존 중복 판본·미연결 이력·대기 작업을 대량 삭제하거나 소급 정정하지 않는다. 따라서 이 수정은 배포 후 신규 중복을 줄이며, 이미 쌓인 대기 작업이 즉시 없어지는 것은 아니다. 종목 관계가 `confirmed`인 GLOBAL 저장기사는 종목 뉴스 목록에 합치지만, 미확정 관계를 소급 확정하거나 기존 대기 작업을 다시 처리하지는 않는다.

## 후속 소비 기능 전 보완할 경계

- 매매일지의 `news_at_execution()`은 발표시각 기준 직전 48시간~직후 5분을 고른다. 발표시각과 실제 가용시각은 다르므로 N1 이력과 판본을 확인하는 별도 조회를 붙여야 한다. 사용자 작성 복기와 기존 연결은 보존한다.
- `MarketEventService._upper_limits`는 거래일을 키에 포함하지 않고 `_load_metadata()`는 기본정보 저장 날짜를 검사하지 않는다. 다음날 상한가 가격 갱신과 당일 최종 체결의 날짜·시장·신선도 회귀가 필요하다.
- 추적군은 현재 KRX 세션 종료에 만료되므로 익일 NXT 20시까지 유지하려는 요구와 차이가 있다. `AutonomousTop20Service.backfill_day()`의 cohort 합류도 현재 `entry_session == day`만 골라 익일 보완 범위를 별도로 확인해야 한다.
- VI/상한가 current 상태와 불변 사건 이력을 구분해야 한다. 한 번 기록된 CURRENT는 이후 하락 후에도 역사에 남으므로 최신 현재 상태로 오해하면 안 된다.
- 1초 행 수는 종목뿐 아니라 KRX/NXT 시장별로 계산된다. 저장 용량 추정에서 거래일 수·거래가 있었던 초·중복 시장·인덱스/WAL·백업을 분리해야 한다.

## 배포·검증 경계

앱 소비 코드와 서버 수집 수정의 반영 상태를 따로 보고한다. 사용자가 재빌드를 맡기로 했으므로 이 점검 자체로 NAS 컨테이너를 중지·재빌드하지 않는다. 실제 API 데이터, 재현 테스트, 코드만으로 확인한 경계를 각각 구분해 기록한다.

### 앱 소비 경로 확인

- 관련 회귀 32개에서 판본·타종목 분리, GLOBAL 완료 본문 재사용, 조회 실패/404/재시도, 한 worker와 최신 선택 한 개, 키보드 선택, 요청 중 종료를 확인했다.
- root 독립 연결 검증: 임시 SQLite 기사 저장 → BODY/RULE worker → FastAPI 인증 이력 API → 실제 `CentralNewsClient` → 상세 자료 조립. 인증 GET 4회로 fulltext, 정확한 event revision, 500억원의 원 단위 금액 전달을 확인했다. 실제 NAS·외부 기사·유료 AI 호출은 없었다.
- 예시 자료를 QTextBrowser에 렌더해 한글 항목, 0점 보존, 규칙 근거가 본문 앞에 배치되는 것을 확인했다. 제품의 전체 실행 화면을 직접 조작한 검증은 아니다.
- 신규 공통 DB/설정/Manager 계층 없이 기존 뉴스 worker·표시 함수·창과 중앙 client를 확장했다. 상세의 추가 호출은 선택 시 NAS 읽기를 위한 비동기 경계이며, 메인 순위 수집에는 새 계산을 넣지 않았다.
- 로컬 상세 소비 경로의 주요 파일은 기존 창·표시 함수 2개에서 worker·HTTP client를 포함한 4개로 늘어난다. 추가 호출은 `선택 → 작업 예약 → worker → 이력 조회 → 표시`이며, 비동기 통신과 요청 수명 때문에 필요한 경계다. 새 단순 위임 Service/Manager는 만들지 않았다.

### 서버 수정 후 독립 재현

root가 같은 임시 SQLite 재현을 수정 코드로 다시 실행해 다음 결과를 확인했다.

- 교차 검색어 신규 판본 수: `[1, 1, 0, 0]`.
- 상세 `limit=1`과 `limit=20`의 기간 `raw_count`: 모두 4.
- 네 관측의 `distinct_identity_count`: 1.
- 본문 저장 후 confirmed 관계를 두 번 재수집한 RULE 작업 수: 1.
- v9 임시 DB에 관측 이력을 만든 뒤 v10만 적용되는 것을 확인했다. 기존 observation ID·article 참조·identity·hash가 모두 같고 source+identity 조회 인덱스가 생겼다.

이는 실제 PostgreSQL 서버에서의 동시성·운용 검증을 대신하지 않는다.

핵심 회귀 실행 중 제품 코드 변경 없이 정식 v9→v10 이전 DB fixture 테스트 1개를 추가했으며, 이 테스트는 별도 실행으로 통과했다.
