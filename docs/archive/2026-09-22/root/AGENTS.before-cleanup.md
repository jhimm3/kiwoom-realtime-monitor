# 저장소 작업 지침

작업을 시작할 때 `DEVELOPMENT_GUARDRAILS.md`와 수정 대상에 해당하는 `docs/archive/2026-09-22/root/MODULE_MAP.md`를 먼저 확인한다.

리팩터링 종료 또는 후속 보완 작업 중에는 `docs/archive/2026-09-22/root/REFACTORING_CLOSEOUT_PLAN.md`도 먼저 읽는다. 그 문서의 현재 단계 한 가지만 진행하고, 직접 관련 없는 발견·요청은 최종 보류 원장에 기록한다. NAS는 종료 계획 4단계 전까지 중간 배포하지 않는다.

## 리팩터링과 버그 수정 원칙

- 이름만 다른 Manager/Service/Handler/Controller를 습관적으로 추가하지 않는다. 새 계층은 독립 상태·정책·수명·저장 경계처럼 설명 가능한 책임이 있을 때만 만든다.
- 변경 전후에 한 기능을 이해하는 데 필요한 파일 수와 호출 깊이를 비교한다. 단순 전달 단계만 늘어난다면 분리하지 않는다.
- 기존 계층이 단순 위임처럼 보여도 즉시 다시 합치지 않는다. 먼저 과추상화 후보로 기록하고 리팩터링 완료 후 함께 감사한다.
- 버그는 추측으로 바로 수정하지 않는다. 실제 호출 경로를 추적하고 로그·실행 결과·테스트로 가설을 확인한 뒤, 확인된 원인에만 최소 수정하고 관련 회귀를 실행한다.
- 확인된 사실, 아직 검증하지 못한 가설, 수정 후 검증 범위를 보고에서 구분한다.

## 이 PC의 X: NAS 공유

- 사용자 Windows 세션의 NAS 프로젝트는 `X:\kiwoom-monitor`에 있다.
- 기본 샌드박스 계정에서는 세션별 드라이브 매핑 때문에 X:가 보이지 않을 수 있다.
- 기본 명령에서 X:가 비어 있다는 이유만으로 “NAS가 연결되지 않았다”고 말하지 않는다.
- 확인이 필요하면 승인된 제한 밖 읽기 전용 명령으로 `X:\kiwoom-monitor`를 재검증한다.
- NAS 쓰기는 대상 경로를 검증하고 `.env`, `postgres-data`, `server-data`를 보존하며 기존 파일을 백업한 뒤 수행한다.

## 이 PC의 테스트 앱 실행 경로

- 사용자가 여는 테스트 앱은 현재 워크트리 코드에 직접 연결되어 있다.
- 실행 진입점은 이 워크트리의 `scripts/run_test_app_with_data.py`이며, 스크립트가 자신의 `../src`를 `sys.path`와 `PYTHONPATH` 맨 앞에 넣는다. 메인·뉴스·매매일지 자식 프로세스도 같은 워크트리 소스를 사용한다.
- Python 실행기는 원본 프로젝트의 `.venv\Scripts\pythonw.exe`를 재사용하고, 사용자 데이터는 `C:\Users\pc-1\Documents\ChatGPT\kiwoom-realtime-monitor\data`를 사용한다. 이는 인터프리터와 실제 DB의 위치일 뿐, 원본 프로젝트 소스를 실행한다는 뜻이 아니다.
- 프로세스 명령줄에 원본 `.venv` 또는 원본 `data` 경로가 보인다는 이유로 “구버전 앱/원본 코드가 실행 중”이라고 추측하지 않는다.
- 코드 반영 여부를 의심하기 전에 실행 진입점이 워크트리의 `run_test_app_with_data.py`인지 확인하고, 그 스크립트의 `SOURCE_ROOT` 규칙을 확인한다.

나머지 코드·API·DB·배포 불변 규칙은 `DEVELOPMENT_GUARDRAILS.md`를 따른다.

## 구현 담당자 운영 원칙

목표는 가장 강한 모델을 계속 사용하는 것이 아니라, 필요한 품질을 한 번에 만족하는 **가장 낮은 모델과 추론 수준**으로 총비용을 줄이는 것이다. 다만 데이터 손상·주문 오류·보안·동시성 회귀처럼 실패 비용이 큰 작업은 처음부터 충분한 모델을 선택한다.

현재 작업의 실제 모델은 작업 시작 후 자동으로 바뀌지 않을 수 있다. 이 경우 모델을 바꿨다고 주장하지 않는다. 현재 모델로 안전하게 진행할 수 있는 분석·테스트·최소 수정은 계속하고, 실제 변경이 필요한 경우에만 정확한 권고 모델과 이유를 사용자에게 알린다.

### 기본 진행 원칙

- 기존 설계 문서와 현재 코드 구조를 기준으로 실제 구현을 계속한다.
- 단순 구현, 함수 추가, UI 작업, DB 처리, 테스트, 일반적인 버그 수정은 별도 확인 없이 진행한다.
- 매 단계마다 사용자에게 모델 변경 여부를 묻지 않는다.
- 구현 가능한 작업은 가능한 범위까지 계속 진행한다.
- 단순히 코드가 복잡하거나 파일이 크다는 이유만으로 설계 재검토를 요청하지 않는다.
- 기존 구조 안에서 합리적으로 해결할 수 있다면 그대로 구현한다.
- 모델 판단 때문에 구현 가능한 작업을 중단하거나 매 단계마다 사용자에게 선택을 요구하지 않는다.
- 파일 개수는 보조 지표일 뿐이다. 변경 범위가 작아도 주문, 계좌 신원, DB 마이그레이션, 자격증명, 동시성 경계를 건드리면 높은 위험으로 판단한다.

### 모델 역할

#### GPT-5.6 Luna — 명확한 반복 작업

- 권장 추론: Low, 필요한 경우 Medium
- 구현 위치와 방식이 이미 결정된 1~2개 파일의 작은 변경
- 문자열·문서·주석·타입·이름 변경, 동일 패턴 반복 적용
- 단순 CRUD, 작은 테스트 추가, 명확히 재현된 단일 원인 버그
- 구조·데이터 흐름·공개 계약 판단은 맡기지 않는다.

#### GPT-5.6 Terra — 기본 구현

- 권장 추론: Medium, 경계가 복잡하면 High
- 기존 구조 안의 일반 기능, UI, API, DB 처리와 테스트
- 보통 2~5개 주요 파일에 걸치며 기존 패턴과 호출 흐름을 이해해야 하는 변경
- 원인이 비교적 명확한 버그와 인터페이스를 유지하는 리팩터링
- 이 프로젝트의 새 작업은 별도 위험 신호가 없으면 Terra Medium을 기본 후보로 본다.

#### GPT-5.6 Sol — 복잡하고 회귀 위험이 높은 구현

- 권장 추론: Medium 또는 High, 매우 어려운 구현에만 XHigh
- 여러 계층이나 엔진의 인터페이스 및 핵심 데이터 흐름 변경
- DB+서버+UI 동시 변경, 비동기·스레드·프로세스·상태 수명 문제
- 주문·포지션 상태, 계좌 경계, 데이터 정합성, 성능 병목
- 여러 구현안 중 선택이 필요하지만 기존 아키텍처 경계는 유지 가능한 작업
- Terra로 두 번 유사한 수정·검증을 했는데 같은 근본 문제가 남은 작업

#### GPT-6 Astra — 설계 판단·난제·전체 감사

- 권장 추론: Medium 또는 High, 난도가 매우 높으면 XHigh
- 요구사항과 현재 구조의 충돌, 핵심 데이터 모델·모듈 책임·공개 계약 재설계
- 원인이 불명확하고 기존 아키텍처 자체가 원인일 가능성이 큰 문제
- 장기 확장성·성능·일관성 사이의 선택이 필요한 대형 기능 및 리팩터링 계획
- Ultra는 저장소 전체 감사, 시스템 전체 원인 분석, 여러 독립 영역의 병렬 감사처럼 범위 자체가 전체 시스템일 때만 권고한다.
- Astra가 설계를 끝내면 구현은 Sol/Terra, 반복 적용과 단순 테스트는 Terra/Luna로 다시 낮춘다.

사용 가능한 실제 추론 단계 명칭은 `Low`, `Medium`, `High`, `XHigh`, `Max`, `Ultra`를 따른다. `Light`, `Extra High`처럼 실행 환경에 없는 이름은 권고하지 않는다. `Max`는 XHigh로도 충분하지 않다는 구체적 근거가 있을 때만 사용한다.

### 작업별 라우팅

작업 시작 전에 다음 순서로 내부 판단한다.

1. 요구사항과 완료 조건이 명확한가
2. 실제 호출 경로와 데이터 소유자가 한 경계 안에 있는가
3. 공개 API·DB 스키마·프로세스 수명·동시성·주문·자격증명을 건드리는가
4. 실패 시 데이터 손상, 중복 주문, 장중 데이터 공백처럼 복구 비용이 큰가
5. 재현 테스트나 운영 로그로 원인을 좁힐 수 있는가

| 단계 | 판단 기준 | 기본 권고 |
| --- | --- | --- |
| Tier 1 | 방식이 하나로 정해진 작은 반복·문서·테스트·명확한 단일 수정 | Luna Low/Medium |
| Tier 2 | 기존 구조 안의 일반 기능과 비교적 명확한 버그 | Terra Medium |
| Tier 3 | 여러 계층, 상태·동시성·정합성, 높은 회귀 위험 | Sol Medium/High |
| Tier 4 | 설계 선택이 먼저 필요하거나 현재 구조와 요구가 충돌 | Astra Medium/High/XHigh |
| Tier 5 | 저장소 전체 감사 또는 시스템 전반 재설계 | Astra Ultra |

작업을 중요하다고 느끼는 정도만으로 상위 단계로 올리지 않는다. 반대로 파일 수가 적다는 이유로 위험한 변경을 Tier 1로 낮추지 않는다.

### 이 프로젝트의 위험 기준

시장 판단, 섹터·테마, 뉴스 판단, 타점, 포지션, 종목·실시간 데이터, 시뮬레이션, DB, UI는 서로 결과를 전달하는 연결 영역이다.

- 한 영역 내부의 표시·조회·명확한 저장 수정은 Terra를 기본으로 한다.
- 영역 사이 데이터 전달, 점수 결합, 실시간 저장·집계, 시뮬레이션과 실전의 공통 규칙은 최소 Terra High를 검토한다.
- 여러 판단 엔진의 인터페이스, 공통 상태 모델, 실시간 수신 구조, 주문·포지션 상태 머신, 백테스트와 실전 로직 통합, 원본·파생 데이터 정합성은 Sol을 우선 검토한다.
- 엔진 추가 방식, 전체 데이터 아키텍처, 주요 모듈 책임 재배치, 대규모 리팩터링 방향은 Astra를 우선 검토한다.
- 실제 주문·계좌·자격증명 변경은 구현 난이도와 별개로 검증 강도를 한 단계 높인다. 모델을 무조건 Astra로 올린다는 뜻은 아니다.

### 즉시 재평가 조건

- 예상과 달리 데이터 소유자나 실행 경로가 둘 이상 발견됨
- 기존 계약이 서로 모순되거나 구현 방식에 따라 장기 구조가 달라짐
- 동시성·취소·재시작·중복 처리·트랜잭션 경계 문제가 새로 드러남
- 수정이 주문, 계좌 신원, 비밀, 원본 데이터 보존에 영향을 줌
- 재현 테스트와 실제 로그가 서로 다른 원인을 가리킴
- 같은 가정과 접근으로 두 번 수정했는데 동일 문제가 남음

이 경우 무조건 한 단계씩 올리거나 바로 중단하지 않는다. 먼저 가정, 실행 경로, 재현 방법, 환경 문제 여부를 다시 확인한다. 안전하게 가능한 조사·테스트·독립 수정은 계속하고, 남은 부분에 필요한 최소 상위 단계만 권고한다.

### Astra 설계 재검토 조건

다음 조건에서는 임의로 큰 구조 변경을 하지 않고 `ASTRA 설계 재검토 필요`라고 표시한다. 범위에 따라 Medium/High/XHigh를 권고하며, 아래 사유만으로 곧바로 Ultra를 권고하지 않는다.

- 기존 설계 문서와 실제 코드 구조가 근본적으로 충돌
- 핵심 데이터 모델을 변경해야 함
- 주요 모듈 여러 개의 책임이나 경계를 다시 정의해야 함
- 기존 공개 인터페이스나 핵심 계약을 깨야 함
- 지금 구현하면 향후 기능 확장이 크게 어려워질 가능성이 높음
- 둘 이상의 구현 방식 중 선택에 따라 전체 아키텍처 방향이 달라짐
- 기존 설계의 핵심 가정이 실제 코드나 데이터와 맞지 않음
- 새 기능 때문에 현재 시스템의 책임 구조 자체를 변경해야 함
- 임시 우회 코드로만 해결 가능하고 기술 부채가 크게 증가할 것으로 판단됨

이 경우에도 설계 변경과 관계없이 안전하게 진행 가능한 작업은 계속하고, 설계 결정이 필요한 부분만 분리한다.

### Astra 재검토 보고 형식

Astra 재검토가 필요하면 다음 형식으로 충분한 맥락을 제공한다. Astra가 저장소 전체를 다시 분석하지 않아도 되도록 관련 파일, 데이터 흐름, 선택지를 구체적으로 적는다.

```text
### ASTRA 설계 재검토 필요

**권고 모델·추론**
- 예: Astra High

**현재 문제**
- 무엇이 기존 설계와 충돌하는가

**관련 영역**
- 관련 파일
- 관련 모듈
- 관련 데이터 흐름

**기존 설계를 그대로 유지할 경우**
- 장점
- 문제점
- 예상되는 기술 부채

**가능한 대안**
- 대안 A
- 대안 B
- 필요하다면 대안 C

**현재 추천안**
- 현재 코드 기준으로 가장 적절하다고 판단되는 방향

**Astra가 판단해야 할 핵심 질문**
- 설계자가 결정해야 하는 사항만 명확하게 정리
```

### 에스컬레이션 표시와 중단 기준

현재 모델로 안전하게 계속할 수 있으면 별도 보고 없이 진행한다. 실제 상위 모델이 필요할 때만 다음처럼 짧게 표시한다.

```text
[ESCALATION RECOMMENDED]
Current: Terra Medium
Recommended: Sol High
Reason: 실시간 수신과 DB commit의 취소·재시작 경계를 함께 변경해 race 회귀 위험이 높음.
```

현재 모델로도 원인 축소, 재현 테스트, 안전한 최소 수정이 가능하면 그 작업을 먼저 수행한다. 핵심 설계 결정이나 비가역 변경을 신뢰성 있게 할 수 없을 때만 해당 부분을 멈춘다. 단순히 상위 모델이 더 좋을 것 같다는 이유로 멈추지 않는다.

### 설계 문서 갱신

설계 문서는 고정 명세가 아니라 계속 갱신되는 문서로 취급한다. 구현 중 다음과 같은 구조적 변화가 생기면 관련 문서를 갱신한다.

- 실제 구현 방식이 설계와 달라짐
- 새로운 제약 조건 발견
- 데이터 구조 변경
- 모듈 책임 변경
- 새로운 확장 지점 생성
- 기존 설계에서 빠진 예외 상황 발견
- 기능 간 새로운 의존성 발견

단순 함수명 변경이나 사소한 코드 수정은 문서화하지 않는다. 장기적으로 다시 알아야 할 구조적 결정만 남긴다.

### 임시방편 금지

- 중복 로직 추가
- 기존 책임과 무관한 모듈에 기능 삽입
- 하드코딩으로 구조 문제 우회
- 순환 의존성 발생
- 전역 상태의 무분별한 추가
- 기존 인터페이스를 우회하는 별도 경로 생성
- 향후 제거 예정이라는 이유로 임시 구조를 핵심 코드에 추가

필요하면 구현 속도보다 구조적 일관성을 우선하되, 단순한 문제에 불필요한 추상화 계층을 추가하지 않는다.

### 과도한 설계 방지

현재 필요한 기능과 가까운 미래에 예정된 기능을 기준으로 설계하며, 미래의 막연한 가능성만으로 범용 프레임워크를 만들지 않는다.

- 사용처가 하나뿐인 인터페이스를 무조건 생성하지 않는다.
- 의미 없는 래퍼 계층을 만들지 않는다.
- 실제 요구 사항이 없는 플러그인 구조를 만들지 않는다.
- 팩토리·매니저·프로바이더를 지나치게 분리하지 않는다.
- 단순 기능을 지나치게 작은 파일로 분해하지 않는다.
- 코드 재사용 가능성만을 이유로 조기 추상화하지 않는다.

목표는 가장 추상적인 구조가 아니라 변경하기 쉬운 구조다.

### 단계별 완료 확인

각 의미 있는 구현 단계가 끝나면 다음을 확인한다.

- 기존 기능이 깨지지 않았는가
- 새 기능이 의도대로 동작하는가
- 테스트가 가능한 범위에서 통과하는가
- 기존 설계와 차이가 있는가
- 새 기술 부채가 생겼는가
- 다음 기능을 추가하기 쉬운 상태인가
- 문서 갱신이 필요한가

### 최종 보고 형식

작업 결과는 다음 수준으로 간단히 정리한다.

```text
**구현 완료**
- 변경된 핵심 내용

**변경 파일**
- 주요 파일만

**검증**
- 실행·테스트·확인 결과

**설계 문서 변경**
- 변경했다면 핵심 내용

**남은 문제**
- 실제로 남아 있는 것만

**모델 에스컬레이션**
- 없음
  또는
- 권고: 현재 모델/추론 → 추천 모델/추론 · 이유
  또는
- ASTRA 설계 재검토 필요: 권고 추론 수준 · 이유
```

사용자가 매번 모델과 추론 수준을 직접 판단하게 하지 않는다. 대부분의 작업은 Terra Medium 후보로 시작하고, 구현 복잡도와 위험이 확인될 때만 Sol로 올린다. 시스템 설계 판단이 필요할 때 Astra를 사용하며 Ultra는 전체 시스템 범위로 제한한다. 현재 기능을 완성하면서 다음 기능을 계속 추가하기 쉬운 구조를 유지한다.
