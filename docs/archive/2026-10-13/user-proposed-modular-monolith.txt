처음에는 판단 엔진 전체를 하나의 Python 패키지로 만들고, 필요할 때만 내부를 나누면 돼.
2. 모듈은 역할이 명확해야 해

특히 시장 판단, 타점 판단, 비중 결정, 주문을 분리하는 것이 중요해.
예를 들어 시장 판단이 바뀌었다고 주문 엔진을 고칠 필요가 없어야 해. 비중 계산 방식을 바꿔도 데이터 수집기까지 건드리는 일이 없어야 하고.
이것이 모듈을 나누는 이유야.
3. DB는 처음부터 다르게 설계하겠어
네 앱에서 가장 크게 바꾸고 싶은 부분 중 하나야.
지금까지는 수집하는 데이터가 많아질수록 저장 작업도 많아지고, 그때마다 DB 호출과 COMMIT이 늘어나는 문제가 있었잖아.
새 구조에서는 실시간 상태와 영구 보존 데이터를 처음부터 분리하겠어.

여기서 원본 녹화는 일반 DB 저장과 반드시 같은 경로일 필요가 없어.
예를 들어 고빈도 관측은 순차 파일에 효율적으로 기록하고, 연구에 필요한 확정 자료는 별도 배치로 DB에 반영할 수 있어. 중요한 것은 녹화 중 입력이 몰려도 기록 유실을 감지하고, 완전하지 않은 기록을 완전하다고 처리하지 않는 거야.
DB 구조도 테이블부터 대량으로 만들지 않고 실제 사용하는 저장·조회 패턴에 맞춰 설계할 거야.

5. 테스트 구조도 간단하게 가져가야 해
나는 테스트 파일 수나 전체 테스트 건수를 개발 품질의 목표로 삼지 않겠어.
대신 세 단계로 분리할 거야.

단, 주문 중복·자금 초과·데이터 유실·잘못된 체결 상태처럼 피해가 큰 기능은 변경과 관련되면 반드시 검사해야 해.
그리고 테스트를 추가할 때마다 다음 기준을 적용하겠어.
'이 테스트를 삭제하면 실제로 어떤 중요한 오류를 놓치게 되는가?'
명확하게 답하지 못하는 테스트나 내부 구현만 고정하는 테스트는 다시 검토해야 해.
단순 리팩터링을 하다가 자동으로 수십 개 테스트 파일을 늘리는 것도 피하고.

이것도 최종 파일 구성이 아니라 책임을 구분하기 위한 출발 예시야.
처음에는 뉴스 LLM도, 동적 비중도, 복잡한 연구 기능도 필요하지 않으면 구현하지 않는 거지. 빈 파일이나 미래에 사용할 추상화도 미리 만들지 않아.
기능이 커졌을 때만 해당 영역을 쪼개면 돼.
또한 UI·API·판단 엔진은 하나의 저장소에서 관리하되, UI가 멈춰도 서버 수집이 지속되어야 하고 무거운 연구가 실시간 주문을 방해하지 않도록 실행 단위를 분리할 수 있어야 해.
즉, 코드 모듈 분리와 별도 프로세스·서버 분리는 다른 결정으로 취급하는 거야.
7. 이 구조에서 처음 만들 기능
이번에는 개발 단위를 'DB 전체 완성', 'API 전체 완성', '테스트 기반 전체 구축'처럼 잡지 않겠어.
작은 기능 하나가 끝까지 동작하게 만들겠어.
순서	개발 목표	완료 기준
1	녹화 데이터로 매매 한 번 재현	동일 입력이면 동일 판단
2	진입·청산·체결·손익 연결	수량·현금·비용이 일치
3	실시간 데이터 연결	동일한 판단 엔진으로 실행
4	시장·테마·뉴스 판단 연결	실제 타점 판단에 근거 제공
5	비중·분할 운용 연결	목표 비중과 실제 주문 차이 검증
6	EV·연구·전략 개선	동일 자료에서 이전 정책과 비교
7	모의 장시간 운용	데이터·주문·복구 안전성 검증
중간에 필요 없는 기능이 있다면 억지로 만들지 않아. 반대로 실제 연결에 반드시 필요한 안전 기능은 처음부터 포함해야 해.

8. 가장 중요한 개발 원칙
이번에는 다음 여섯 가지를 지키고 싶어.
1. 기능 없이 구조만 만드는 작업을 최소화한다. 미래 확장 때문에 추상화·어댑터·서비스를 미리 늘리지 않는다.
2. 한 기능은 입력부터 결과까지 완성한다. 파일 여러 개에 이름만 만들고 미연결 상태로 남겨두지 않는다.
3. 데이터는 목적에 맞게 저장한다. RAM 최신 상태, 녹화 원본, DB 확정 자료, 조회 캐시를 구분한다.
4. 판단·비중·Risk·주문은 분리한다. 하지만 굳이 별도 서버로 만들지는 않는다.
5. 실시간과 Replay는 같은 핵심 로직을 사용한다. 입력의 시간·완전성 차이는 명확하게 기록한다.
6. 개발 범위를 임의로 확대하지 않는다. 리팩터링 중 발견한 개선점은 정말 필요한 경우를 제외하면 별도 후보로 남긴다.
여기에 뉴스 LLM은 실시간 판단을 보조하는 독립 작업으로 두고, LLM 응답을 기다리느라 주문·손절이 멈추는 구조는 피해야 해.
최종적으로 어떤 앱이 되어야 할까?
내가 생각하는 이상적인 앱은 기능 수가 적거나 코드 줄 수가 작은 앱만은 아니야.
내부 구현은 최소한으로 유지하면서도, 필요한 기능을 서로 독립적으로 발전시킬 수 있고 실제 연결 상태를 쉽게 검증할 수 있는 앱이야.
그리고 네 상황에서는 한 가지 더 중요해.
지금까지 만든 기능을 100% 복제하려고 하면 새 프로젝트도 금방 거대해질 수 있어. 따라서 기존 코드를 전부 옮기지 말고, 9월 20일 통합 설계를 최종 목적지로 삼되, 새 프로젝트가 실제로 사용하는 기능만 선택해서 가져오는 방식이 더 잘 맞을 것 같아.
처음부터 기존 프로젝트의 모든 문제를 해결하려 하지 않는 거지.
내가 지금 선택한다면 기존 프로젝트를 보존하고, 위 구조로 아주 작은 새 앱을 만들어 단일 매매 경로의 동작·성능·개발 복잡성을 비교하겠어. 그 결과를 보고 완전 전환 여부를 결정하는 게 가장 합리적이야.
