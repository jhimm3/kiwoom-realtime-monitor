# OpenAPI+ 검증 및 프로젝트 구조 설계 (참조용)

작성일: 2026-08-14  
상태: **현재 채택하지 않은 대안 설계.** 실제 구현 방향은 REST API이며, 이 문서는 비교·참조용으로 보관한다.

범위: 키움 **OpenAPI+** 구조 설계와 공식 문서 기반 사전 검증만 수행. API 호출·GUI·DB 기능은 구현하지 않음.

## 1. 결론

키움 **OpenAPI+**를 이 프로젝트의 유일한 증권 API로 채택한다. OpenAPI+는 Windows에 설치하는 OCX(ActiveX) 기반 API이며, 로그인·TR 조회·실시간 수신은 모두 이벤트 방식으로 처리해야 한다.

다만 명세의 일부는 문서 목록만으로 세부 응답 필드가 확정되지 않았거나, 계산에 필요한 정적 기준 데이터가 별도로 필요하다. 따라서 아래의 `확인 필요` 항목은 실제 App Key로 모의투자 응답을 저장·대조하기 전에는 구현하지 않는다.

## 2. 공식 OpenAPI+ 확인 결과

| 요구 데이터/기능 | 공식 문서에서 확인된 수단 | 상태 | 설계 결정 |
| --- | --- | --- | --- |
| 로그인·연결 | `CommConnect`, 연결 이벤트 | 확인 | OCX가 로그인 UI와 연결 결과 이벤트를 담당 |
| 국내주식 TR 조회 | `CommRqData` 요청과 수신 이벤트, `GetCommData` | 확인 | `OpenApiPlusGateway`만 OCX 메서드 호출 허용 |
| 실시간 시세 | 실시간 등록/해지, `OnReceiveRealData`, `GetCommRealData` | 확인 | 화면 Top 20을 실시간 등록 대상으로 관리 |
| 실시간 구독 한도 | 최대 200개 화면번호, 화면당 최대 100종목 | 확인 | 화면번호 1개에 Top 20 등록; 구독 해제도 동일 컴포넌트가 담당 |
| 순위 데이터 | OpenAPI+ TR 목록에서 후보를 KOA Studio로 검색 | 확인 필요 | 요구하는 ‘실시간 조회순위’의 정확한 TR·출력 필드는 실측 전 확정하지 않음 |
| 현재가·등락률·누적 거래량 | 실시간 종목체결 FID와 조회 TR로 획득 가능 | 부분 확인 | 실제 FID·TR 출력명은 KOA Studio와 수신 원문으로 계약화 |
| 1·5·60분 거래대금 | 분봉 TR 후보 존재 | 부분 확인 | 분봉 출력의 가격·거래량·시간대와 집계 방식 검증 필요 |
| 1일 거래대금 | 일봉/당일 시세 TR 후보 존재 | 부분 확인 | 장중 당일 값의 기준과 단위를 검증 필요 |
| 시가총액·유통비율 | 관련 TR/출력 필드가 명세 요구를 충족하는지 미확정 | 미확인 | 필드·단위 확인 전 거래강도 계산에 사용하지 않음 |
| 신고가/최근 N일 고가 | 순위 TR 및 차트 TR 후보 존재 | 부분 확인 | 기간별 정의와 연속조회 범위를 검증 필요 |
| 종목코드 목록·이름 매핑 | 시장별 코드 목록과 종목명 조회 메서드 제공 | 확인 | 코드가 식별자, 이름은 갱신 가능한 속성으로 저장 |
| 테마 데이터 | 테마그룹·구성종목 조회 메서드 제공 | 확인 | 사용자 테마 원천은 명세대로 Excel/수동 입력; API 테마는 참조용으로만 분리 |

### 호출 제한과 설계 영향

- TR 호출은 초당 5건, 분당 100건, 시간당 1,000건이다.
- 분당 또는 시간당 제한에 도달하면 안내 메시지가 표시되며 프로그램 재실행이 필요하다고 공식 안내되어 있다.
- 실시간 시세는 화면번호 최대 200개, 화면당 최대 100종목이다.

따라서 30초마다 순위 TR 하나만 요청하고, 그 결과 Top 20만 실시간 등록하는 구조가 적합하다. 반면 20개 종목마다 1·5·60분봉과 일봉을 매 30초 요청하면 분당 한도를 쉽게 넘는다. 거래강도는 캐시·순차 수집·요청 큐를 전제로 하며, API 실측 전에는 기본 화면의 필수 데이터로 확정하지 않는다.

## 3. 사전 검증(구현 전 계약 테스트) 목록

로그인 비밀번호·인증서 정보는 소스·문서·로그에 저장하지 않는다. OpenAPI+ 모듈과 모의투자 환경에서 다음만 실행하여 수신 원문(개인정보 제거)을 보관한다.

1. OpenAPI+ 모듈 설치, 로그인, 연결·종료 이벤트와 모의투자 접속을 확인한다.
2. KOA Studio에서 순위 TR 후보의 입력값, 순위 수, 종목코드·이름·현재가·등락률·거래량/거래대금 출력명을 확인한다.
3. 주식기본정보 TR의 시가총액 및 유통 관련 출력 필드와 단위를 확인한다.
4. 분봉/일봉 TR의 시간대·거래량·거래대금 출력을 확인하고, 1·5·60분·1일 집계가 중복 없이 가능한지 검증한다.
5. 실시간 종목체결 FID의 실제 값, 재연결, 등록 해제, 20종목 동시 수신을 확인한다.
6. 장중·장외·장 시작 전 수신과 호출 제한 오류를 확인한다.

검증 실패 또는 미제공인 필드는 `지원하지 않음` 상태로 UI에서 숨기고, 추정값으로 대체하지 않는다.

## 4. 제안 구조

```text
.
├─ docs/                         # 명세, API 검증 결과, 데이터 계약
├─ src/kiwoom_monitor/
│  ├─ application/               # 화면이 호출하는 유스케이스·스케줄 조정
│  ├─ domain/                    # Stock, Theme, Ranking, Strength 등 순수 모델/규칙
│  ├─ infrastructure/
│  │  ├─ openapi_plus/           # OCX 래퍼·이벤트 어댑터·TR 큐·실시간 등록·응답 변환
│  │  ├─ persistence/            # SQLite 저장소와 마이그레이션
│  │  └─ excel/                  # Excel 읽기·검증·변경 미리보기
│  ├─ presentation/              # PySide6 창·테이블 모델·대화상자
│  └─ bootstrap/                 # OCX 사전점검, 의존성 조립, 앱 진입점
├─ tests/
│  ├─ unit/                      # 도메인 계산, 테마 파싱, 저장소 단위 테스트
│  ├─ contract/                  # 저장된 키움 API 응답을 쓰는 변환 계약 테스트
│  └─ integration/               # SQLite·Excel·API 모의 연동 테스트
├─ data/                         # 실행 중 생성되는 SQLite/로그; Git 제외 대상
└─ pyproject.toml                # 의존성·품질도구·빌드 설정 (Phase 1에서 작성)
```

### 경계 원칙

- `domain`은 PySide6, HTTP, SQLite, pandas를 직접 알지 않는다.
- 키움의 TR 코드·FID·원본 필드명은 `infrastructure/openapi_plus` 밖으로 새지 않는다.
- UI는 `application`이 주는 화면용 모델만 소비한다.
- SQLite는 사용자 관리 데이터(테마·화면 설정·임계값·캐시 메타데이터)만 영속화한다. 실시간 시세는 메모리 상태가 원본이다.
- API 미확인 필드는 `None/미지원`으로 표현한다. 계산기에서 0으로 취급하지 않는다.

## 5. 데이터 모델 초안

| 영역 | 핵심 식별자 | 주요 내용 |
| --- | --- | --- |
| 종목 | `stock_code` | 이름, 시장, 정적 기본정보, 마지막 검증 시각 |
| 테마 | `theme_id` | 이름, 기본 색상 |
| 종목-테마 | `(stock_code, theme_id)` | 종목별 색상 재정의 |
| 화면 설정 | `setting_key` | 갱신 주기, 표시 열, 레이아웃, 경고 기준 |
| API 캐시 메타 | `(resource, stock_code)` | 취득 시각, 원본 버전, 만료 시각 |
| 실시간 화면 상태 | `stock_code` | 순위, 현재가, 등락률, 거래량/대금, 수신 시각 — DB 기본 저장 대상 아님 |

거래강도는 다음 전제 필드가 **검증된 경우에만** 계산한다.

```text
유통시가총액 = 시가총액 × 유통비율
거래강도(%) = 기간 거래대금 ÷ 유통시가총액 × 100
```

## 6. 단계별 구현 순서

1. **OpenAPI+ 계약 검증**: 위 6개 항목을 모의투자에서 확인하고 결과를 `docs/api-contract/`에 기록한다.
2. **Phase 1**: OpenAPI+ OCX가 동작하는 Qt 바인딩을 확정하고, 빈 GUI 셸·SQLite 마이그레이션·설정/로그 기반만 구현한다. TR/실시간 연결은 넣지 않는다.
3. **Phase 2**: 더미 데이터 기반 메인 테이블과 열 설정/배치만 구현한다.
4. **Phase 3–4**: 종목 마스터와 Excel 테마 반영을 구현한다.
5. **Phase 5**: 계약 테스트를 통과한 데이터에 한해 OpenAPI+ 순위 TR와 실시간 FID 수신을 연결한다.
6. **Phase 6 이후**: 분봉·기본정보 검증 결과가 충분할 때만 거래강도·신고가 기능을 추가한다.
