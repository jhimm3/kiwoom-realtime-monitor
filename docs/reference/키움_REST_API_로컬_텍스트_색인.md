# 키움 REST API 로컬 텍스트 색인

## 목적

- 원본: 프로젝트 루트의 `키움 REST API 문서.pdf` (855쪽)
- 같은 PDF를 매번 처음부터 렌더링·확인하지 않도록, 실제 개발에서 확인한 API의 읽을 수 있는 텍스트와 페이지를 누적한다.
- 원본 PDF는 한글 글꼴 매핑 때문에 일반 PDF 텍스트 추출 결과가 깨진다. 따라서 깨진 전체 덤프 대신 확인한 페이지를 정확히 전사하고, 새 API를 사용할 때 이 문서에 계속 추가한다.
- 문서 내용과 실제 REST 응답이 다르면 `실제 응답 확인`에 차이를 반드시 남긴다.

## kt00007 - 계좌별주문체결내역상세요청

### 기본 정보

- 메뉴: 국내주식 > 계좌 > 계좌별주문체결내역상세요청
- Method: `POST`
- URL: `/api/dostk/acnt`
- 운영 도메인: `https://api.kiwoom.com`
- 모의투자 도메인: `https://mockapi.kiwoom.com`
- 연속조회: 응답 헤더 `cont-yn=Y`이면 다음 요청에 `cont-yn=Y`와 응답의 `next-key`를 전달

### 요청 Body

| 필드 | 뜻 | 필수 | 값 |
|---|---|---:|---|
| `ord_dt` | 주문일자 | 아니요 | `YYYYMMDD` |
| `qry_tp` | 조회구분 | 예 | `1`: 주문순, `2`: 역순, `3`: 미체결, `4`: 체결내역만 |
| `stk_bond_tp` | 주식채권구분 | 예 | `0`: 전체, `1`: 주식, `2`: 채권 |
| `sell_tp` | 매도수구분 | 예 | `0`: 전체, `1`: 매도, `2`: 매수 |
| `stk_cd` | 종목코드 | 아니요 | 전체 종목은 빈 문자열 |
| `fr_ord_no` | 시작주문번호 | 아니요 | 전체 조회는 빈 문자열 |
| `dmst_stex_tp` | 국내거래소구분 | 예 | `%`: 전체, `KRX`, `NXT`, `SOR` |

매매일지 조회 기본값:

```json
{
  "ord_dt": "YYYYMMDD",
  "qry_tp": "4",
  "stk_bond_tp": "1",
  "sell_tp": "0",
  "stk_cd": "",
  "fr_ord_no": "",
  "dmst_stex_tp": "%"
}
```

### 응답 목록

- 목록 필드: `acnt_ord_cntr_prps_dtl`

| 필드 | 뜻 |
|---|---|
| `ord_no` | 주문번호 |
| `stk_cd` | 종목번호. 실제 응답은 주식의 경우 `A` 접두어가 붙을 수 있음 |
| `trde_tp` | 매매구분/주문유형 |
| `crd_tp` | 신용구분 |
| `ord_qty` | 주문수량 |
| `ord_uv` | 주문단가 |
| `cnfm_qty` | 확인수량 |

| `rsrv_tp` | 반대여부 |
| `ord_tm` | 주문시간. 실제 응답 필드, 형식 `HH:mm:ss` |
| `ord_dtm` | 주문시간. PDF 표기 필드, 구현에서는 호환용으로 함께 처리 |
| `ori_ord` | 원주문번호 |
| `stk_nm` | 종목명 |
| `io_tp_nm` | 주문구분. 실제 응답의 `현금매수`, `현금매도` 등으로 매수·매도 판별 |

| `dmst_stex_tp` | 국내거래소구분 |
| `cond_uv` | 스톱가 |

### 실제 응답 확인

- 확인일: 2026-08-29
- 실전 계좌, 주문일자 `20260828`, `qry_tp=4`로 읽기 전용 조회
- 체결 16건 반환 확인
- 실제 응답은 PDF의 `ord_dtm` 대신 `ord_tm`을 사용했다.
- `ord_tm` 값은 `09:08:56`처럼 콜론을 포함했다.
- 종목코드는 `A032820`처럼 `A` 접두어가 붙었다.
- `io_tp_nm`에 `현금매수 K`, `현금매도 K`처럼 매수·매도와 시장 표기가 함께 들어왔다.
- 구현은 `ord_tm → ord_dtm → cnfm_tm` 순서로 시간을 찾고, 종목코드의 `A/J/Q` 접두어를 제거한다.

## kt00015 - 위탁종합거래내역요청

### 기본 정보

- 원본 PDF: 420~423쪽
- Method: `POST`
- URL: `/api/dostk/acnt`
- 용도: 체결일별 실제 수수료·거래세·농특세와 정산금액 보완
- 요청 기간은 계좌 거래·정산일 기준이며, 실제 체결일은 응답의 `cntr_dt`를 사용해야 한다.

### 요청 Body

| 필드 | 뜻 | 사용값 |
|---|---|---|
| `strt_dt` | 시작일자 | `YYYYMMDD` |
| `end_dt` | 종료일자 | `YYYYMMDD` |
| `tp` | 구분 | `0`: 전체 |
| `stk_cd` | 종목코드 | 전체는 빈 문자열 |
| `crnc_cd` | 통화코드 | 빈 문자열 |
| `gds_tp` | 상품구분 | `1`: 국내주식 |
| `frgn_stex_code` | 해외거래소코드 | 빈 문자열 |
| `dmst_stex_tp` | 국내거래소구분 | `%`: 전체 |
| `qry_sort_tp` | 조회정렬구분 | `1`: 최근거래순 |

### 사용하는 응답 필드

- 목록: `trst_ovrl_trde_prps_array`
- `trde_dt`: 계좌 거래·정산일
- `cntr_dt`: 실제 체결일. 매매일지 체결과 연결할 때 반드시 이 날짜를 사용
- `stk_cd`, `stk_nm`, `io_tp_nm`: 종목과 매수·매도 구분
- `trde_qty_jwa_cnt`, `trde_unit`, `trde_amt`: 거래수량·단가·금액
- `exct_amt`: 정산금액
- `cmsn`: 수수료
- `trde_agri_tax`: 거래세·농특세
- `tax_sum_cmsn`: 세금·수수료 합계
- `proc_tm`: 처리시간. 실제 체결시간이 아니라 정산 처리시간일 수 있음

### 실제 응답 확인

- 확인일: 2026-08-29, 실전 계좌 읽기 전용 조회
- `trde_dt=20260828`인 행의 `cntr_dt`는 `20260826`, `proc_tm`은 정산 처리시간으로 반환됐다.
- 따라서 2026-08-28 당일 체결 비용은 아직 조회되지 않았으며, 결제 처리 후 나타난다.
- 2026-08-26의 `kt00007` 체결 19건과 2026-08-28 정산내역 16건 중 13건은 종목·매매구분·수량·단가로 개별 일치했다.
- 일부 체결은 정산내역에서 합산되므로 1:1 연결하지 않는다. 구현은 `cntr_dt + 종목 + 매수/매도`로 실제 비용을 합산하고, 같은 단위에 여러 매매 묶음이 있으면 거래금액 비율로 배분한다.
- 실제 비용이 아직 없으면 임의 추정하지 않고 `정산 대기`로 표시한다.

## kt00016 - 일별계좌수익률상세현황요청

- 원본 PDF: 424~426쪽
- Method: `POST`, URL: `/api/dostk/acnt`
- 요청: `fr_dt` 평가시작일, `to_dt` 평가종료일
- 주요 응답: `evltv_prft` 평가손익, `prft_rt` 수익률, `tern_rt` 회전율, 기간 내 총입금·총출금·총입고·총출고
- 종목별 또는 개별 매매 손익이 아니라 계좌 전체 기간 성과이므로, 개별 매매 비용 연결에는 `kt00015`를 사용한다.

## 분봉 관련 메모

- `ka10080` 1분봉은 한 요청에서 여러 봉을 반환한다.
- 한 페이지는 약 390개이며, 초기 보완은 연속조회 한 페이지를 추가해 최대 730개를 사용한다.
- 장중 매매일지는 선택한 한 종목만 첫 페이지로 보완한다.
- 과거 거래일 차트 또는 장 종료 확정은 필요한 종목·날짜만 연속조회한다.

## 유지 규칙

1. 새 API를 확인하면 API ID, 이름, PDF 페이지를 먼저 목차에 추가한다.
2. 요청·응답 필드는 실제 코드에서 사용하는 것만이라도 빠짐없이 기록한다.
3. PDF와 실제 응답 차이는 실제 응답 확인 절에 기록한다.
4. API 키, 계좌번호, 토큰, 개인 주문번호와 같은 민감정보는 기록하지 않는다.


## kt10002 - 주식 정정주문 (2026-11-05 원문 사본 확인)

프로젝트 원문 PDF 436~437/855쪽을 렌더링해 요청/응답 표와 예제를 확인했다. 원본은 수정하지 않았다. SHA256 `7de955070c922282a7300a918e5589a4123a84cacc8eca236f3ef8abdf4fa283`. 웹 공식 가이드의 TR 목록에도 kt10002가 있으나 개별 상세는 이번 웹 조회에서 확인하지 못했으므로 이 표는 고정한 로컬 원문 사본의 계약이며 실제 모의 broker 수락은 아니다.

- POST `/api/dostk/ordr`, API ID `kt10002`, 모의 도메인 `https://mockapi.kiwoom.com`.
- 필수 body: `dmst_stex_tp`, `orig_ord_no`(매수/매도 응답의 7자리 번호), `stk_cd`, `mdfy_qty`(1주 단위, `0`은 잔량 전부), `mdfy_uv`(원). 선택 `mdfy_cond_uv`(원).
- body 응답: `ord_no`는 **새 주문번호**, `base_orig_ord_no`는 **모주문번호**, `mdfy_qty`는 정정수량, `dmst_stex_tp`는 거래소다. 예제는 원0000139 → 새0000140/모0000139다.
- 따라서 정정 접수와 실제 체결/잔여 확인을 구분하고 원·새 번호 및 상세 체결 계보를 연결해야 한다. 기존 `REPRICE`의 취소→신규 경로를 kt10002 구현으로 부르지 않는다.
- 사용자 후속 기준: 접수 미체결의 같은 방향 가격 변경은 정정 우선이지만 **현재 조건을 다시 판단하는 원칙을 유지**한다. 명령 응답 불명을 미접수로 간주하거나 자동 재전송하지 않는다. 실제 키/계좌 주문은 이번 S12 개발 검증에 포함하지 않는다.

## 00 - 주문체결의 원주문번호 (2026-11-06 원문 사본 확인)

프로젝트 원문 PDF781/855쪽 전체를 렌더링해 확인했다. SHA256 `7de955070c922282a7300a918e5589a4123a84cacc8eca236f3ef8abdf4fa283`, 원본 변경0. 9203은 주문번호, 904는 원주문번호이며 원주문이 없으면 `0000000`이다. 909는 체결번호다. 기존 parser의 실제 unit FILL/계좌 scope 기준은 유지하고904만 optional metadata로 보존하며 선행0을 지운 숫자나 symbol 추정으로 대체하지 않는다. 이 확인은 고정 원문 계약과 합성 입력 검증이며 실제 모의/실전 수신 수락은 아니다.
