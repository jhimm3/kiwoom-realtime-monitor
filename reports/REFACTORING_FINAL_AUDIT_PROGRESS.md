## 2B. worker controller와 뉴스·매매일지 경계 — 완료

### 작은 worker controller

`presentation/*worker_controller.py` 13개를 생성·시작·완료·중단 경로까지 비교했다. 각 파일은 56~109줄이다.

| 분류 | 대상 | 실제 소유 책임 | 판정 |
| --- | --- | --- | --- |
| 장기 실행 | `RealtimeWorkerController` | 구독 worker 한 개의 생성, 9개 신호 전달, 코드 교체, 중단과 factory 교체 | ⚪ 유지 |
| 이중 작업 | `UpdateWorkerController` | 확인/다운로드 worker 두 개, 개별 중복 실행 차단과 다운로드 중단 | ⚪ 유지 |
| 결과 신선도 | `GoogleDriveWorkerController` | 실행 worker와 결과 worker 동일성 확인, 뒤늦은 이전 결과 차단 | ⚪ 유지 |
| 취소 가능한 작업 | `ImageThemeOcrWorkerController` | 저우선순위 시작, 취소, 진행·결과 수명 | ⚪ 유지 |
| 순차·후속 작업 | `MinuteHistoryWorkerController`, `KrxStockCatalogWorkerController` 등 | 실행 문맥, 형식 검증, 완료 뒤 후속 단계와 QThread 해제 | ⚪ 유지 |
| 반복 형태 | 일봉/기본정보/역사 신고가/NXT controller | factory·중복 실행·형식 검증·완료 해제 형태가 유사 | 🟡 향후 후보 |

유사한 네 controller를 범용 기반 클래스로 묶으면 신호 인수와 worker 생성자의 차이를 처리하기 위한 제네릭·분기·추가 파일이 필요하다. 현재는 한 기능의 호출 깊이만 늘고 실제 결함 감소가 명확하지 않으므로 통합하지 않는다. 같은 수명 버그가 다시 여러 controller에 반복될 때만 작은 내부 helper를 우선 검토한다.

### `MainWindow` worker 호환 속성

`_ranking_worker` 등 14개 읽기 전용 속성은 controller의 현재 worker를 노출한다. 이름만 보면 중복처럼 보이지만 실제 호출자는 다음과 같다.

- API 연결 방식을 바꿀 때 관련 worker 전체를 중단하고 종료 대기
- 순위 조회 직전 저우선순위 작업을 양보시키는 우선순위 보호
- 앱 종료 시 실행 중 QThread 목록과 사용자 표시 이름 구성
- 기존 실시간 worker의 생존 여부 및 테스트 대기 확인

속성을 없애면 각 호출자가 controller 구현을 직접 알거나 새로운 worker 집계 계층이 필요하다. 객체 생성이나 I/O도 없으므로 시작 성능 부담은 사실상 없다. 현 단계에서는 ⚪ 유지한다.

### 뉴스 창

`StockNewsWindow`는 1,030줄이지만 준비·검색·AI라는 서로 다른 세 QThread의 최신 요청, 자동 분석 대기열, 선택·렌더링 상태를 한 창 수명 안에서 조정한다. 계산 정책과 화면 문구는 이미 `news_execution.py`, `news_view_model.py` 등으로 분리돼 있다. 새 coordinator를 추가하면 창 상태를 다시 전달하는 얇은 계층이 될 가능성이 높아 추가 분리는 보류한다.

`dispose_finished_worker()`는 짧지만 `finished` 이후 `wait()`와 `deleteLater()` 순서를 한 곳에 고정하고 단위 테스트가 있어 제거 이득이 없다. ⚪ 유지한다.

종료 시 준비 worker는 최대 3초, 검색·AI worker는 각각 최대 10초 동기 대기한다. 검색/AI에는 중단 요청이 있으나 준비 worker에는 없다. 코드상 조건부 종료 지연 가능성은 확인됐지만 잔류나 시간 초과가 재현된 것은 아니다. 🟠 측정 후보로 남기고 지금 구조를 바꾸지 않는다.

### 매매일지 창

`JournalWindow`는 1,841줄이며 여전히 화면 상태와 다섯 QThread를 직접 조정한다. 그러나 worker마다 역할이 다르고 시장지수·일봉은 실행 중 들어온 최신 요청 한 건을 보존해야 한다. 이들을 동일 controller 형태로 옮기면 상태 전달 파일만 늘 수 있어 현 단계에서는 ⚪ 유지한다.

중앙 매매일지 동기화의 `CentralJournalSyncRunner`는 단일 실행 상태와 daemon thread, 오류 경계를 소유하므로 단순 wrapper가 아니다. ⚪ 유지한다.

종료는 최대 3초 대기를 worker 다섯 개에 순차 적용한다. 이론상 지연 상한은 누적될 수 있지만 보조 프로세스의 상위 종료 경계와 회귀 테스트가 있고 실제 잔류는 이번 감사에서 확인되지 않았다. 뉴스 창과 함께 실측 뒤에만 고칠 🟠 후보로 남긴다.

### 2B 결론

- 🔵 실제로 되돌릴 가치가 확인된 과추상화는 없다.
- 시작 때 controller는 QObject와 signal 연결만 만들며 worker를 시작하지 않는다. 2A의 빈 `MainWindow` 생성 약 0.04초 결과와도 일치한다.
- 작은 controller 통합, 뉴스/매매일지 추가 분리는 현재보다 확실히 좋아진다는 근거가 없어 하지 않는다.
- 단계 3의 최소 수정 후보는 아직 확정하지 않았다. 뉴스·매매일지 종료 대기는 실제 시간 측정이나 잔류 재현이 있어야 선택한다.

### 실제 운영 로그에서 추가 확인한 병목

`monitor-20260911.log`에는 뉴스 프로세스의 `중앙 콘텐츠 동기화 완료`가 약 1분마다 기록되고, 매회 내려받기 수가 약 18,724~18,792건이며 `로컬 변경=True`였다.

호출 흐름을 추적한 결과:

1. `news_process.schedule_content_sync()`가 `monitor.sqlite3`와 `news.sqlite3` **파일 전체 수정 서명**을 비교한다.
2. 실시간 순위·분봉 등 콘텐츠와 무관한 정상 저장도 `monitor.sqlite3` 서명을 바꾼다.
3. 이를 뉴스/테마 변경으로 판단해 `CentralContentSyncService.push()`가 뉴스·AI·테마 전체를 다시 전송한다.
4. 중앙 `upsert_documents()`는 내용이 같아도 모든 문서의 `updated_at`을 현재 시각으로 바꾼다.
5. 다음 `pull(updated_after=cursor)`에서 방금 갱신된 전체 문서를 다시 내려받는다.

따라서 이는 🔴 **실제 병목 가능성이 매우 높은 확인된 동기화 피드백 루프**다. 네트워크 작업 자체는 daemon thread라 메인 Qt 루프를 직접 기다리게 하지는 않지만, 매분 대량 네트워크·NAS DB·로컬 SQLite 쓰기를 발생시켜 앱과 NAS의 디스크/DB 경합을 만들 수 있다. controller 계층의 비용이 아니라 중앙 콘텐츠 변경 감지 범위가 너무 넓은 것이 원인이다.

### 시작 속도 원인 우선순위

2. 🟡 Python/PySide import: 보통 약 0.5초, 냉간 1회 2.32초
3. 🔴 show 이후 매분 중앙 콘텐츠 전체 재동기화: 순수 시작 지연은 아니지만 지속 체감 성능 저하의 가장 강한 원인
4. 🟡 실제 순위 응답: 운영 로그상 약 0.13~2.8초 편차가 있으나 QThread이며 창 표시를 막지 않음
5. 🟠 검증된 이전 매매일지가 살아 있을 때의 최대 2초 종료 대기: 코드상 조건부이며 이번 계측에는 발생하지 않음

- `MainWindow` 생성과 첫 UI 배치는 합계 약 0.05초 수준이다.
- 구조를 되돌리거나 controller를 합칠 성능상 이유는 없다.
- 단계 3에서 수정할 확인된 최소 항목은 **뉴스 프로세스의 중앙 콘텐츠 전체 재동기화 피드백 루프 1건**이다.
- 일봉 정리, 종료 대기, 냉간 import는 측정값을 보존하되 이번 종료 수정 범위에는 넣지 않는다.

### 수정 여부

제품 코드는 변경하지 않았다. 읽기 전용 계측 스크립트와 감사 문서만 추가·갱신했다.

## 3. 확인된 동기화 피드백 루프 최소 수정 — 완료

### 재현

운영 로그와 호출 경로로 확인한 불변 조건을 `test_news_process.py`에 먼저 추가했다.

- `monitor.sqlite3`만 바뀌면 뉴스 콘텐츠 서명은 바뀌지 않아야 한다.
- `news.sqlite3`가 바뀌면 뉴스 콘텐츠 서명은 바뀌어야 한다.

워크트리 소스를 명시한 수정 전 실행은 `_news_content_signature`가 없어 실패했다. 첫 unittest 실행이 원본 프로젝트 `src`를 읽은 것은 제품 오류가 아니어서 결과에서 제외하고, 이후 모든 실행은 워크트리 `src`를 `PYTHONPATH`로 고정했다.

### 최소 수정

`news_process.py`의 60초 동기화 판단에서 `monitor.sqlite3` 파일 서명을 제거하고 `_news_content_signature(news.sqlite3)`만 사용한다.

- 뉴스/AI 저장은 기존처럼 다음 주기에 중앙으로 올라간다.
- 중앙 변경분 pull과 영속 cursor는 그대로 유지된다.
- 테마 변경은 이미 메인 프로세스의 `CentralThemeSyncDispatcher`가 `replace_themes()`로 전송하므로 손실되지 않는다.
- NAS API, DB schema, TR 순서, 메인 실시간 처리에는 변경이 없다.

### 검증

| 검증 | 결과 |
| --- | --- |
| 수정 전 새 불변 조건 | 실패 확인 |
| 뉴스 프로세스·중앙 콘텐츠·테마 동기화 | 10개 통과 |
| 뉴스창 UI·worker 정리·자동 AI·화면 모델 포함 인접 회귀 | 30개 통과 |

테스트 도중 새 helper 삽입 위치 때문에 `_file_signature`의 정상 반환문이 밀린 오류가 한 번 발생했으나, 같은 회귀가 즉시 탐지했다. 함수 경계만 바로잡은 뒤 위 30개가 모두 통과했다.

### 보류 유지

일봉 시작 정리, 냉간 import, 뉴스/매매일지 조건부 종료 대기, worker controller 통합은 확인된 피드백 루프와 무관하므로 수정하지 않았다. `REFACTORING_CLOSEOUT_PLAN.md`의 최종 보류 원장에 그대로 남긴다.

## 4. 기존 보류 항목 최종 감사 — 완료

### TOP20 시장 분류와 저장 복구

- 실제 NAS `ka00198` 저장 응답에는 날짜·시각·종목코드·종목명·순위·가격·등락 필드만 있고 KOSPI/KOSDAQ 필드는 없었다.
- 공식 KRX 상장종목 페이지를 순수 파서로 읽어 `stock_catalog` 중앙 문서에 저장하고, NAS 독립 TOP20 수집기가 이를 사용하도록 연결했다. 실조회 2,802건은 KOSPI 847, KOSDAQ 1,841, KONEX 114였다.
- 네트워크 갱신 실패 시 저장된 카탈로그를 사용하며, 카탈로그에도 없는 종목은 시장을 추측하지 않고 `unknown`으로 남긴다.
- TOP20 지수 DB 저장 실패 자료는 이제 `/app/data/top20-index-outbox.json`에 먼저 원자 저장하고 성공 후 제거한다. 새 서비스 인스턴스의 재시작 복구 회귀가 통과했다.

### PostgreSQL 경계

- 공통 codec 밖에 남은 차이는 연결 수명, 트랜잭션 객체, `?`/`%s`, JSONB와 DATE/TIME 변환 등 실제 DB 방언 책임이다. 이를 한 실행 계층으로 합치면 분기와 호출 깊이만 늘어나므로 현재 유지한다.
- `scripts/check_postgres_integration.py`는 중앙 스키마 v2 마이그레이션, 쿼리 캐시, 실시간 최신값, 분봉, 일봉, 관측 메타데이터, 데이터셋, 문서, 외부 봉, 롤백을 실제 PostgreSQL에서 왕복하고 검증 자료를 삭제한다.
- 개발 PC에서는 NAS PostgreSQL 5432를 직접 노출하지 않는 구성이므로 실제 실행은 누적 이미지 배포 후 서버 컨테이너 안에서 수행한다. 이 실행 전에는 PostgreSQL 실검증 완료라고 하지 않는다.

### 시작·조회·종료

- 실제 268MB DB 복제본에서 분봉 30일 정리는 최대 0.64초, 일봉 250개 정리는 0.12초가 걸렸다. 둘을 창 표시 전 경로에서 제거하고 첫 화면·최초 순위 처리 뒤 30초에 같은 유지보수 thread에서 실행한다.
- 변경 후 `bootstrap` 진입부터 `show()`는 0.0744초였다. import 0.5381초는 별도이며, 보존 정책은 그대로 유지된다.
- 실제 매매일지 DB 315묶음에서 유형·회차 수정·복기 개별 조회는 0.4356초, 일괄 조회는 0.0048초였다. 요약 렌더링과 백필 상태 조회를 batch API로 바꾸고 단건 API 호환은 유지했다.
- 뉴스/매매일지 종료 경로는 현재 프로세스 목록, 최신 로그와 35개 프로세스/QThread 회귀에서 잔류·지연을 재현하지 못했다. 확인되지 않은 종료 구조 변경은 하지 않았다.

### 과추상화·대형 UI

- 13개 worker controller는 56~109줄이며 worker 현재 참조, 중복 실행 차단, 신호 형식, 완료 해제, 후속 요청 중 하나 이상을 소유한다. 범용 controller 통합은 콜백·분기와 호출 깊이를 늘리므로 현재 유지한다.
- `main_window.py`와 `stock_news_window.py`는 크지만 계산·수명 정책이 이미 별도 모듈로 이동했고, 이번 감사에서 독립적으로 떼어낼 새 책임이나 결함 집중이 확인되지 않았다. 크기만으로 추가 분리하지 않는다.

### 명칭과 테마 호환

- 사용자 UI의 선택지는 `이 PC에서 키움 API 직접 연결`과 `NAS로 연결`이다. `local_server`와 `personal_server`는 기존 `data_source.json`, 테스트, 장애전환 경로를 위한 내부 호환 값이므로 일괄 이름 변경하지 않는다.
- 실제 사용자 DB에는 구형 `themes/stock_themes` 108/773행과 현행 프로필형 `theme_profiles/profile_themes/profile_stock_themes` 2/273/2,040행이 함께 있다. 현행 편집은 프로필형 테이블을 사용하고 구형 테이블은 최초 이전·구형 백업 복원에 사용된다.
- 데이터 이전·백업 호환을 깨는 삭제나 양방향 동기화는 하지 않는다. 이 둘은 활성 이중 쓰기가 아니라 현행 저장소와 읽기 전용 호환 원본의 경계다.

### 운영 기준선

- 배포 전 현재 NAS 실행본은 `2026.09.11-db-codec-v1`, uptime 7,430초, 서버 프로세스 약 119MB, 컨테이너 약 154MB, DB 약 283MB였다.
- 인증 API, capabilities, 자원 진단, WebSocket ready/pong, ranking/TOP20/market-state 저장 조회가 실제 NAS에서 통과했다.
